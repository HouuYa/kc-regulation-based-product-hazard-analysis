# `humanize-korean` 스킬 보완 계획

작성일: 2026-09-04  
대상: `skills/humanize-korean/`  
목표: AI 번역투를 줄이면서도 KC안전기준 분석 콘솔의 기술적 의미·정책적 표현·수치를 훼손하지 않는 반복 윤문 체계 구축

## 1. 현재 스킬의 상태

현재 스킬은 다음 기능을 갖추고 있다.

- Fast·Strict 모드 구분
- 번역투(A), 영어 병기(B), 구조적 AI 표현(C), 관용구(D), 리듬(E), 완곡 표현(G), 접속사(H), 형식명사(I), 행정 문체(K) 탐지
- 원문 보존·근거 기반 수정·장르 유지·과윤문 방지의 4대 철칙
- 변경률·S1/S2 잔존 수·문장 길이 분산을 계산하는 `metrics.py`
- 정부·정책 문서용 `gov-patterns.md`

이 구조는 일반적인 한국어 윤문에는 적합하다. 다만 이 프로젝트에 적용할 때는 아래 세 가지를 더 분명히 해야 한다.

1. 화면 문구와 설계문서·법령·원문 데이터는 같은 방식으로 윤문하면 안 된다.
2. 쉬운 표현으로 바꾸는 과정에서 시스템 상태와 업무 절차의 의미가 달라질 수 있다.
3. 현재 `metrics.py`는 패턴 수를 세지만, 코드·수치·직접 인용·상태값이 보존됐는지는 확인하지 않는다.

## 2. 보완 목표

### 목표 A. 문서 장르별 처리 분리

| 대상 | 기본 강도 | 허용 범위 | 특별히 보존할 것 |
|---|---|---|---|
| 관리자 화면 문구 | 표준 | 짧고 행동 중심으로 수정 | 버튼 동작, 상태명, 다음 행동 |
| 운영 알림 | 보수적 | 불필요한 번역투만 수정 | 오류 코드, HTTP 상태, 작업명, 수치 |
| README·사용 안내 | 표준 | 쉬운 설명으로 재작성 가능 | 기능 범위, 처리 순서, 제한사항 |
| 00·01 설계문서 | 보수적 | 문장 흐름만 다듬음 | 설계 결정, 대안, 근거, 미확정 사항 |
| 법령·안전기준 원문 | 윤문 금지 | 인용·원문 그대로 표시 | 조문, 조항번호, 허용치, 시험조건 |
| `구현이력.md` | 보수적 | 담당자용 설명만 다듬음 | 실측 수치, 사고 경위, 결정 이유 |

### 목표 B. 프로젝트 고유 용어를 별도 보호

`태깅`, `임베딩`, `HF`, `DT`, `GPC`, `RRF`, `리랭킹`, `시험방법`, `시험 항목·허용치`, `원문 확인함`, `자동 작업`, `기준 사각지대`는 문맥에 따라 의미가 달라질 수 있다.

- 코드·컬럼·모델명·마이그레이션명은 바꾸지 않는다.
- 화면에서는 공식 용어를 먼저 쓰고, 첫 등장 또는 도움말에서만 쉬운 풀이를 붙인다.
- 같은 상태를 화면마다 다른 표현으로 바꾸지 않도록 `src/lib/terms.ts`의 표준 표현을 우선한다.
- `위반`, `부적합`, `안전함`처럼 시스템이 자동 판정하는 것으로 읽힐 수 있는 표현은 새로 만들지 않는다.

### 목표 C. 의미 보존을 정량 검증

현재 지표에 다음 검사를 추가한다.

- 숫자·단위·날짜 보존 여부
- 코드·경로·환경변수·URL 보존 여부
- 법령·직접 인용·안전기준 조항 보존 여부
- 화면 상태값과 버튼 라벨의 1:1 대응 여부
- 화살표 업무 흐름의 단계 수와 실제 화면 기능 일치 여부
- 변경된 문구가 원래의 책임 주체를 바꾸지 않았는지 여부

예: `담당자가 확인합니다`를 `시스템이 확인합니다`로 바꾸면 문장은 자연스러워져도 업무 책임이 바뀐다. 이런 변경은 문체 개선이 아니라 기능 의미 변경으로 간주해 차단한다.

## 3. 스킬 파일 보완안

### 안 1. 현재 스킬에 프로젝트 보존 규칙만 추가

**추가 파일**

- `references/project-terms.md`
- `references/project-preservation.md`

**내용**

- 화면 표준 용어와 금지 표현
- 00·01 문서의 설계 용어 보존 목록
- 법령·안전기준·수치·코드·상태값 보호 규칙
- `src/lib/terms.ts`를 기준 사전으로 사용하는 방법

**장점**

- 기존 스킬 구조와 출력 형식을 유지한다.
- 일반 한국어 윤문과 이 프로젝트의 예외 규칙을 쉽게 결합할 수 있다.

**단점**

- 대상 파일별 처리 순서를 SKILL.md에서 추가로 설명해야 한다.
- 프로젝트가 커지면 보존 목록이 길어질 수 있다.

### 안 2. 화면 문구 전용 모드를 신설

**추가 모드**

```text
UI 모드: 화면 문구·버튼·상태·도움말을 윤문
설계문서 모드: 설계·근거·미확정 사항을 보수적으로 윤문
운영알림 모드: 짧은 장애·처리 결과 문구를 윤문
```

**장점**

- 화면에서 긴 설명을 줄이는 작업과 설계문서 윤문을 분리할 수 있다.
- “쉽게 쓰되 책임과 상태는 보존한다”는 기준을 명확히 적용할 수 있다.

**단점**

- 사용자 intake와 출력 형식이 복잡해진다.
- 모드 선택을 잘못하면 적절한 보존 규칙이 적용되지 않을 수 있다.

### 안 3. 스킬과 코드 사전 연동

`src/lib/terms.ts`에서 화면 표준 용어를 읽어 윤문 시 보호 목록으로 사용한다.

**장점**

- 화면 코드와 윤문 스킬의 용어가 어긋날 가능성이 줄어든다.
- 용어를 한 곳에서 바꾸면 화면·윤문 결과 기준을 함께 갱신할 수 있다.

**단점**

- 스킬이 특정 저장소 구조에 의존한다.
- 일반 문서 윤문 스킬로 재사용하기 어렵다.

### 권고안

**안 1을 기본으로 적용하고, 안 2를 얇게 추가한다. 안 3은 이 저장소에서 실행하는 보조 검증 도구로만 둔다.**

스킬 자체는 범용성을 유지해야 하므로 저장소 코드를 직접 import하지 않는다. 대신 `project-terms.md`에 화면 표준 용어를 복사해 두고, 변경 시 `src/lib/terms.ts`와 수동 대조한다.

## 4. 세부 실행 계획

### 1단계. 보존 목록과 표준 용어 확정

- `src/lib/terms.ts`의 표준 화면 용어를 추출한다.
- 00·01 문서에서 보존해야 할 설계 용어와 정책 표현을 목록화한다.
- 절대 바꾸지 않을 항목을 지정한다: 수치, 단위, 날짜, 코드, URL, 법령 조문, 직접 인용, 제품명, 모델명, DB·API 이름.
- 바꿔도 되는 표현과 바꾸면 안 되는 표현을 예시로 쌍을 만든다.

### 2단계. 프로젝트 참고자료 추가

- `references/project-terms.md`: 권장 용어, 쉬운 풀이, 금지 대체어, 사용 장르
- `references/project-preservation.md`: 의미 보존 검사 목록과 화면 상태 보존 규칙
- `SKILL.md`의 STEP 1에 프로젝트 참고자료를 장르별로 읽는 규칙 추가
- 화면 문구 요청이면 UI 모드, 설계문서 요청이면 보수적 모드로 자동 판정

### 3단계. 정량 검사 강화

`metrics.py`에 다음 출력을 추가한다.

- 보호 토큰 원문·윤문 일치 검사
- 문장별 변경 위치 목록
- 권장 용어 위반 목록
- 금지 표현 잔존 목록
- 변경률과 함께 “의미 보존 검사 통과/확인 필요” 표시

자동 검사가 모든 의미를 판정할 수는 없으므로, 통과가 곧 내용 검토 완료라는 뜻은 아니라고 출력한다.

### 4단계. 저장소 문구 일괄 점검

- `src/app`, `src/components`, `src/lib/terms.ts`, `README.md`, `구현이력.md`를 대상 목록으로 삼는다.
- 코드·SQL·법령 인용·안전기준 원문 데이터는 윤문 대상에서 제외한다.
- 화면 문구는 UI 모드로, 문서와 이력은 장르에 맞는 보수적 모드로 처리한다.
- 각 파일별 변경률을 기록하고 30% 초과 파일은 사용자 검토 대상으로 남긴다.

### 5단계. 회귀 검증

- 용어 사전과 실제 화면 문구가 일치하는지 검색한다.
- `npm run typecheck`로 JSX·문자열 변경에 따른 코드 오류를 확인한다.
- `npx next build`로 전체 페이지 빌드를 확인한다.
- 버튼 라벨·상태값·업무 흐름이 실제 링크와 기능에 대응하는지 브라우저에서 확인한다.
- 00·01 문서의 숫자·코드·직접 인용이 바뀌지 않았는지 diff로 확인한다.

## 5. 권장 출력 형식 보완

현재 출력 형식에 다음 항목을 추가한다.

```text
## 윤문 결과 — [문서명]

> 장르 X | 모드 UI/설계문서/운영알림 | 등급 X | 변경률 X.X%
> 보호 항목 보존: 통과/확인 필요 | 담당자 의미 검토: 필요/불필요

### 변경 내역
변경된 span, 탐지 코드, 교정 이유

### 보존 항목 확인
- 수치·단위·날짜:
- 코드·URL·고유명사:
- 법령·직접 인용:
- 상태값·책임 주체:

### 최종 윤문본
...
```

특히 화면 문구를 바꾼 경우 “담당자에게 보이는 의미가 바뀌지 않았는지” 확인 결과를 반드시 남긴다.

## 6. 완료 기준

- 같은 프로젝트 용어가 화면마다 다른 이름으로 바뀌지 않는다.
- 00·01 문서의 설계 결정과 미확정 사항이 윤문 과정에서 확정된 것처럼 바뀌지 않는다.
- 수치·코드·법령·직접 인용·상태값·책임 주체가 보존된다.
- 화면 문구는 짧아져도 다음 행동과 처리 책임이 분명하다.
- 변경률 30% 초과 시 경고하고, 50% 초과 시 자동 중단한다.
- 문체 규칙 검사와 별도로 `typecheck`, `build`, 화면 회귀 검증을 수행한다.
- 윤문 결과가 “자연스러움”만 평가하지 않고 정확성·일관성·업무 이해 가능성을 함께 평가한다.

## 7. 이번 단계에서 미루는 것

- LLM을 이용한 자동 대량 윤문
- 완전 자동 의미 동등성 판정
- 모든 저장소 문서의 일괄 재작성
- 새로운 번역학 패턴을 대규모로 추가하는 v2.0 작업
- Canvas 결과 화면

MVP에서는 먼저 보존 목록과 프로젝트 용어 사전을 확정하고, 대표 화면 2~3개와 00·01 문서의 짧은 구간으로 시험한 뒤 전체 적용한다.
