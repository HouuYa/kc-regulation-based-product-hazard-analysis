# 화면 구조 개편 — 탭에서 URL 분리 · 처리중 표시 보완 · 좌우 메뉴 기본 숨김

## 0. 출처

`claude.ai/design` 프로젝트 "Project wireframe improvement planning"의
`Analysis Screen Wireframes.dc.html`과 그 안의 구현 지시서
`handoff/a안-적용-구현지시서.md`. 그 문서에서 "a안 전부 적용 — 사고보고서·리콜
포함"으로 확정된 세 가지(1a·2a·3a)를 그대로 코드에 옮긴 것이 이 라운드다.

## 1. 1a — 검토/인사이트, 현황/처리할 것을 탭에서 URL로

`화면_구조_개편_검토_인사이트_분리_2026-09-12.md`가 설계한 탭 방식(같은 URL,
`Tabs.tsx` + `?tab=` 쿼리)을 실제로 써 보니 "탭도 결국 또 하나의 내비게이션"
이라는 지적이 나왔다. 그래서 URL 자체를 가른다 — 링크를 누르면 진짜 다른
화면으로 이동한다(브라우저 뒤로가기·북마크·공유 링크가 그대로 작동).

| 전 | 후 |
| --- | --- |
| `/analysis/[caseId]?tab=review\|insight` | `/analysis/[caseId]`(검토, 기본) · `/analysis/[caseId]/insight`(인사이트) |
| `/accidents?tab=status\|todo` | `/accidents`(처리할 것, 기본) · `/accidents/status`(현황) |
| `/recalls?tab=status\|todo` | `/recalls`(처리할 것, 기본) · `/recalls/status`(현황) |

`standards/review`는 애초에 탭이 없어(단독 검수 화면) 대상이 아니다 — 073
설계문서 §2 감사 결과 그대로다.

### 1.1 공통 부분은 어떻게 두 화면이 나눠 쓰는가

- **accidents·recalls**: 목록·집계 조회(`load()`, 상수)를 `data.ts`로 뽑아
  두 페이지(`page.tsx`, `status/page.tsx`)가 같이 가져다 쓴다(CLAUDE.md §9).
- **analysis/[caseId]**: 사건 요약·품목·적용기준(어린이제품 확정 버튼 포함)은
  검토·인사이트 둘 다 봐야 하는 진짜 공통부분이라, `layout.tsx`로 옮겨
  **한 번만** 그린다. `page.tsx`(검토)와 `insight/page.tsx`는 그 아래
  `{children}`으로 들어간다.
  - 어린이제품 확정 버튼을 레이아웃에 남긴 이유는 073 문서 §3.1 그대로다 —
    "품목·적용기준"과 "그걸 바꾸는 버튼"이 떨어지면 헷갈린다.
  - 레이아웃과 두 페이지가 전부 같은 사건 조회(`load(caseId)`)를 부른다.
    그대로 두면 한 요청에서 DB를 세 번 왕복하므로, `data.ts`의 `load`를
    React `cache()`로 감쌌다 — 같은 렌더(요청) 안에서 같은 인자로 부른
    호출을 하나로 묶어 주는, Next.js가 이런 레이아웃+페이지 데이터 공유에
    공식으로 권하는 방법이다. 이 저장소에 `cache()`를 쓴 첫 자리다.
  - `layout.tsx`는 Next.js 규칙상 `searchParams`를 못 받는다. 그래서
    `?done=`(DoneBanner)은 레이아웃이 아니라 두 페이지가 각자 그린다 —
    화면에서 위치가 헤더 바로 아래(예전엔 헤더보다 위)로 살짝 내려갔다.
    지금 이 배너를 실제로 채우는 액션이 없어(전부 `ActionForm`으로 바뀌며
    버튼 옆 문장으로 대체됨, §2 참고) 체감 영향은 없다.

### 1.2 화면을 오가는 링크

탭 대신 `ScreenSwitch`(`src/components/ScreenSwitch.tsx`) 컴포넌트를 새로
만들어 세 화면이 같이 쓴다 — 현재 화면은 채운 상자, 다른 화면은 테두리만 +
"→"로 표시한다(와이어프레임 mockup 그대로).

### 1.3 앵커가 화면을 넘어가는 자리

전에는 같은 페이지 안 해시(`#accidents-upload` 등)로 충분했다. 지금은 그
구역이 다른 URL에 있을 수 있어 전체 경로로 바꿨다 — 예:
`/accidents#accidents-upload`, `/analysis/${caseId}#analysis-results`.
Next.js의 `<Link>`는 다른 라우트로 이동한 뒤 그 해시로 스크롤까지 해 준다.

## 2. 2a — 처리중 표시가 빠진 제출 버튼 보완

와이어프레임의 감사 목록을 실제 코드로 다시 확인해 보니 몇 곳은 이미
`ActionForm`을 쓰고 있었다(키워드·용어 사전의 승인/반려 버튼 등) — 목록이
약간 낡아 있었다. 실제로 빠져 있던 자리만 고쳤다.

| 파일 | 무엇을 고쳤나 |
| --- | --- |
| `analysis/[caseId]/page.tsx` | 후보 조항 채택/반려, 원인 후보 찾기 |
| `analysis/[caseId]/layout.tsx` | 어린이제품 여부 4지선다 |
| `analysis/[caseId]/SecondOpinion.tsx` | 병행 점검 판정 버튼(3지선다) |
| `standards/review/page.tsx` | 조항 검수 반려(사유 select 포함) |
| `keywords/page.tsx` | 검색어 직접 넣기 |
| `terms/page.tsx` | 품목 직접 추가 |
| `accidents/actions.ts`, `accidents/page.tsx` | PDF 여러 건 올리기 |

### 2.1 `ActionForm`을 넓혔다, 새로 안 만들었다

기존 `ActionForm`은 버튼 하나 + 선택적 텍스트 입력 한 칸만 지원했다. 위 목록
중 여럿은 버튼이 여럿(어린이제품 4지선다, 병행 점검 3지선다)이거나 부가 입력이
여럿(반려 사유 select, 파일 입력, 검색어 사전의 품목/검색어 두 칸)이라 그대로는
못 썼다. 새 컴포넌트를 만드는 대신 `ActionForm`에 두 가지를 더했다.

- `children` — 버튼 앞에 끼워 넣을 부가 입력(select·file·text 등 아무거나).
- `buttons` — 값만 다른 버튼 여럿을 한 폼에 두는 모드. 눌린 버튼만 처리중
  문구로 바뀌고, 나머지는 비활성화만 된다(같은 폼의 다른 버튼을 또 못
  누르게).

기존 8곳(단일 버튼)은 손대지 않아도 그대로 동작한다 — 새 prop이 다 선택값.

### 2.2 예외 — 「원인 후보로 시험항목 찾기」

이 버튼은 서버 액션이 아니라 GET 폼 제출이다(고른 원인을 `?cause=`에 실어야
링크를 복사해도 같은 화면이 열린다). `ActionForm`은 서버 액션이 문장을
돌려주는 모양을 전제하므로 그대로 못 썼다. 대신 `CausePickerSubmit.tsx`
(작은 클라이언트 컴포넌트)를 만들어 `useTransition`으로 같은 효과(누르면
잠기고 "찾는 중…"으로 바뀜)를 냈다 — 주소는 그대로 GET 이동한다.

### 2.3 사고보고서 업로드 — 문장을 만들려면 세어야 했다

`uploadAccidentPdfs`는 원래 `Promise<void>`였다. 여러 PDF를 순서대로
처리하며 파일마다 결과가 다를 수 있어(올림·중복·개인정보 차단·스캔본·오류),
`ActionForm`이 요구하는 `Promise<string>`으로 바꾸면서 각 결과를 세어
"7건 중 올림 5건 · 이미 있어 건너뜀 1건 · 개인정보 발견으로 막힘 1건." 같은
요약 문장을 만들도록 고쳤다.

## 3. 3a — 좌우 메뉴 기본 숨김

좌측 업무흐름 레일(`layout.tsx`)과 우측 이 페이지 목차(`PageToc.tsx`)를 전부
기본 숨김 오버레이로 바꿨다. 둘 다 화면 크기와 무관하게 같은 규칙이다 —
아이콘(☰/≡)을 눌러야 열리고, 바깥을 누르거나 Esc 로 닫히고, 열림 상태를
저장하지 않는다(다시 들어오면 항상 접혀 있다).

- 좌측 레일의 실제 목록·토글 로직은 `src/components/SideNav.tsx`(신규,
  클라이언트 컴포넌트)로 옮겼다 — `layout.tsx`는 이제 그것만 부르는 얇은
  서버 컴포넌트다.
- 우측 목차는 기존 `PageToc.tsx`를 그대로 고쳤다(sticky 사이드바 +
  `<details>` 아코디언 → 오버레이 패널 하나).
- 두 오버레이 모두 사라지면서, 본문을 감싸던 `xl:grid-cols-[minmax(0,1fr)_10rem]`
  그리드(우측 목차 칸을 비워 두던 것)도 8개 화면(`accidents`, `recalls`,
  `analysis/[caseId]`, `standards`, `insights`, `codebook`, `llm`, `ops`)과
  `PageSkeleton.tsx`에서 걷어냈다 — 본문이 이제 전체 폭을 쓴다.
- `globals.css`의 `.page-toc*` 규칙(예전 레이아웃 전용)은 지웠다 — 지금은
  컴포넌트 안의 Tailwind 클래스가 전부 맡는다.

## 4. 손대지 않은 것

- `Tabs.tsx` 컴포넌트 자체는 지우지 않았다 — 이번에 쓰는 세 화면에서의
  import만 뺐다. 다른 곳에서 필요해지면 그대로 쓸 수 있다.
- 검색·판정 로직(`src/lib/search/*`, `src/lib/second-opinion/*`)은 그대로다.
  이번 개편은 배치·탐색·처리중 표시이지 판정 로직이 아니다.

## 5. 검증

- `npm run typecheck`, `npm run build` 통과(정적 페이지 5개 포함, 새 라우트
  `/accidents/status`·`/recalls/status`·`/analysis/[caseId]/insight` 정상
  등록 확인).
- `npm run lint`는 이 라운드 이전부터 로컬 환경에 `@eslint/eslintrc` 패키지가
  없어 실행 자체가 안 된다(`node_modules/@eslint` 없음) — 이번 변경과 무관한
  환경 문제이며 고치지 않았다.
- 실제 DB를 붙인 화면 클릭 확인은 아직 안 했다 — 다음에 열 때 사건 하나로
  검토→인사이트 전환, 사고보고서 올리기 처리중 표시, 좌우 메뉴 열고 닫기를
  직접 봐야 한다.
