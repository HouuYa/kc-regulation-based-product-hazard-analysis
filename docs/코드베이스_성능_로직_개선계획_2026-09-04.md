# 코드베이스·성능·로직 개선 계획

작성일: 2026-09-04  
범위: 안전기준·사고보고서·리콜 처리, 태깅·임베딩·검색, 자동 작업, 서버 액션  
원칙: 먼저 데이터 누락과 잘못된 판단을 막고, 그 다음 속도와 운영 편의성을 개선한다

## 0. 정확성 우선 MVP 재검토

00·01 문서의 핵심은 빠른 검색 자체가 아니라 **원문과 근거를 보존하고, 사람이 확인할 수 있는 시험 후보를 재현 가능하게 제시하는 것**이다. 따라서 MVP에서는 응답 속도를 조금 희생하더라도 다음 순서를 우선한다.

`원문 보존 → 파싱 품질 확인 → 태깅 근거 검수 → 품목·기준 범위 확정 → 후보 검색 → 시험방법 확인 → 담당자 판단 기록`

현재 구현은 조항 단위 파싱, HF/DT 태깅 구조, 하이브리드 검색, 시험방법 연결, 리랭킹 결과 보존까지 큰 뼈대는 문서와 일치한다. 다만 아래 항목은 문서의 원칙과 실제 동작 사이에 차이가 있어 MVP의 정확성 경계로 먼저 다뤄야 한다.

| 설계 약속 | 현재 구현 | 판단 |
|---|---|---|
| 검수 확정 태깅을 정식 근거로 사용 | 검색 SQL이 `rejected`가 아닌 태그를 모두 사용 | 자동 미검수 태그가 코드 근거처럼 결과에 영향을 줄 수 있음 |
| PDF 업로드 후 추출·코드화·임베딩 흐름 | 업로드 액션은 추출·사건 생성까지, 코드화는 별도 명령 | 화면 상태가 실제 처리 완료로 오해될 수 있음 |
| 원본은 불변·재현 가능 | 사고 PDF는 Storage 저장 실패 후에도 진행 가능, 기준 JSON은 해시·파일명 중심 | 원본과 파생 결과의 감사 추적이 끊길 수 있음 |
| 3번째 산출물은 판단 기록 축적 후 집계 | `review_log`·`match_result`는 있으나 개선 요인 집계·화면 없음 | 아직 구현 전 단계 |

정확성 우선 MVP의 완료 조건은 “모든 기능을 자동화”하는 것이 아니라, **분석 결과가 어떤 원문·태그·기준 범위·검색 설정에서 나왔는지 담당자가 되짚을 수 있는 상태**다.

## 1. 점검 결론

현재 구조는 안전기준 파싱, 사고보고서 처리, 태깅, 임베딩, 검색의 주요 흐름이 분리되어 있고, 명령줄과 화면이 공통 라이브러리를 사용하는 점은 좋다. 최근 추가한 자동 작업 구간 처리도 한 번에 너무 오래 실행되는 문제를 줄이는 방향이 맞다.

다만 다음 세 가지는 성능 개선보다 먼저 확인해야 한다.

1. 태깅 병렬 요청의 고정 오프셋 때문에 일부 조항이 건너뛰어질 가능성
2. 안전기준 동기화 API가 토큰 미설정 상태에서 열릴 가능성
3. 재태깅한 조항에 과거 코드와 현재 코드가 함께 남아 검색 점수와 검수 근거를 부풀릴 가능성

이 세 항목은 실제 검색 결과와 처리 완료 건수를 바꿀 수 있으므로, 구현 전에 데이터베이스에서 재현 여부를 확인한다.

추가로 확인한 두 가지도 별도 과제로 올린다.

4. 메인 화면이 여러 DB 집계와 목록 조회를 순차로 기다려 첫 화면 표시가 늦어질 가능성
5. 설계문서의 3번째 산출물인 `KC안전기준 개선 요인` 집계가 아직 구현되지 않은 상태

## 1.1 설계 대비 구현 현황

구현설계 v0.6과 컨셉 v0.4의 3번째 산출물은 다음 세 가지다.

| 설계 산출물 | 필요한 근거 | 현재 확인된 상태 |
|---|---|---|
| 기준 사각지대 목록 | 사고·리콜 HF/DT와 대응 조항 부재 | 건별 검색 결과와 `review_log`는 있으나 집계 화면·RPC 없음 |
| 국내외 기준 수준 차이 | 해외 리콜의 근거 표준과 국내 조항의 요구 수준 비교 | `cited_standards`·`matched_standard_ids`는 저장하지만 수준 비교 로직 없음 |
| 저활용 시험항목 목록 | 시험 후보 도출 빈도와 사고·리콜 연관성 비교 | `clause_link`, `match_result`, `review_log`는 있으나 집계 로직 없음 |

따라서 현재 시스템은 1·2번째 산출물인 `시험 후보군`과 `위해성 판별을 위한 건별 근거`까지 구현되어 있고, 3번째 산출물은 원자료가 일부 준비된 상태일 뿐 실제 산출물로 구현되지는 않았다. 단순히 `review_log` 건수를 보여 주는 것은 기준 개선 분석이 아니다.

## 2. 우선순위별 개선 항목

### P0. 분석에 사용할 수 있는 상태를 명시적으로 제한

**개선 방향**

- `is_confirmed = true`, 품목 확정, 적용 기준 확정, 원본 보관 완료를 분석 가능 조건으로 묶는다.
- 자동 태그는 `auto_unreviewed`로 표시하고, 정식 코드 근거 검색에는 승인 태그만 사용하거나 자동 태그 경로를 별도로 표시한다.
- `HF.UNKNOWN` 사건은 일반 코드 매칭 결과와 구분하고, “피해유형·어휘 기반의 넓은 후보”임을 결과에 고정 표시한다.
- 분석 가능 상태와 파싱 완료·코드화 완료·임베딩 완료를 서로 다른 상태로 관리한다.

**검증**

- 원문 미확인, 품목 미확정, 자동 태그만 존재, HF.UNKNOWN, 정상 승인 태그의 다섯 상태를 각각 넣고 분석 실행 가능 여부와 결과 표기가 분리되는지 확인한다.

### P0. 원문·파싱·시험 연결의 감사 추적성 보강

**개선 방향**

- 안전기준 JSON도 Storage 또는 원본 테이블에 보관하고 `source_sha256`와 1:1로 연결한다.
- PDF·JSON 원본 보관 실패는 분석 불가로 처리한다. 미리보기용 잘라낸 텍스트와 감사용 전체 원문을 구분한다.
- 조항·시험조건·시험방법 연결에 페이지·원문 위치·연결 근거를 남긴다.
- 같은 marker가 여러 `part`에 존재할 때 잘못 연결되지 않도록 `part`와 기준 ID를 필수 키로 삼는다.

**검증**

- 원본 저장 실패, 표 파싱 실패, 동일 marker 반복, 외부 기준 참조, 시험방법 미연결 사례를 각각 재현한다.
- 담당자가 조항 결과에서 원본 페이지와 연결 근거까지 역추적할 수 있는지 확인한다.

### P0. 태깅 검수 근거와 변경 이력 구현

**개선 방향**

- 하나의 `evidence_span`을 HF·DT 코드별 근거 배열로 확장하거나 코드별 태그 행에 근거를 분리 저장한다.
- 검수자, 검수 시각, 기존 코드, 새 코드, 수정 사유를 이력으로 남긴다.
- 코드북 버전·태깅 버전·프롬프트 버전을 검수 화면과 분석 매니페스트에서 함께 확인한다.
- 코드북에 없는 코드와 빈 근거는 저장 단계에서 차단한다.

**검증**

- 한 사건·조항에 복수 HF/DT 코드와 서로 다른 근거를 넣고 코드별 근거가 섞이지 않는지 확인한다.

### P1. 사고보고서 처리 상태와 자동화 경계 정리

**관찰**

- 설계문서는 PDF 업로드 후 L0 추출, L2 코드화, 임베딩까지의 흐름을 설명하지만 현재 업로드 액션과 코드화 명령은 분리돼 있다.

**개선 방향**

- MVP에서는 자동화하지 않아도 되지만, 화면에 `추출 완료`, `원문 확인 필요`, `코드화 완료`, `의미 검색 준비`, `분석 가능`을 분리해 표시한다.
- 자동 코드화를 연결할 때도 업로드 요청 안에서 기다리지 말고 작업 등록 후 상태를 폴링한다.
- 코드화 실패를 업로드 실패로 뭉뚱그리지 않고 파일·사건별로 재시도한다.

**검증**

- 정상 PDF, 개인정보 차단 PDF, 스캔본, 코드화 실패, 임베딩 대기 상태가 화면에서 서로 구분되는지 확인한다.

### P1. 리랭킹 provenance 매니페스트 저장

**개선 방향**

- 분석 실행마다 질의 원문, 사건 코드, 적용 기준 ID, 검색 스위치·가중치, 후보 ID 전체, 모델·프롬프트 버전을 저장한다.
- 리랭커가 낮은 점수를 준 후보와 응답에서 빠진 후보를 구분한다.
- 리랭킹 실패 결과는 성공 결과처럼 저장하지 않고 `rerank_failed` 상태로 표시한다.

**검증**

- 같은 분석을 다시 열었을 때 저장된 결과가 유지되는지, 후보 누락이 기록되는지 확인한다.

### P0. 메인 화면 초기 로딩 지연 측정과 분리

**관찰**

- `src/app/accidents/page.tsx`, `src/app/recalls/page.tsx`, `src/app/ops/page.tsx`는 요약 집계, 전체 건수, 목록, 보조 상태를 여러 쿼리로 순차 조회한다.
- `src/app/**/loading.tsx`가 없어 서버 조회가 끝날 때까지 페이지의 유용한 화면이 먼저 표시되지 않는다.
- 사고·리콜 목록은 페이지 단위지만, 목록 행마다 태그·분석·임베딩 상태를 확인하는 상관 서브쿼리가 있어 페이지당 DB 작업량이 커질 수 있다.
- 자동 새로고침은 진행 중인 화면 전체를 다시 요청하므로, 조회 조건과 목록 위치를 유지하더라도 서버의 전체 조회 비용은 반복된다.

**개선 방향**

1. 먼저 페이지별 TTFB, 각 쿼리 소요시간, 반환 행 수를 측정한다.
2. `loading.tsx` 또는 페이지 내부 Suspense 경계로 제목·업무 흐름·기본 골격을 먼저 표시한다.
3. 요약 숫자와 목록을 별도 서버 컴포넌트로 나눠 느린 영역이 전체 화면을 막지 않게 한다.
4. 목록 행의 반복 서브쿼리는 집계 CTE·뷰·인덱스 중 측정 결과에 맞는 하나로 정리한다.
5. 자동 새로고침은 전체 페이지 대신 상태 숫자와 진행률만 갱신하는 작은 경로를 검토한다.

**검증**

- 개요·사고보고서·리콜·운영 화면에서 첫 바이트, 제목 표시, 목록 표시 시점을 각각 측정한다.
- 데이터가 느린 경우에도 업무 흐름과 “불러오는 중” 상태가 먼저 보이는지 확인한다.
- 10·100·1,000·10,000건 규모의 샘플에서 목록 쿼리 실행시간과 DB 호출 횟수를 비교한다.
- 검색 조건·페이지·펼친 원문이 자동 새로고침 뒤 유지되는지 확인한다.

### P0. 3번째 산출물: KC안전기준 개선 요인 도출 구현

**목표**

건별 분석 결과를 바로 정책 결론으로 만들지 않고, 담당자의 검토 기록을 모아 “추가 검토가 필요한 신호”를 만드는 집계 기능을 구현한다. 시스템은 기준 강화·완화나 법적 판단을 자동 확정하지 않는다.

**구현 범위**

1. **기준 사각지대**
	- 사고·리콜의 HF/DT 코드와 적용 품목을 기준으로 그룹화한다.
	- 대응 후보 조항이 없거나, 후보는 있으나 담당자가 모두 반려한 경우를 구분한다.
	- 코드 미부여·품목 미확정·검색 준비 미완료를 “사각지대”와 섞지 않는다.
	- 최소 출력: 품목, HF/DT, 사건 수, 대응 조항 수, 채택·반려 수, 데이터 준비 상태.

2. **국내외 기준 수준 차이**
	- 해외 리콜의 `cited_standards`가 실제로 확보된 건만 대상으로 한다.
	- 해외 표준 번호와 국내 기준 번호가 직접 대응하는 경우와, 번호 체계가 달라 비교할 수 없는 경우를 구분한다.
	- 허용치·시험조건·시험방법이 구조화된 비교 가능한 경우만 차이 후보로 올린다.
	- 문장만 보고 “국내 기준이 낮다/높다”고 추정하지 않으며, 비교 불가 사유를 함께 저장한다.

3. **저활용 시험항목**
	- 시험방법 조항별로 후보로 제시된 횟수, 채택 횟수, 반려 사유, 연결된 사고·리콜 수를 집계한다.
	- “채택이 적다”와 “사고·리콜이 없다”를 같은 뜻으로 보지 않는다.
	- 표본 수, 자료 기간, 국내외 자료 범위, 미분석 사건 수를 함께 표시한다.
	- 완화 대상이 아니라 전문가가 다시 검토할 후보 목록으로만 제공한다.

**필요한 데이터 구조**

- `insight_run`: 집계 실행 시점, 대상 기간, 코드북 버전, 기준 버전, 검색 설정
- `standard_gap_insight`: 사각지대 그룹, 근거 사건 수, 대응 조항 수, 검토 상태
- `standard_level_comparison`: 해외 표준, 국내 조항, 비교 가능 여부, 비교 근거, 검토 상태
- `test_usage_insight`: 시험방법 조항, 후보·채택·반려 횟수, 사건 수, 표본 범위
- 원자료인 `match_result`, `review_log`, `case_tag`, `clause_tag`, `clause_link`는 삭제하거나 덮어쓰지 않는다.

**화면과 API**

- 운영 화면과 분리된 `/insights` 페이지를 만든다.
- `기준 사각지대`, `국내외 비교`, `시험항목 사용 현황` 세 탭으로 나눈다.
- 각 행에 근거 사건·조항·검토기록으로 내려가는 링크를 둔다.
- 데이터 부족, 비교 불가, 담당자 미검토를 정상 결과와 구분해 표시한다.
- 최초에는 자동 보고서 문장을 만들지 않고 표와 근거 목록을 제공한다.

**검증**

- 의도적으로 대응 조항이 없는 사건, 후보가 있으나 모두 반려된 사건, 아직 검토하지 않은 사건을 각각 만든다.
- 세 경우가 사각지대·오탐 가능성·검토 대기로 분리되는지 확인한다.
- 해외 표준 번호가 대응하는 사례와 대응하지 않는 사례를 비교한다.
- 시험방법 채택·반려 기록이 있는 표본에서 집계 수치가 원자료 합계와 일치하는지 확인한다.
- 표본이 부족한 경우 “분석 불충분”으로 표시되고 강화·완화 결론을 내리지 않는지 확인한다.

### P0. 3번째 산출물의 구현 대안 비교

3번째 산출물은 단순 통계 화면이 아니라, 사고·리콜의 발생 정보와 담당자의 시험 후보 판단을 연결해 **기준 개선을 검토할 근거**를 만드는 기능이다. 정확성을 우선하는 MVP에서는 아래 세 가지 안을 비교한 뒤, 1안으로 시작하고 2안·3안을 단계적으로 붙이는 방식을 권고한다.

#### 안 1. 기존 원자료를 바로 집계하는 읽기 전용 방식

**구조**

```text
case_tag + case_event
		  ↓
match_run + match_result
		  ↓
review_log
		  ↓
SQL VIEW / RPC
		  ↓
/insights 화면
```

**내용**

- 현재 저장된 `case_tag`, `match_result`, `review_log`, `clause_link`를 그대로 조회한다.
- 기준 사각지대는 “사건은 있으나 채택된 대응 조항이 없는 경우”부터 산출한다.
- 저활용 시험항목은 시험방법 조항으로 연결된 후보의 제시·채택·반려 횟수를 집계한다.
- 국내외 기준 차이는 `recall_cache.cited_standards`가 있는 리콜만 별도 목록으로 뽑고, 수준 비교는 “비교 자료 확인 필요” 상태로 둔다.

**장점**

- 새 테이블과 대량 백필이 거의 필요 없다.
- 현재 데이터로 바로 검증할 수 있다.
- 원자료가 바뀌면 최신 집계가 즉시 반영된다.

**단점**

- 집계 시점에 따라 결과가 달라진다.
- 당시의 검색 설정·코드북·기준 판을 함께 고정하지 않으면 과거 결과를 동일하게 재현하기 어렵다.
- “왜 이 항목이 개선 후보가 되었는가”를 한 번에 설명하려면 여러 테이블을 다시 조인해야 한다.

**적합한 용도**

- 정확한 정책 결론 전의 탐색 화면
- MVP에서 데이터가 충분히 쌓였는지 확인하는 1차 구현

#### 안 2. 집계 실행마다 결과 스냅샷을 저장하는 방식

**구조**

```text
원자료 조회 + 기준/코드북 버전 고정
				  ↓
			insight_run 생성
				  ↓
	  세 가지 집계 결과 계산
				  ↓
 insight_* 스냅샷 테이블 저장
				  ↓
		 담당자 검토·비교
```

**내용**

- 담당자가 기간·품목·출처·기준 판을 선택해 집계를 실행한다.
- `insight_run`에 실행 시각, 대상 기간, 기준 판, 코드북 버전, 검색 설정, 집계 규칙 버전을 저장한다.
- `standard_gap_insight`, `standard_level_comparison`, `test_usage_insight`에 집계 당시의 수치와 근거 ID 목록을 저장한다.
- 화면은 실시간 원자료가 아니라 선택한 스냅샷을 보여 준다.

**장점**

- 보고 시점의 수치와 근거를 고정할 수 있다.
- 나중에 집계 규칙을 바꿔도 과거 결과와 비교할 수 있다.
- 담당자가 “검토 중”, “검토 완료”, “보류” 상태를 붙일 수 있다.

**단점**

- 새 테이블과 집계 실행 작업이 필요하다.
- 원자료가 수정되면 스냅샷과 현재 상태가 달라질 수 있으므로 차이를 표시해야 한다.

**적합한 용도**

- 정확성·감사성이 중요한 정식 MVP
- 기준 개정 검토 회의 자료로 재사용할 결과

#### 안 3. 개선 후보를 별도 검토 사건으로 승격하는 방식

**구조**

```text
사각지대·기준 차이·저활용 신호
				  ↓
		  개선 후보 등록
				  ↓
  담당 부서 검토·보류·채택·반려
				  ↓
		 조치·근거·후속 결과 기록
```

**내용**

- 집계 결과를 단순 목록으로 끝내지 않고 `improvement_candidate`로 등록한다.
- 후보마다 유형, 대상 품목, HF/DT, 관련 기준·시험방법, 근거 사건, 제안 사유, 검토 상태를 저장한다.
- 검토자는 “자료 부족”, “이미 다른 기준에서 처리”, “추가 시험 필요”, “기준 개정 검토 착수” 등의 상태를 기록한다.
- 채택·반려는 기준을 자동 변경하지 않고, 외부 기준 개정 절차의 시작 여부만 기록한다.

**장점**

- 컨셉 문서의 “정책 환류” 목적과 가장 잘 맞는다.
- 집계 결과와 실제 담당 부서의 후속 판단을 분리해 추적할 수 있다.
- 장기적으로 기준 개선 후보가 어떻게 처리됐는지 평가할 수 있다.

**단점**

- 담당 부서와 검토 절차를 먼저 합의해야 한다.
- 업무 상태·권한·알림·이력까지 필요해 MVP 범위가 커진다.
- 자동 생성 후보가 많으면 검토 부담이 생긴다.

**적합한 용도**

- 3단계 정식 운영
- 기준 개정 담당 부서와 업무 연계가 확정된 뒤

#### 권고안: 안 1 → 안 2 → 안 3의 단계적 적용

| 단계 | 구현 범위 | 목적 |
|---|---|---|
| MVP-1 | 안 1의 읽기 전용 SQL/RPC와 `/insights` 화면 | 집계 정의가 실제 데이터에서 성립하는지 검증 |
| MVP-2 | 안 2의 `insight_run` 및 세 스냅샷 테이블 | 수치·근거·버전을 고정해 재현성과 회의 활용성 확보 |
| 정식 3단계 | 안 3의 개선 후보 검토·후속 이력 | 정책 환류와 기준 개정 검토 절차 연결 |

처음부터 안 3으로 가면 “집계 기준이 맞는가”와 “업무 절차가 맞는가”를 한 번에 검증하게 된다. 따라서 먼저 안 1로 원자료와 수작업 계산을 대조하고, 수치가 안정된 뒤 안 2로 고정하며, 실제 담당 부서의 처리 절차가 정해졌을 때 안 3을 추가한다.

### P0. 3번째 산출물의 공통 집계 규칙

세 구현안 모두 다음 규칙을 공유한다.

- **분석 대상 범위**: 원문 확인 완료, 품목·적용 기준 확정, 분석 실행 완료 자료를 기본 대상으로 한다.
- **검토 상태**: 자동 태그와 미검토 후보는 별도 표시하고, 기준 개선 근거의 주 집계는 담당자가 검토한 기록과 분리한다.
- **기간 기준**: 사고 발생일·리콜 발표일·분석 실행일·검토일을 구분해 선택한다.
- **품목 기준**: `product_scope_id`가 같은 자료를 우선 묶고, 품목 미확정 자료는 별도 보류 그룹으로 둔다.
- **코드 기준**: HF와 DT를 분리 집계하며, `HF.UNKNOWN`은 별도 그룹으로 표시한다.
- **기준 판 기준**: 현재 기준만 기본 집계하고 과거 기준은 선택했을 때만 포함한다.
- **0건의 의미**: 실제 대응 조항 없음, 태깅 미완료, 품목 미확정, 시험 연결 누락, 분석 미실행을 서로 다른 상태로 구분한다.
- **표본 부족**: 사건 수·리콜 수·검토 완료 수가 최소 기준보다 작으면 개선 후보가 아니라 `자료 부족`으로 표시한다.

### P0. 3번째 산출물의 단계별 세부 개발 순서

1. **원자료 품질 점검**
	- 사건별 원문 확인·품목 확정·HF/DT 코드·분석 실행·검토 기록의 상태를 점검한다.
	- `review_log`의 최신 판단과 중복 판단 처리 규칙을 확정한다.
	- `MODIFIED` 판단의 수정 대상과 사유를 저장할지 결정한다.

2. **기준 사각지대 집계**
	- 대응 조항 0건과 후보 전부 반려를 구분한다.
	- 분석 미실행·태깅 미완료·품목 미확정 자료를 별도 제외 사유로 집계한다.
	- HF/DT·품목·기간별 근거 사건 목록을 함께 반환한다.

3. **저활용 시험항목 집계**
	- 성능요건 조항과 시험방법 조항의 연결을 따라 시험방법 단위로 집계한다.
	- 후보 제시, 담당자 채택, 반려, 미검토를 각각 센다.
	- 연결된 사건이 없다는 사실과 분석 대상이 적었다는 사실을 구분한다.

4. **국내외 기준 비교 집계**
	- 해외 표준명이 실제로 기록된 리콜만 대상으로 한다.
	- 표준 번호 직접 대응, 수작업 매핑 필요, 비교 불가를 구분한다.
	- 허용치·시험조건이 구조화되지 않은 비교는 자동 우열 판정하지 않는다.

5. **근거 화면과 스냅샷**
	- 각 집계 행에서 사건·리콜·조항·시험방법·검토기록으로 이동한다.
	- 집계 실행 조건과 버전을 고정한다.
	- 담당자가 검토 상태와 메모를 남길 수 있게 한다.

6. **정확도 검증과 운영 전환**
	- 표본을 손으로 계산한 결과와 SQL 결과를 비교한다.
	- 표본 부족·중복 판단·과거 기준 혼입·미검토 태그 포함 여부를 점검한다.
	- 결과가 안정된 뒤에만 기준 개정 검토 후보 등록과 알림을 연다.

### P0. 3번째 산출물의 완료 기준

- 세 산출물 각각에 대해 집계 정의, 대상 범위, 제외 사유가 문서화되어 있다.
- 각 숫자에서 원자료 사건·리콜·조항·검토기록으로 역추적할 수 있다.
- 집계 당시의 기준 판·코드북 버전·검색 설정을 확인할 수 있다.
- 자동 미검수 태그와 담당자 검토 결과가 섞이지 않는다.
- “기준 강화”, “기준 완화”, “법적 의무 발생”을 자동 확정하지 않는다.
- 표본 부족과 비교 불가 자료가 정상 결과처럼 표시되지 않는다.

### P0. 태깅 작업 예약 방식 수정

**관찰**

- `supabase/migrations/027_tag_chunk_parallel.sql`은 `offset=0/40/80`으로 세 요청을 나눈다.
- `src/lib/standards/tag-run.ts`는 처리할 때마다 아직 태그가 없는 조항만 다시 조회한다.
- 앞 요청이 조항을 처리하면 다음 실행에서 목록의 위치가 당겨지므로 고정 오프셋이 이미 처리된 행을 건너뛸 수 있다.

**개선 방향**

- 가장 안전한 방법은 DB에서 작업 대상을 먼저 예약하는 방식이다.
- `tagging_job` 또는 기존 작업 장부에 조항 ID를 예약하고, `FOR UPDATE SKIP LOCKED`로 다른 요청과 겹치지 않게 한다.
- 예약 장부를 새로 만들지 않는다면 고정 오프셋 대신 `clause.id > last_id` 커서를 사용하되, 처리 실패 시 재시도할 수 있는 상태를 함께 남긴다.
- `남은 조항 0건` 알림은 조회 잔량과 예약·실패 잔량을 모두 확인한 뒤 보낸다.

**검증**

- 미태깅 조항 120건을 준비하고 병렬 요청을 반복 실행한다.
- 실제 태깅된 ID와 최초 대상 ID를 비교해 누락·중복이 0건인지 확인한다.
- 일부 요청을 강제 실패시킨 뒤 실패 대상만 다시 처리되는지 확인한다.

### P0. 자동 동기화 API 잠금

**관찰**

- `src/app/api/standards/sync/route.ts`는 `STANDARDS_SYNC_TOKEN`이 없으면 인증을 통과시킨다.
- 배포 환경변수 누락은 설정 실수로도 발생할 수 있으므로, 안전기준 전체 동기화라는 쓰기 작업이 공개될 수 있다.
- 자동 작업은 이미 `JOBS_TOKEN`을 별도로 사용한다.

**개선 방향**

- 운영 환경에서는 `STANDARDS_SYNC_TOKEN`이 없으면 500으로 중단하고, 인증 없는 실행을 허용하지 않는다.
- 실제 자동 호출은 `/api/jobs/standards-sync` 하나로 통합하고, 수동 라우트는 제거하거나 같은 인증 정책을 적용한다.
- 허용할 토큰을 하나로 통합할지 별도로 둘지는 운영 편의성과 권한 분리를 비교해 결정한다.

**검증**

- 토큰 미설정, 잘못된 토큰, 올바른 토큰 세 경우에 각각 500 또는 401, 200이 나오는지 확인한다.
- 배포 환경에서 인증 없이 POST 요청을 보내도 파일 적재가 시작되지 않는지 확인한다.

### P0. 검색에 쓰는 태그의 최신성 보장

**관찰**

- `src/lib/standards/tag-run.ts`의 재태깅은 검수 확정 태그를 보존하고 새 `tagging_version` 태그를 추가한다.
- `007_clause_hybrid_search.sql`의 코드 매칭은 반려되지 않은 태그를 모두 읽는다.
- 같은 조항에 과거 태그와 새 태그가 같이 있으면 코드 일치 횟수와 검수 여부가 과대 계산될 수 있다.

**개선 방향**

- 조항별로 현재 검색에 사용할 태깅 버전을 하나로 정한다.
- 검수 확정 태그는 보존하되, 검색 함수는 현재 활성 버전의 태그만 사용한다.
- 이전 버전은 감사·비교용으로만 남기고, 현재 검색 경로와 분리한다.
- 기존 중복 태그를 바로 삭제하지 말고 먼저 조항별 버전 분포와 검색 결과 차이를 측정한다.

**검증**

- 한 조항에 서로 다른 버전의 HF·DT 태그를 넣고 `hit_full`, `hit_partial`, 검수 근거가 한 세트만 반영되는지 확인한다.
- 기존 검색 결과와 새 검색 결과의 순위 변화 및 후보 누락을 비교한다.

### P1. 리콜 적재의 건별 일관성 확보

**관찰**

- `src/lib/recall/load.ts`는 캐시 저장, 사건 생성, 품목 확정, 태그 저장을 여러 DB 호출로 나눠 수행한다.
- 중간 오류가 나면 캐시만 있거나 사건은 있지만 검색용 문장·태그가 없는 상태가 남을 수 있다.
- `case_event`는 이미 존재하면 일부 파생 필드를 갱신하지 않는다.

**개선 방향**

- 리콜 한 건의 캐시·사건·품목·태그·검색용 문장 갱신을 한 트랜잭션으로 묶는다.
- 원본 변경 시 사건의 제목·서술·원본 필드도 갱신하되, 담당자 검토 기록은 보존한다.
- 트랜잭션 실패는 해당 리콜의 ID와 단계만 오류 목록에 남기고 다음 리콜은 계속 처리한다.

**검증**

- 각 단계 직전에 강제 오류를 넣어 고아 캐시·불완전 사건이 남지 않는지 확인한다.
- 원본 리콜의 제목·위해 설명을 수정한 뒤 재수집해 파생 필드가 갱신되는지 확인한다.
- 재실행 후 `external_ref` 중복과 태그 중복이 없는지 확인한다.

### P1. 리콜 수집을 증분 처리로 전환

**관찰**

- `fetchApprovedRecalls()`는 `select('*')`로 승인 자료를 페이지 단위로 읽고, `loadRecalls()`는 각 건을 순차 처리한다.
- 현재 10건 배치는 타임아웃을 줄이지만, 전체 순환이 길어 새 리콜 반영이 늦어질 수 있다.

**개선 방향**

- 전체 오프셋 순환보다 `id` 또는 `updated_at` 커서 기반으로 새 자료와 변경 자료를 먼저 처리한다.
- 필요한 컬럼을 명시하고, 원본 전체는 `raw`에 저장할 때만 받는다.
- 동일한 crosswalk 결과와 품목 범위 조회는 캐시하거나 배치로 묶는다.
- 최근 자료 우선 처리와 과거 자료 재확인을 별도 작업으로 나눈다.

**검증**

- 10·100·1,000건에서 외부 조회량, DB 호출 횟수, 평균·최대 처리시간을 측정한다.
- 새 자료 1건이 다음 주기 안에 반영되는지 확인한다.
- 변경·삭제·승인 상태 전환 자료의 처리 규칙을 별도로 확인한다.

### P1. 입력값과 환경설정 범위 검증

**관찰**

- `src/lib/env.ts`의 숫자 환경설정은 음수·과대값을 그대로 허용한다.
- 작업 URL의 `limit`, `offset`도 정수·최대값 검증이 없다.

**개선 방향**

- 동시성, 반복 횟수, 시간 예산, RRF 값에 최소·최대값을 둔다.
- `limit`과 `offset`은 정수·비음수로 제한하고, 요청당 최대 처리량을 둔다.
- 잘못된 값은 조용히 기본값으로 바꾸지 말고 운영 로그와 응답에 명확히 남긴다.

**검증**

- `limit=-1`, `offset=-1`, 소수, `NaN`, 과대값과 `TAGGING_CONCURRENCY=1000`을 각각 시험한다.
- 정상 범위 값은 기존 처리 결과와 동일한지 확인한다.

### P1. 안전기준 화면 집계 기준 통일

**관찰**

- 안전기준 목록은 `is_current`인 기준만 보여 주지만, 일부 상단 집계는 과거 기준의 조항·태그·시험 연결까지 포함할 수 있다.
- 개정판이 추가되면 화면 숫자와 목록 합계가 달라질 수 있다.

**개선 방향**

- 상단 집계와 행별 집계 모두 현재 기준 조인 조건을 사용한다.
- 조항·태그·임베딩·시험 연결·허용치의 분모 정의를 한 쿼리 또는 공통 뷰로 통일한다.

**검증**

- 같은 표시명의 개정판을 추가한 테스트 데이터에서 상단 숫자와 현재 목록 합계를 비교한다.

### P2. 임베딩 모델·차원 계약 단일화

**관찰**

- 코드와 SQL에 임베딩 차원 `1536`이 각각 존재하면서 환경변수로도 변경할 수 있다.
- 환경변수만 바꾸면 CLI, 자동 작업, DB 타입이 서로 달라질 수 있다.

**개선 방향**

- 당분간 차원 1536을 단일 상수로 고정하고 환경변수 변경을 막는다.
- 모델·차원·검색문 변형을 하나의 버전 정보로 기록한다.
- 차원을 바꾸는 경우에는 새 컬럼·새 인덱스·전체 재생성을 포함하는 별도 마이그레이션으로만 허용한다.

**검증**

- 잘못된 차원 설정이 시작 단계에서 즉시 실패하는지 확인한다.
- CLI와 자동 임베딩의 모델·차원 기록이 일치하는지 확인한다.

### P2. 서버 전용 경계와 서버 액션 입력 강화

**개선 방향**

- `src/lib/recall/source.ts`에 서버 전용 import 경계를 추가하고, 외부 Supabase 키가 브라우저 번들에 들어가지 않는지 빌드 산출물을 검사한다.
- 운영 작업명은 허용 목록으로 제한하고, 사건·결과·리뷰 ID는 양의 정수와 대상 존재 여부를 서버에서 확인한다.
- 실패 응답에 접속 정보나 외부 API 비밀값이 포함되지 않는지 회귀 테스트를 둔다.

## 3. 단계별 실행 순서

### 1단계: 정합성과 접근 통제

- 태깅 오프셋 누락 여부 SQL 검증
- 자동 동기화 API 인증 정책 확정 및 테스트
- 태그 버전 중복이 검색에 미치는 영향 측정
- 안전기준 집계의 현재 판 조건 통일
- 3번째 산출물의 원자료 연결과 집계 정의 확정

완료 기준: 처리 대상 누락 0건, 인증 없는 쓰기 요청 차단, 검색 점수 중복 반영 원인 확인, 3개 개선 신호의 산출 가능 여부 확인

### 2단계: 실패 복구와 처리량

- 메인 화면 로딩 병목 측정 및 Suspense/쿼리 최적화
- 태깅 예약 또는 커서 방식 구현
- 리콜 건별 트랜잭션 구현
- 리콜 증분 수집과 최근 자료 우선 처리 구현
- 실패 구간 재시도와 중복 방지 검증

완료 기준: 첫 화면 표시 지연 개선 수치 확보, 중간 실패 후 고아 데이터 0건, 새 리콜 반영 지연 측정값 확보, 배치별 최대 실행시간 제한 준수

### 3단계: 계약·관측성·유지보수

- 환경설정 범위 검증
- 임베딩 모델·차원 계약 단일화
- 서버 전용 import와 서버 액션 입력 검증
- 작업별 처리 건수·실패 건수·재시도 횟수·소요시간 기록 확대

완료 기준: 잘못된 설정이 시작 단계에서 발견되고, 운영 화면에서 실패 원인과 남은 작업을 구분해 확인 가능

## 4. 공통 검증 명령과 운영 확인

코드 변경마다 다음 순서로 확인한다.

```powershell
$env:NODE_OPTIONS=''
npm run typecheck
$env:NODE_OPTIONS=''
npx next build
git diff --check
```

데이터 변경은 별도 테스트 DB 또는 되돌릴 수 있는 샘플 행으로 먼저 검증한다. 운영 DB에 적용하기 전에는 다음을 확인한다.

- 태깅 대상·완료·실패·예약 건수의 합이 맞는지
- 현재 기준과 과거 기준의 집계가 섞이지 않는지
- 리콜 `external_ref` 중복이 없는지
- 임베딩 모델과 차원이 기존 자료와 일치하는지
- 자동 작업의 1회 실행시간과 최근 실패 응답
