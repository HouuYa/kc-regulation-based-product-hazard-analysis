## 이 문서를 쓰는 방법

- frontmatter 버전과 updated 날짜를 업데이트
- 코드를 크게 바꾸는 작업 한 라운드가 끝나면, 위쪽에 새 항목을 추가한다.
- 라운드에 종료 시간과 날짜를 작성한다.(즉 이 문서 업데이트)
- "무엇을 했는지"보다 "왜 했는지, 뭘 확인했는지"를 더 자세히 쓴다.
  (무엇을 했는지는 git 커밋 메시지를 보면 되지만, 왜 했는지는 그때 가서야 알 수 있다.)
- 전문용어가 나오면 괄호로 짧게 풀어 쓴다. 이 문서는 코드를 안 보는 사람도 읽을 수 있어야 한다.
	- 블릿 활용 및 개조식 명사형 종결(~분류하였다 -> 분류)하고 마지막은 `.`없이 문장 종료
	- 다만, 설명은 문장형태로 쉽게 풀어 쓴다.

## 라운드 2 — 데이터베이스(Supabase) 만들고 실제로 돌려 보기

**한 일**
- Supabase에 새 프로젝트(`kc-hazard-analysis`)를 만들었다.
- 설계에 필요한 표(테이블) 18개와 검색 함수들을 실제로 만들었다.
- 한국어 검색이 되는지 실측했다. PostgreSQL 기본 검색 기능은 "전도가", "전도를"처럼 조사가 붙으면 다른 단어로 착각한다 — 이게 진짜 문제인지 실제로 테스트해 봤더니 정말 그랬다. 그래서 한국어를 제대로 검색하는 별도 기능(PGroonga)을 설치했고, 이번엔 조사가 붙어도 잘 찾는 것을 확인했다.
- 가짜 사고 1건을 넣고 실제로 검색을 돌려 봤다. "의자가 옆으로 넘어져 아이가 떨어졌다"는 사고를 코드화(설계결함 + 낙상)한 뒤 검색했더니,
  정확히 그 원인·결과 코드가 붙어 있던 조항("4.3.3 안정성")을 찾아냈고, 그 조항이 가리키는 시험방법("5.9.2")까지 자동으로 이어졌다. 설계문서에
  적혀 있던 예시가 실제로 작동한 것을 확인한 셈이다.

**발견해서 고친 문제**
- Supabase는 새로 만든 함수를 기본적으로 "누구나 실행 가능"하게 열어 둔다는 사실을 발견했다. 데이터를 볼 수 있는 건 아니지만, 굳이 열어 둘 이유가 없어서 전부 잠그고 서버만 쓸 수 있게 고쳤다.

## 라운드 4 — 실제 데이터 채우기 · 신규 자료 감지 기능 · 정리

**한 일**

1. **환경설정 값 채움** — 승호님이 새로 발급받은 Supabase 접속 정보와 국내·해외 리콜 API 주소를 `.env.local`에 반영했다.

2. **깃(git) 이력 정리** — 이 작업들을 하는 동안, 원격 저장소(GitHub)에 다른 경로로 커밋 3개가 먼저 올라와 있어서 로컬 작업과 갈라져 있었다.
   서로 다른 파일을 건드린 커밋들이라 충돌 없이 합쳤다. 

3. **실제 데이터 적재** — 지금까지는 프로그램이 "이론적으로 맞다"는 것만 확인했는데, 이번에 처음으로 실제 데이터를 전부 넣어 봤다.
   - 위해요인 코드북 1건 (HF 64개, DT 16개)
   - 안전기준 76개 문서 전체, 조항 13,501개, 시험조건 333개,
     "이 조항은 이 시험과 연결된다"는 관계 644개
   - 넣은 뒤 개수를 다시 세어 봤더니 프로그램이 미리 계산했던 숫자와 한 자리도 틀리지 않고 똑같았다.

4. **새 자료가 들어왔을 때 자동으로 알아채는 기능** — 협회가 나중에
   기준을 개정해서 새 JSON 파일을 주면, 그게 "완전히 새로운 기준"인지  "이미 있는 기준의 개정판"인지 자동으로 구분하는 기능을 만들었다.
   - 완전히 같은 내용이면 → 아무 것도 안 함
   - 이름은 같은데 내용이 바뀌었으면 → 옛날 버전은 지우지 않고 "지금은 안 씀"으로 표시만 하고, 새 버전을 새로 넣는다. (옛 버전에 달려 있던 사람의 판단 기록은 절대 사라지면 안 되기 때문에 지우지 않는다.)
   - 완전히 새로운 이름이면 → 새로 넣는다.
   - 나중에 이 기능을 웹 주소(API)로도 호출할 수 있게 만들어 뒀다.
     지금 당장 누가 자동으로 호출하는 건 아니지만, 나중에 "자동 감시" 기능을 붙일 때 바로 쓸 수 있도록 미리 만들어 둔 것이다.

4. **사고조사보고서 5건 처리** — `사고조사보고서` 폴더에 있는 실제 PDF 5건(보조배터리 2건, LED등기구, 스팀다리미, 가습기)을 한 번에 처리하는 기능을 만들어 돌렸다.
   - **처리 중 실제 문제를 하나 발견했다.** 개인정보 탐지 기능이 "계좌번호"로 착각한 게 있었는데, 확인해 보니 진짜 계좌번호가
     아니라 보고서에 적힌 접수일자("25-11-24" 같은 형식)였다. 날짜와 계좌번호가 둘 다 숫자에 하이픈이 섞인 모양이라 헷갈린 것이다.
     실제 계좌번호는 자릿수가 훨씬 많다는 점을 이용해서 구분하도록 고쳤다. 고친 뒤에는 날짜는 더 이상 걸리지 않으면서, 진짜
     계좌번호처럼 생긴 것은 여전히 잡아내는 것을 확인했다.
   - 5건 모두 정상 처리됐다. (다만 이 상태로는 "등록"만 된 것이고, 담당자가 화면에서 원문을 확인하고 "확정" 버튼을 눌러야 실제 분석 대상이 된다 — 이것도 의도한 설계다. 사람이 확인하기 전에는 시스템이 멋대로 넘어가지 않는다.)

## 라운드 5 — AI 코드화 실제 가동 · 품목 확정 · 해외 리콜 연결

**한 일 (크게 넷)**

#### **① AI에게 코드를 붙이게 하되, 두 번 물어보게 했다**

앞 라운드까지는 "AI로 코드를 붙인다"고 만들어만 두고 실제로는 못 돌렸다. 
API 키가 채워져서 이번에 처음 돌렸다.

그냥 돌리지 않고 방식을 하나 정했다. **싼 모델에게 세 번 물어보고, 세 번 답이 갈리면 그때만 비싼 모델에게 다시 묻는다.**

왜 이렇게 했는가. 값을 재 봤더니 싼 모델(Luna) 세 번이 비싼 모델(Terra) 한 번보다 **3.3배 싸다.** 그런데 세 번 물어서 답이 같으면 그 답은 믿을 만하다. 답이 갈리는 건은 원래도 어려운 건이니 비싼 모델로 올린다.

여기서 한 가지를 일부러 피했다. AI에게 "네 답이 얼마나 확실하냐"고 물어 그 숫자로 판단하는 방법이 있는데, **설계문서가 그 숫자를 믿지 말라고 명시** 했다(§5.2.3). 실제로 틀린 답에도 0.9를 매긴다. 대신 **같은 질문을 세 번 해서 답이 얼마나 일치했는지**를 기준으로 삼았다. 이건 AI의 자기 평가가 아니라 관측된 사실이다.

돌려 본 결과 — 안전기준 조항 53개 중 **16개(30%)가 비싼 모델로 올라갔고, 그중 10개는 비싼 모델이 다른 답을 냈다.** 이 10개가 사람이 제일 먼저 봐야 할 목록이다.

> 정직하게 덧붙인다. 비싼 모델이 답을 **바꿨다**는 것과 **맞혔다**는 것은 다르다. 
> 어느 쪽이 옳은지는 전문가가 만든 정답지가 있어야 알 수 있고, 그건 아직 없다. 지금은 "여기가 흔들리는 구간"까지만 말할 수 있다.

#### **② 사고 사건을 실제 흐름에 연결했다 — 품목부터 정한다**

사고보고서를 넣으면 이제 이 순서로 처리된다.

```
사고보고서 → ① 품목이 무엇인가 → ② 그 품목에 적용되는 기준은 무엇인가
          → ③ 원인·결과 코드 붙이기 → ④ 관련 조항 찾기
```

**품목을 제일 먼저 정하는 게 핵심이다.** 설계문서가 한 문장으로 정리해 뒀다
— "위해요인 코드가 같아도 제품이 다르면 관련 시험이 다르다." 코드부터 찾으면 유아용 의자 사고에 전기다리미 시험이 섞여 나온다.

품목을 못 찾으면 **전체 검색을 자동으로 돌리지 않고 멈춘다.** 
억지로 아무거나 보여 주는 것보다 "못 찾았습니다"가 낫다.

품목 찾는 길은 두 갈래다. 어린이제품 33종은 이름으로 바로 찾고, 전기용품은 파일명에 품목이 없어서 **각 기준의 '적용범위' 원문을 뒤진다.** 
예를 들어 "가습기"는 KC 60335-2-98의 적용범위 문장에 적혀 있어서 그렇게 찾았다.

#### **③ 실제로 돌려 보니 AI가 옳았던 일**

사고보고서 5건을 모두 코드화했더니 **전부 원인이 "알 수 없음"으로 나왔다.**
처음엔 AI가 일을 못한 줄 알고 한 건을 직접 열어 봤다.

가습기 화재 사건이었는데, AI는 "물 부족 시 자동 전원 차단 기능 미작동으로 화재 발생"이라고 상황은 정확히 읽어 냈다. 그런데 원인 칸은 비웠다.
보고서 본문에 이렇게 적혀 있었기 때문이다 — **"제품 시험 결과 모두 안전기준에 적합", "특이사항을 식별하지 못함".**

즉 **조사에서 결함을 못 찾은 사건**이었고, AI는 없는 원인을 지어내지 않았다.

맞는 판단이었다.

그래서 이런 사건은 화면에 이렇게 알리도록 했다.

> ※ 이 사건은 원인이 확정되지 않았습니다. 아래 후보는 피해유형과 어휘만으로 넓게 건진 것이므로 코드 근거가 없습니다. 특정 시험을 단정하지 마십시오.

원인을 모르는데 결과(화재)만 가지고 "이 시험을 하십시오"라고 하면 그건 근거 없는 지목이 된다.

#### **④ 해외 리콜(트랙 B)을 붙였다**

해외 리콜 2,239건이 있는 협회 시스템(Recall Hub)에 실제로 연결했다.
그러면서 **설계 때의 전제 두 개가 실물과 다른 것을 발견했다.**

*전제 1 — "해외 리콜은 이미 코드가 붙어 있다"*
→ **아니었다.** 실제 응답에는 코드가 없고 "질식 위험", "화학적 위험", "전기적 위해 (Electrical Hazard)" 같은 자유 서술만 온다. 표기가 제각각이라 분류 기준으로 쓸 수 없다. 그래서 **해외 리콜도 우리가 코드를 붙이기로**
했다. 조항·사고·리콜 셋이 같은 코드 위에 있어야 대조가 되고, 그게 이 체계의 존재 이유다.

*전제 2 — 주소 오타*
→ `.env.local`에 적혀 있던 `recalhub.kr`(L 하나)은 존재하지 않는 주소였다.
`recallhub.kr`(L 둘)이 맞는 주소다. 고쳤다.

**그리고 설계문서가 "먼저 확인하라"고 남겨 둔 항목 하나를 실측해서 답했다.**

컨셉 문서는 "다른 나라와 우리 기준의 수준 차이를 비교하려면, 그 나라가 어떤 기준을 근거로 리콜했는지 알아야 한다. 확보 가능한 범위를 먼저 확인해야
한다"고 적어 두고 미뤄 놨었다. 2,239건 전수를 훑어서 셌다.

| 출처 | 건수 | 위반 표준 명시 | 비율 |
|---|---:|---:|---:|
| EU | 864 | 450 | **52%** |
| 중국 | 172 | 106 | **62%** |
| 영국 | 266 | 57 | 21% |
| 프랑스 | 171 | 9 | 5% |
| 미국·호주·캐나다·일본 등 | 766 | 3 | 0~1% |
| **합계** | **2,239** | **625** | **27.9%** |

**결론: 기준 수준 비교는 전체의 28%, 사실상 EU·중국·영국 건에서만 가능하다.**
나머지 72%는 사유만 적혀 있어 비교할 근거가 없다. 이걸 알고 시작하는 것과 모르고 시작하는 것은 다르다.

한 가지 더 확인했다. EU 공고의 "EN 60598-2-12"와 우리 "KC 60598-2-12"는 같은 국제표준(IEC)에서 온 같은 문서라 **번호로 바로 대조된다.** 반면 완구
표준(EN 71)이나 중국 가전 표준(GB 4706)은 우리 어린이제품 기준과 번호 체계가 아예 달라 번호로는 안 이어진다 — 그건 사람이 판단할 몫으로 남겼다.

#### **⑤ 심각한 누락 하나를 발견해서 고쳤다**

해외 리콜 분석을 돌려 보다가 결과가 이상하게 얄팍한 것을 발견했다.
조항 본문이 대부분 **"제1부의 이 항목을 적용한다"** 한 줄이었다.

이유를 찾아보니 이랬다. 전기용품 국제표준은 **"제1부(공통) + 제2-x부(품목별)"** 두 권으로 되어 있고, **제2-x부는 제1부를 고치는 개정문**이다. 실제 요구사항의
대부분은 제1부에 있다.

```
KC 60335-2-98 (가습기)   요구사항  54개  ← 우리가 보고 있던 것
KC 60335-1    (공통)     요구사항 395개  ← 통째로 빠져 있던 것
```

**가습기 사고를 분석하면서 요구사항의 88%를 못 보고 있었다.** 품목을 찾을 때 제1부를 자동으로 함께 넣도록 고쳤다. 어린이제품에서 부속서에 공통안전기준을
같이 묶는 것과 같은 구조인데, 전기용품은 그 묶음이 없어서 만들어 준 것이다.

#### **⑥ 정확도 측정표를 만들었다**

설계문서 §5.8이 요구한 비교표(코드만 / 코드+어휘 / 코드+어휘+의미 / +리랭킹을 하나씩 켜면서 재현율·오탐률을 재는 표)를 만들었다.

정답지를 어디서 가져오느냐가 갈리는 지점인데, **운영 기록을 정답지로 쓰지 않기로** 했다.  
시스템이 보여 준 후보 중에서 담당자가 고른 기록은, 시스템이 애초에 안 보여 준 조항을 정답에 넣을 수 없다. 그러면 점수가 늘 부풀려진다.
전문가가 **시스템 결과를 보기 전에** 작성한 정답지를 기본으로 삼는다.

> 지금은 정답지가 없어서 실제 수치는 아직 못 낸다. 표를 찍는 도구까지만 준비된 상태다.

#### **⑦ 순위 재조정(리랭킹)이 한 번도 작동한 적이 없었다는 것을 발견했다**

검색 결과의 순서를 AI가 다시 매기는 기능이 있는데, 그동안 계속 꺼 놓고 돌려서 아무도 몰랐다. 켜 봤더니 바로 거절당했다.

원인은 데이터베이스가 큰 정수(조항 번호표 등)를 **숫자가 아니라 글자로** 돌려주기 때문이었다. `6070`이 아니라 `"6070"`으로 온다. 프로그램 안에서는
숫자라고 적혀 있어서 자동 검사에도 안 걸린다. 조용히 틀리는 자리다.

같은 문제가 네 군데에 있었고, 그중 하나는 **정확도 측정표를 항상 0%로 만들고 있었다** — 정답 조항 번호는 글자, 시스템이 찾은 조항 번호는 숫자라
서로 대조가 안 됐던 것이다.

고친 뒤 실제로 돌려 보니 이렇게 나왔다 (가습기 화재 사건).

```
[1] 19.4     이상운전 시험 조건            재채점 0.82
[2] 24.101   온도과승방지장치는 비자동복귀형   재채점 0.76
[3] 2-98     (기준 표지)                  재채점 0.35
```

**2순위 24.101이 이 사건의 핵심이다.** 사고 보고서가 "물 부족 시 자동 전원 차단 기능 미작동"이라고 적은 그 장치를 규정한 조항이다. AI가 붙인 이유도
정확했다 — "물 부족 시 보호차단이 작동하지 않았다는 사고 경위와 밀접하다."

그리고 순위 재조정은 기준 표지 조항(2-98)을 1위에서 3위로 내렸다. 이유도 적어 놨다 — "가습기 기준 전체에는 해당하지만 구체적 시험 조건을 규정한
조항은 아니다." 이게 이 기능이 해야 할 일이다.

#### **⑧ 표시 조항이 기준마다 다르게 분류되고 있었다**

같은 성격의 절인데 제목 표기에 따라 갈렸다.

```
"표시사항"           → 표시 조항으로 분류  28건
"표시 및 사용설명서"   → 성능요건으로 분류   14건
```

국제표준(IEC 60335) 제7절은 "표시 및 사용설명서"라는 묶인 제목을 쓰는데, 분류 규칙이 그 형태를 몰랐다. 고쳤더니 성능요건 7,766 → 7,472,
표시 조항 879 → 1,173으로 정리됐다.

여기서 한 가지를 **일부러 바꾸지 않았다.** 표시 조항은 지금 검색 후보에서 빠져 있는데, 설계문서가 "사고 원인이 경고·표시와 관련될 때만 켠다"고 정해
놨기 때문이다. 다만 **그 '켜는' 장치는 아직 안 만들었다.** 화상·질식 사고에서 경고 표시는 실제로 확인하는 항목이므로, 조건부로 켜는 기능이 다음 과제로
남아 있다. 지금은 표시 조항 1,173건이 어떤 사건에서도 후보가 되지 않는다.


**왜 이 라운드가 중요한가**

- 이제 사고보고서 한 건을 넣으면 **품목 확정 → 코드화 → 조항 검색 → 시험방법**  까지 끊기지 않고 이어진다. 그전까지는 조각들만 있었다.
- 해외 리콜도 같은 엔진을 타되, **국내 유통 확인·기준 수준 비교·안전조치 검토는 별도로** 다룬다. 리콜을 사고와 똑같이 취급하면 트랙 B의 고유한 가치(제품안전기본법 13조 3항 사업자 보고의무 판단 등)가 사라진다.
- **시스템이 판단하지 않는 선을 그었다.** 국내에 같은 제품이 유통됐는지는통관·유통 자료로 확인할 일이지 이 시스템이 추측할 일이 아니다. 담당자가 확인한 결과를 받아 적기만 한다.

**되어 있는 것**

  → 시험방법 연결**까지 끊기지 않고 이어진다. 가습기 화재 사건으로 끝까지 돌려서 확인했다.

**아직 안 되어 있는 것 (다음에 할 일)**
- **전체 조항 태깅**: 요구사항 조항 7,766개 중 지금까지 코드를 붙인 것은 가습기 관련 기준뿐이다. 나머지는 아직이다. 한 번에 다 돌리기 전에 담당자가 지금까지 붙은 코드를 검수해 보는 게 순서다.
- **정확도 수치**: 재는 도구(§5.8 비교표)는 만들었지만, **전문가가 만든 정답지가 없어서 실제 숫자는 아직 못 낸다.** "이 사고면 어느 조항의 시험을 의뢰하겠는가"를 담당자가 시스템 결과를 보기 전에 적어 주면 바로 잴 수 있다.
- **국내 리콜 연동**: 해외 리콜은 연결했지만 국내 리콜(주소는 받아 둠)은 아직이다. 국내 리콜은 코드가 안 붙어 있어 우리가 붙여야 한다.
- **전기용품 품목 등록**: LED등기구, 스팀다리미 등 일부 품목은 적용범위 원문 검색으로도 안 잡힌다. 담당자가 확인해서 등록해 줘야 한다.
- **화면 반영**: 이번 라운드에 새로 생긴 것들(조항 역할 구분, 품목 확정 근거, 원인 미확정 안내, 해외 리콜 분석)이 아직 화면에는 안 붙었다.
  명령줄에서만 돌아간다.

**① 리랭킹(rerank.ts)·매칭(match.ts)이 되돌아갔다는 우려 확인**

라운드 5에서 고친 bigint→Number() 정규화, effort 기반 LLM 호출이 이후 머지 과정에서

`git diff`로 그 커밋(fb1ddc0)과 지금 최신 상태를 직접 비교해 봤더니 **두 파일 모두

두 개도 이 두 파일에는 아무 변경을 남기지 않은 "깨끗한" 병합이었다. 만약 지금도
예전처럼 동작하는 것처럼 보인다면, 코드 문제가 아니라 (1) 오래된 빌드를 보고 있거나,
(2) 실행 환경에 `OPENAI_RERANK_EFFORT` 값이 실제로 전달 안 되고 있거나, (3) 다른 작업
폴더(워크트리)를 보고 있는 경우일 가능성이 크다 — 코드 자체는 정상이다.

**② 해외 리콜 원본 테이블(Recall Hub)과 지금 쓰는 API 사이의 격차 분석**

지금 이 시스템이 해외 리콜을 가져오는 창구(`src/lib/recall/hub.ts`)는 협회
Recall Hub 관리자 시스템이 공개한 **얇은 API 하나**뿐이다. 그런데 그 관리자
시스템 뒤에는 담당자가 직접 검토·승인한 **훨씬 두꺼운 원본 표(90개 이상 컬럼)**가
따로 있다는 제보가 있어서, 그 원본 표 스키마 문서(`docs/해외리콜수집/recalls table
schema.txt`, `recalls_rows.sql` 실제 표본 데이터)를 읽고 지금 API가 주는 정보와
정확히 뭐가 다른지 대조했다.

- 지금 API가 주는 건 16개 필드뿐이다(제품명, 브랜드, 위험유형, 국가 등 기본 정보).
- 원본 표에는 있지만 API에는 없는 것 중 가장 중요한 두 가지:
  - **원인-결과 2차원 분류(HF-DT) 코드**: 이 시스템이 국내 사고에 쓰는 것과
    **똑같은 코드 체계**(`HF.*`/`DT.*`)로 이미 담당자가 분류해 둔 값이 원본 표에
    있다. 그런데 API는 이걸 안 준다. 그래서 지금 이 시스템은 해외 리콜마다
    **AI로 다시 분류하는 중복 작업**(`recalls:code`)을 하고 있는 셈이다 — 담당자가
    이미 검토해서 붙여 놓은 값을 안 쓰고 있었다.
  - **승인 상태(`approval_status`)**: 담당자 표본 100건을 세어 보니 승인(approved)
    53건, 반려(rejected) 46건, 검토대기(pending) 1건이었다. 즉 원본 표에서 승인된
    것만 골라 오면 담당자가 이미 거른, 신뢰도 높은 건만 받을 수 있는데 지금 API로는
    이 구분을 알 방법이 없다.
  - 그 밖에도 부상자 수, 원문·번역문 양쪽, 이미지·PDF 여러 장, 관리자가 고친 이력
    전체(`update_history`) 등이 원본 표에는 있지만 API에는 없다.
- 원본 표에 직접 연결하려면 그 표가 있는 Supabase 프로젝트(`xicivtmjfkpuehgsieex`)의
  DB 접속 정보가 필요한데, **지금 연결된 관리 도구 계정에는 이 프로젝트가 없었다.**
  같은 조직에 이름이 비슷한 프로젝트(`recall-management`)가 있었지만 주소(ref)가
  다르고 사용 중지 상태였다 — 확인해 보길 잘했다, 헷갈렸으면 엉뚱한 곳에 연결할

## 라운드 8 — HF.S.STD 자동 재분류 · GPC 코드 조회 · 사고사진 비전 분석

세 가지를 한 라운드에 붙였다. 앞의 두 가지(HF.S.STD, GPC)는 라운드 6·7의 뒷정리이고,

### ① HF.S.STD 40건, LLM이 세부 코드로 재분류 — 이제 "미분류"가 생기면 자동으로 이렇게 처리된다

라운드 7에서 미뤄 둔 40건(관리자 쪽이 폐기된 코드 `HF.S.STD`를 붙인 건)을, 우리 쪽
코드북에서 유효한 세부 코드로 LLM이 다시 분류하도록 적재 스크립트를 고쳤다.
새 프롬프트를 만들지 않았다 — 기존 `tagCase()`(사고·리콜 코드화에 원래 쓰던 함수)는
애초에 "지금 유효한 코드 목록"만 답으로 허용하도록 짜여 있어서, 이 함수를 그대로
다시 부르기만 하면 폐기된 코드가 나올 수 자체가 없다. 그래서 앞으로 관리자 쪽에서
또 다른 옛 코드를 보내와도(코드북이 계속 바뀌므로 또 생길 수 있다) 사람이 매번
손대지 않아도 똑같이 처리된다.

관리자 값을 그대로 쓴 코드는 `review_status='approved'`, LLM이 대신 채운 축만
`'auto_unreviewed'`(검수 대상)로 남긴다 — 같은 사건 안에서도 축마다 출처를 구분해
남겨서, 나중에 담당자가 뭘 다시 봐야 하는지 바로 걸러낼 수 있게 했다.

실제로 40건 전부 돌려 봤다. 대부분(32건)은 `HF.H.ELEC.BAT`, `HF.S.NATL.DEF`처럼
구체적인 세부 코드로 갔고, 일부(8건)는 `HF.H`, `HF.S`처럼 큰 갈래 이름만 나왔다.
이건 이번에 새로 생긴 문제가 아니라 **이 시스템의 코드화 기능 전체가 원래 갖고
있던 특성**이라는 것도 확인했다 — 코드북 조회 옵션을 어떻게 주든 그 큰 갈래
이름 자체가 항상 고를 수 있는 목록에 들어 있었다(사고보고서 코드화에도 똑같이
적용된다). 다만 그런 애매한 답이 나오면 검수 대상으로 표시되게 만들어 뒀으니,
이번 경우엔 딱 설계한 대로 걸러진 셈이다.

### ② GPC(GS1 국제 품목분류) 코드 조회 — 처음 생각과 다르게 방식을 바꿨다

담당자가 "이미 있는 edge function을 부르자"고 했는데, 실제로 만들어 보니 두 가지
문제가 나와서 방식을 바꿨다.

1. 그 edge function은 후보를 1개(top-1)만 주도록 고정돼 있었다. 담당자가 원한
   "후보 3~5개"를 애초에 못 낸다.
2. 그 edge function 안에 박혀 있는 OpenAI 키가 크레딧이 다 떨어진 상태였다
   (`429 no credits remaining` 실측). 우리가 고칠 수 있는 부분이 아니다.

그런데 담당자가 이어서 보내 준 n8n 워크플로(`(GS1) [한국리콜__OECD] OECD GPC
RAG.json`)를 보니, 그 edge function이 쓰는 것과 **같은 프로젝트 안에 있는 원본
표·검색 함수**(`oecd_gpc_202405` 표, `match_documents_202405` 함수)를 직접
참조하고 있었다. 실제로 그 함수를 우리 쪽 anon 키로 직접 불러 봤더니(edge
function을 거치지 않고) **바로 실행이 됐다** — 즉 협회가 처음부터 이 함수를
외부에서 부를 수 있게 열어 둔 상태였다.

그래서 edge function은 아예 안 쓰기로 했다. 대신:
- 상품명·설명 문장을 **우리 OpenAI 키**로 임베딩한다(그쪽 크레딧 문제와 무관해진다).
- 그 벡터로 `match_documents_202405`를 직접 불러 후보를 원하는 개수(3~5개)만큼 받는다.

실제로 "가습기"로 검색해 봤다. 1위가 정확히 "가습기 - 이동형" 브릭이었다. 그런데
유사도 값 자체는 0.25 안팎으로 낮았다 — 원래 edge function의 기본 임계값(0.75)을
그대로 썼다면 **정답인 1위조차 "일치 없음"으로 걸러졌을 것**이다. 그래서 임계값으로
거르지 않고 순위(상위 몇 개)로만 판단하기로 했다. 또 하나, 사진에서 뽑은 좀 더
상세한 설명 문장으로 다시 검색했더니 1위가 "제습기"(가습기의 반대 기능)로 바뀌고
"가습기"가 2위로 밀린 적도 있었다 — 이게 정확히 담당자가 "후보 여러 개를 보고
싶다"고 한 이유였다는 걸 실측으로 확인한 셈이다. 1개만 믿었으면 틀렸을 사례다.

### ③ 사고조사보고서 첨부 사진 분석 — 새 기능, 실제로 텍스트가 놓친 단서를 찾았다

다수가 "시험 결과 안전기준 적합"이라는 문장만 남기고 원인 미확인(HF.UNKNOWN)으로
끝났던 걸 다시 보니, 사진에 텍스트에 없는 단서가 있을 수 있겠다 싶어 이번에 붙였다.

**한 일**
- PDF에서 삽입 사진만 뽑아낸다(페이지를 통째로 찍는 게 아니라 실제 이미지
  오브젝트만 — 표·글자는 안 섞인다). 가로세로 200px 미만인 것은 뺀다(로고·직인
  같은 서식 이미지가 여러 보고서에서 정확히 같은 크기로 반복되는 걸 실측으로

  이 프로젝트의 원칙을 사진에도 그대로 적용했다.
- 뽑은 사진은 Supabase Storage(기존 원본 보관 버킷)에 저장하고, 새 표

- 비전 LLM(담당자 요청대로 최상위 모델은 아니고 이 시스템의 "품질 우선" 등급

  실제로 맞았다.

**실제로 돌려서 확인한 것 (가습기 사고, 2026-09-02)**
- 11쪽짜리 보고서에서 사진 4장을 뽑았고, 비전 LLM이 4장 전부 증거 사진으로
  판단했다.
- 그중 4쪽 사진 2장에서 **"바닥면 내부 부품 주변에 갈색 변색 또는 얼룩이 보인다"**는
  관찰을 냈다. 이 보고서의 텍스트만으로는(원래 결론이 "시험 결과 적합") 전혀
  나오지 않았던 단서다. 텍스트 코드화 결과는 여전히 HF.UNKNOWN(원인 미확인)으로
  남아 있는데, 이 갈변 관찰이 담당자가 재검토할 때 실제로 쓸모 있을 만한 신호다.

**작업 중 실수하고 바로 고친 것**
- 이 기능을 가습기 사건으로 테스트하면서 `--force` 옵션을 썼는데, 이게 그
  사건의 **기존 확정 상태·품목·코드화 결과(라운드 5의 리랭킹 시연 데이터)를
  통째로 지워 버렸다.** 바로 알아채고 코드화를 다시 돌리고(`HF.UNKNOWN` /
  `DT.THERMAL.FIRE`로 원래와 같은 결과 확인) 확정 상태를 되돌리고 임베딩을
  다시 만들어 복구했다. 앞으로 이런 시연·데모 데이터가 있는 사건에는
  `--force`를 함부로 쓰면 안 된다는 걸 기록해 둔다.
- GPC 조회를 처음엔 edge function 기준으로 구현하고 사고 스크립트에 연결까지
  했는데, 위 ②의 이유로 도중에 직접 RPC 호출 방식으로 다시 짰다. 함수
  자체(`findGpcCandidates`)는 실제 호출로 검증했지만, 새 방식으로 사고 적재
  스크립트 전체를 다시 돌려서 확인하지는 못했다 — 위 `--force` 실수를 반복하지
  않으려고 기존 5건에는 재실행을 안 했다. **다음에 새 사고보고서가 들어오면
  그때 사진→비전→GPC 전체 경로가 실제로 이어지는지 처음으로 확인하게 된다.**
