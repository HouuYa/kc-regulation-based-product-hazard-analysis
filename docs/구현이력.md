# 구현 이력 — 쉬운 설명

> 이 문서는 코드를 몰라도 "지금까지 무엇을 왜 만들었는지" 알 수 있도록 쓴다.
> 작업 한 라운드가 끝날 때마다 아래에 새 항목을 추가한다. 오래된 내용을 지우지
> 않고 쌓아 간다 — 나중에 "그때 왜 이렇게 정했지"를 되짚을 수 있어야 하기 때문이다.
> (자세한 기술적 근거는 각 코드 파일 맨 위 주석에 있다. 이 문서는 그 요약이다.)

## 라운드 1 — 설계 검토와 첫 골격

**한 일**
- 설계문서 3종(컨셉 v0.4, 구현설계 v0.6, 코드북 PDR v0.9.7)을 읽고 실제로 구현
  가능한지 확인했다.
- `credentail.md`에 평문으로 있던 국내·해외 리콜 API 키를 `.env.local`로 옮기고
  원본 파일은 삭제했다. (저장소가 비공개라 즉시 위험은 낮았지만, 평문 키를
  깃에 올려 두는 것 자체가 좋지 않은 습관이라 바로 정리했다.)
- 위해요인 코드북(2차원 분류 — 원인 HF / 결과 DT)을 자동으로 읽어 들이는
  프로그램을 만들고, 실제 파일로 돌려서 문서에 적힌 숫자(HF 64개, DT 16개)와
  정확히 일치하는지 확인했다.
- KC안전기준 JSON 파일 76개를 열어 봐서, "조항이 어떤 시험방법과 연결되는지"가
  파일 안에 이미 들어 있다는 것을 확인했다. (예: "의자가 넘어지지 않아야
  한다"는 조항이 "150N의 힘을 가한다"는 시험방법과 서로 짝지어져 있었다.)

**왜 중요한가**
- 이 시스템의 핵심은 "사고 원인 코드"와 "안전기준 조항"을 같은 코드로 이어
  붙이는 것이다. 코드북이 정확히 안 읽히면 그 뒤 모든 게 흔들리므로, 제일
  먼저 검증했다.

## 라운드 2 — 데이터베이스(Supabase) 만들고 실제로 돌려 보기

**한 일**
- Supabase에 새 프로젝트(`kc-hazard-analysis`)를 만들었다.
- 설계에 필요한 표(테이블) 18개와 검색 함수들을 실제로 만들었다.
- 한국어 검색이 되는지 실측했다. PostgreSQL 기본 검색 기능은 "전도가",
  "전도를"처럼 조사가 붙으면 다른 단어로 착각한다 — 이게 진짜 문제인지
  실제로 테스트해 봤더니 정말 그랬다. 그래서 한국어를 제대로 검색하는
  별도 기능(PGroonga)을 설치했고, 이번엔 조사가 붙어도 잘 찾는 것을
  확인했다.
- 가짜 사고 1건을 넣고 실제로 검색을 돌려 봤다. "의자가 옆으로 넘어져
  아이가 떨어졌다"는 사고를 코드화(설계결함 + 낙상)한 뒤 검색했더니,
  정확히 그 원인·결과 코드가 붙어 있던 조항("4.3.3 안정성")을 찾아냈고,
  그 조항이 가리키는 시험방법("5.9.2")까지 자동으로 이어졌다. 설계문서에
  적혀 있던 예시가 실제로 작동한 것을 확인한 셈이다.

**발견해서 고친 문제**
- Supabase는 새로 만든 함수를 기본적으로 "누구나 실행 가능"하게 열어
  둔다는 사실을 발견했다. 데이터를 볼 수 있는 건 아니지만, 굳이 열어 둘
  이유가 없어서 전부 잠그고 서버만 쓸 수 있게 고쳤다.

## 라운드 3 — 사람이 쓸 화면 만들기

**한 일**
- 화면 4개를 만들었다: 전체 현황, 안전기준 목록, 위해요인 코드 목록,
  사고보고서 등록, 사건 분석 결과.
- "이 시스템은 위반 여부를 판정하지 않는다"는 원칙을 화면에도 그대로
  옮겼다. 예를 들어 위험하다는 뜻으로 빨간색을 쓰지 않는다. 빨간색은
  오직 "시스템이 진짜로 고장 났을 때"(연결 실패 등)에만 쓴다. 후보
  조항 목록에는 빨간 경고색을 절대 쓰지 않는다 — 시스템이 위험을
  판정하는 것처럼 보이면 안 되기 때문이다.
- 사고보고서 PDF를 업로드하면 자동으로 글자를 뽑아내고, 그 안에
  주민등록번호·전화번호·이메일 같은 개인정보가 있는지 확인한다.
  걸리면 그 파일은 분석 대상으로 넘기지 않는다(외부 AI에게 보내지
  않는다는 뜻).

**중간 점검에서 반영한 것**
- 처음 문서(v0.6)를 검토한 보완본(v0.7)이 도중에 도착했다. v0.7은
  "품목을 먼저 확정하지 않고 검색부터 하면 다른 제품의 시험이 섞일 수
  있다"거나 "검색 결과가 0건이라고 해서 무조건 '이 기준엔 조항이
  없다'로 단정하면 안 된다(아직 준비가 덜 된 것일 수도 있다)" 같은
  지적을 했다. 두 버전(v0.6, v0.7)이 서로 다르게 말하는 부분은 어느
  한쪽만 고르지 않고, 나중에 실제 데이터로 비교해 볼 수 있게 "선택
  가능한 방식"으로 만들어 두었다.

## 라운드 4 — 실제 데이터 채우기 · 신규 자료 감지 기능 · 정리

**한 일**

1. **환경설정 값 채움** — 승호님이 새로 발급받은 Supabase 접속 정보와
   국내·해외 리콜 API 주소를 `.env.local`에 반영했다.

2. **깃(git) 이력 정리** — 이 작업들을 하는 동안, 원격 저장소(GitHub)에
   다른 경로로 커밋 3개가 먼저 올라와 있어서 로컬 작업과 갈라져 있었다.
   서로 다른 파일을 건드린 커밋들이라 충돌 없이 합쳤다.

3. **실제 데이터 적재** — 지금까지는 프로그램이 "이론적으로 맞다"는
   것만 확인했는데, 이번에 처음으로 실제 데이터를 전부 넣어 봤다.
   - 위해요인 코드북 1건 (HF 64개, DT 16개)
   - 안전기준 76개 문서 전체, 조항 13,501개, 시험조건 333개,
     "이 조항은 이 시험과 연결된다"는 관계 644개
   - 넣은 뒤 개수를 다시 세어 봤더니 프로그램이 미리 계산했던 숫자와
     한 자리도 틀리지 않고 똑같았다.

4. **새 자료가 들어왔을 때 자동으로 알아채는 기능** — 협회가 나중에
   기준을 개정해서 새 JSON 파일을 주면, 그게 "완전히 새로운 기준"인지
   "이미 있는 기준의 개정판"인지 자동으로 구분하는 기능을 만들었다.
   - 완전히 같은 내용이면 → 아무 것도 안 함
   - 이름은 같은데 내용이 바뀌었으면 → 옛날 버전은 지우지 않고 "지금은
     안 씀"으로 표시만 하고, 새 버전을 새로 넣는다. (옛 버전에 달려
     있던 사람의 판단 기록은 절대 사라지면 안 되기 때문에 지우지
     않는다.)
   - 완전히 새로운 이름이면 → 새로 넣는다.
   - 나중에 이 기능을 웹 주소(API)로도 호출할 수 있게 만들어 뒀다.
     지금 당장 누가 자동으로 호출하는 건 아니지만, 나중에 "자동 감시"
     기능을 붙일 때 바로 쓸 수 있도록 미리 만들어 둔 것이다.

5. **사고조사보고서 5건 처리** — `사고조사보고서` 폴더에 있는 실제
   PDF 5건(보조배터리 2건, LED등기구, 스팀다리미, 가습기)을 한 번에
   처리하는 기능을 만들어 돌렸다.
   - **처리 중 실제 문제를 하나 발견했다.** 개인정보 탐지 기능이
     "계좌번호"로 착각한 게 있었는데, 확인해 보니 진짜 계좌번호가
     아니라 보고서에 적힌 접수일자("25-11-24" 같은 형식)였다. 날짜와
     계좌번호가 둘 다 숫자에 하이픈이 섞인 모양이라 헷갈린 것이다.
     실제 계좌번호는 자릿수가 훨씬 많다는 점을 이용해서 구분하도록
     고쳤다. 고친 뒤에는 날짜는 더 이상 걸리지 않으면서, 진짜
     계좌번호처럼 생긴 것은 여전히 잡아내는 것을 확인했다.
   - 5건 모두 정상 처리됐다. (다만 이 상태로는 "등록"만 된 것이고,
     담당자가 화면에서 원문을 확인하고 "확정" 버튼을 눌러야 실제
     분석 대상이 된다 — 이것도 의도한 설계다. 사람이 확인하기 전에는
     시스템이 멋대로 넘어가지 않는다.)

## 지금 시점에서 되어 있는 것 / 안 되어 있는 것

**되어 있는 것**
- 위해요인 코드북, 안전기준 76개 문서, 사고조사보고서 5건이 모두
  데이터베이스에 들어가 있다.
- 코드로 조항을 찾고, 그 조항의 시험방법까지 자동으로 잇는 기능이
  실제로 작동한다.
- 화면에서 현황을 볼 수 있고, 사고보고서를 올릴 수 있다.

**아직 안 되어 있는 것 (다음에 할 일)**
- **AI 태깅**: 사고보고서·조항에 "원인·결과 코드"를 자동으로 붙이는
  기능은 만들어져 있지만, 아직 실행하지 않았다. OpenAI API 키가
  필요한데 아직 안 채워졌기 때문이다. 키를 넣으면 바로 돌릴 수 있다.
- **정확도 측정표**: "코드로만 찾을 때 vs 코드+키워드 vs 코드+키워드+
  의미검색" 중 어느 조합이 실제로 더 정확한지 재는 표(설계문서
  §5.8)는 아직 안 만들었다. 태깅이 끝나야 잴 수 있는 것이라 다음
  순서다.
- **국내·해외 리콜 연동**: API 주소는 받았지만 아직 실제로 연결해서
  데이터를 가져오는 코드는 안 만들었다.
- **원본 파일 보관함(Storage)**: 사고보고서 PDF 원본을 안전하게
  따로 보관하는 저장소가 아직 안 만들어져 있어서, 지금은 추출한
  텍스트만 저장되고 원본 PDF 자체는 보관되지 않는다.

## 앞으로 이 문서를 쓰는 방법

- 코드를 크게 바꾸는 작업 한 라운드가 끝나면, 위쪽에 새 항목을 추가한다.
- "무엇을 했는지"보다 "왜 했는지, 뭘 확인했는지"를 더 자세히 쓴다.
  (무엇을 했는지는 git 커밋 메시지를 보면 되지만, 왜 했는지는 그때
  가서야 알 수 있다.)
- 전문용어가 나오면 괄호로 짧게 풀어 쓴다. 이 문서는 코드를 안 보는
  사람도 읽을 수 있어야 한다.
