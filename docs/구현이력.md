  먼저 검증했다.

## 라운드 2 — 데이터베이스(Supabase) 만들고 실제로 돌려 보기

**한 일**
- Supabase에 새 프로젝트(`kc-hazard-analysis`)를 만들었다.
- 설계에 필요한 표(테이블) 18개와 검색 함수들을 실제로 만들었다.
- 한국어 검색이 되는지 실측했다. PostgreSQL 기본 검색 기능은 "전도가",
  "전도를"처럼 조사가 붙으면 다른 단어로 착각한다 — 이게 진짜 문제인지
  실제로 테스트해 봤더니 정말 그랬다. 그래서 한국어를 제대로 검색하는
  별도 기능(PGroonga)을 설치했고, 이번엔 조사가 붙어도 잘 찾는 것을
  확인했다.
- 가짜 사고 1건을 넣고 실제로 검색을 돌려 봤다. "의자가 옆으로 넘어져
  아이가 떨어졌다"는 사고를 코드화(설계결함 + 낙상)한 뒤 검색했더니,
  정확히 그 원인·결과 코드가 붙어 있던 조항("4.3.3 안정성")을 찾아냈고,
  그 조항이 가리키는 시험방법("5.9.2")까지 자동으로 이어졌다. 설계문서에
  적혀 있던 예시가 실제로 작동한 것을 확인한 셈이다.

**발견해서 고친 문제**
- Supabase는 새로 만든 함수를 기본적으로 "누구나 실행 가능"하게 열어
  둔다는 사실을 발견했다. 데이터를 볼 수 있는 건 아니지만, 굳이 열어 둘
  이유가 없어서 전부 잠그고 서버만 쓸 수 있게 고쳤다.

  가능한 방식"으로 만들어 두었다.

## 라운드 4 — 실제 데이터 채우기 · 신규 자료 감지 기능 · 정리

**한 일**

1. **환경설정 값 채움** — 승호님이 새로 발급받은 Supabase 접속 정보와
   국내·해외 리콜 API 주소를 `.env.local`에 반영했다.

2. **깃(git) 이력 정리** — 이 작업들을 하는 동안, 원격 저장소(GitHub)에
   다른 경로로 커밋 3개가 먼저 올라와 있어서 로컬 작업과 갈라져 있었다.
   서로 다른 파일을 건드린 커밋들이라 충돌 없이 합쳤다.

3. **실제 데이터 적재** — 지금까지는 프로그램이 "이론적으로 맞다"는
   것만 확인했는데, 이번에 처음으로 실제 데이터를 전부 넣어 봤다.
   - 위해요인 코드북 1건 (HF 64개, DT 16개)
   - 안전기준 76개 문서 전체, 조항 13,501개, 시험조건 333개,
     "이 조항은 이 시험과 연결된다"는 관계 644개
   - 넣은 뒤 개수를 다시 세어 봤더니 프로그램이 미리 계산했던 숫자와
     한 자리도 틀리지 않고 똑같았다.

4. **새 자료가 들어왔을 때 자동으로 알아채는 기능** — 협회가 나중에
   기준을 개정해서 새 JSON 파일을 주면, 그게 "완전히 새로운 기준"인지
   "이미 있는 기준의 개정판"인지 자동으로 구분하는 기능을 만들었다.
   - 완전히 같은 내용이면 → 아무 것도 안 함
   - 이름은 같은데 내용이 바뀌었으면 → 옛날 버전은 지우지 않고 "지금은
     안 씀"으로 표시만 하고, 새 버전을 새로 넣는다. (옛 버전에 달려
     있던 사람의 판단 기록은 절대 사라지면 안 되기 때문에 지우지
     않는다.)
   - 완전히 새로운 이름이면 → 새로 넣는다.
   - 나중에 이 기능을 웹 주소(API)로도 호출할 수 있게 만들어 뒀다.
     지금 당장 누가 자동으로 호출하는 건 아니지만, 나중에 "자동 감시"
     기능을 붙일 때 바로 쓸 수 있도록 미리 만들어 둔 것이다.

5. **사고조사보고서 5건 처리** — `사고조사보고서` 폴더에 있는 실제
   PDF 5건(보조배터리 2건, LED등기구, 스팀다리미, 가습기)을 한 번에
   처리하는 기능을 만들어 돌렸다.
   - **처리 중 실제 문제를 하나 발견했다.** 개인정보 탐지 기능이
     "계좌번호"로 착각한 게 있었는데, 확인해 보니 진짜 계좌번호가
     아니라 보고서에 적힌 접수일자("25-11-24" 같은 형식)였다. 날짜와
     계좌번호가 둘 다 숫자에 하이픈이 섞인 모양이라 헷갈린 것이다.
     실제 계좌번호는 자릿수가 훨씬 많다는 점을 이용해서 구분하도록
     고쳤다. 고친 뒤에는 날짜는 더 이상 걸리지 않으면서, 진짜
     계좌번호처럼 생긴 것은 여전히 잡아내는 것을 확인했다.
   - 5건 모두 정상 처리됐다. (다만 이 상태로는 "등록"만 된 것이고,
     담당자가 화면에서 원문을 확인하고 "확정" 버튼을 눌러야 실제
     분석 대상이 된다 — 이것도 의도한 설계다. 사람이 확인하기 전에는
     시스템이 멋대로 넘어가지 않는다.)

## 라운드 5 — AI 코드화 실제 가동 · 품목 확정 · 해외 리콜 연결

**한 일 (크게 넷)**

**① AI에게 코드를 붙이게 하되, 두 번 물어보게 했다**

앞 라운드까지는 "AI로 코드를 붙인다"고 만들어만 두고 실제로는 못 돌렸다.
API 키가 채워져서 이번에 처음 돌렸다.

그냥 돌리지 않고 방식을 하나 정했다. **싼 모델에게 세 번 물어보고, 세 번
답이 갈리면 그때만 비싼 모델에게 다시 묻는다.**

왜 이렇게 했는가. 값을 재 봤더니 싼 모델(Luna) 세 번이 비싼 모델(Terra)
한 번보다 **3.3배 싸다.** 그런데 세 번 물어서 답이 같으면 그 답은 믿을
만하다. 답이 갈리는 건은 원래도 어려운 건이니 비싼 모델로 올린다.

여기서 한 가지를 일부러 피했다. AI에게 "네 답이 얼마나 확실하냐"고 물어
그 숫자로 판단하는 방법이 있는데, **설계문서가 그 숫자를 믿지 말라고 명시**
했다(§5.2.3). 실제로 틀린 답에도 0.9를 매긴다. 대신 **같은 질문을 세 번
해서 답이 얼마나 일치했는지**를 기준으로 삼았다. 이건 AI의 자기 평가가
아니라 관측된 사실이다.

돌려 본 결과 — 안전기준 조항 53개 중 **16개(30%)가 비싼 모델로 올라갔고,
그중 10개는 비싼 모델이 다른 답을 냈다.** 이 10개가 사람이 제일 먼저
봐야 할 목록이다.

> 정직하게 덧붙인다. 비싼 모델이 답을 **바꿨다**는 것과 **맞혔다**는 것은
> 다르다. 어느 쪽이 옳은지는 전문가가 만든 정답지가 있어야 알 수 있고,
> 그건 아직 없다. 지금은 "여기가 흔들리는 구간"까지만 말할 수 있다.

**② 사고 사건을 실제 흐름에 연결했다 — 품목부터 정한다**

사고보고서를 넣으면 이제 이 순서로 처리된다.

```
사고보고서 → ① 품목이 무엇인가 → ② 그 품목에 적용되는 기준은 무엇인가
          → ③ 원인·결과 코드 붙이기 → ④ 관련 조항 찾기
```

**품목을 제일 먼저 정하는 게 핵심이다.** 설계문서가 한 문장으로 정리해 뒀다
— "위해요인 코드가 같아도 제품이 다르면 관련 시험이 다르다." 코드부터 찾으면
유아용 의자 사고에 전기다리미 시험이 섞여 나온다.

품목을 못 찾으면 **전체 검색을 자동으로 돌리지 않고 멈춘다.** 억지로
아무거나 보여 주는 것보다 "못 찾았습니다"가 낫다.

품목 찾는 길은 두 갈래다. 어린이제품 33종은 이름으로 바로 찾고, 전기용품은
파일명에 품목이 없어서 **각 기준의 '적용범위' 원문을 뒤진다.** 예를 들어
"가습기"는 KC 60335-2-98의 적용범위 문장에 적혀 있어서 그렇게 찾았다.

**③ 실제로 돌려 보니 AI가 옳았던 일**

사고보고서 5건을 모두 코드화했더니 **전부 원인이 "알 수 없음"으로 나왔다.**
처음엔 AI가 일을 못한 줄 알고 한 건을 직접 열어 봤다.

가습기 화재 사건이었는데, AI는 "물 부족 시 자동 전원 차단 기능 미작동으로
화재 발생"이라고 상황은 정확히 읽어 냈다. 그런데 원인 칸은 비웠다.
보고서 본문에 이렇게 적혀 있었기 때문이다 — **"제품 시험 결과 모두 안전기준에
적합", "특이사항을 식별하지 못함".**

즉 **조사에서 결함을 못 찾은 사건**이었고, AI는 없는 원인을 지어내지 않았다.
맞는 판단이었다.

그래서 이런 사건은 화면에 이렇게 알리도록 했다.

> ※ 이 사건은 원인이 확정되지 않았습니다. 아래 후보는 피해유형과 어휘만으로
> 넓게 건진 것이므로 코드 근거가 없습니다. 특정 시험을 단정하지 마십시오.

원인을 모르는데 결과(화재)만 가지고 "이 시험을 하십시오"라고 하면 그건
근거 없는 지목이 된다.

**④ 해외 리콜(트랙 B)을 붙였다**

해외 리콜 2,239건이 있는 협회 시스템(Recall Hub)에 실제로 연결했다.
그러면서 **설계 때의 전제 두 개가 실물과 다른 것을 발견했다.**

*전제 1 — "해외 리콜은 이미 코드가 붙어 있다"*
→ **아니었다.** 실제 응답에는 코드가 없고 "질식 위험", "화학적 위험",
"전기적 위해 (Electrical Hazard)" 같은 자유 서술만 온다. 표기가 제각각이라
분류 기준으로 쓸 수 없다. 그래서 **해외 리콜도 우리가 코드를 붙이기로**
했다. 조항·사고·리콜 셋이 같은 코드 위에 있어야 대조가 되고, 그게 이
체계의 존재 이유다.

*전제 2 — 주소 오타*
→ `.env.local`에 적혀 있던 `recalhub.kr`(L 하나)은 존재하지 않는 주소였다.
`recallhub.kr`(L 둘)이 맞는 주소다. 고쳤다.

**그리고 설계문서가 "먼저 확인하라"고 남겨 둔 항목 하나를 실측해서 답했다.**

컨셉 문서는 "다른 나라와 우리 기준의 수준 차이를 비교하려면, 그 나라가 어떤
기준을 근거로 리콜했는지 알아야 한다. 확보 가능한 범위를 먼저 확인해야
한다"고 적어 두고 미뤄 놨었다. 2,239건 전수를 훑어서 셌다.

| 출처 | 건수 | 위반 표준 명시 | 비율 |
|---|---:|---:|---:|
| EU | 864 | 450 | **52%** |
| 중국 | 172 | 106 | **62%** |
| 영국 | 266 | 57 | 21% |
| 프랑스 | 171 | 9 | 5% |
| 미국·호주·캐나다·일본 등 | 766 | 3 | 0~1% |
| **합계** | **2,239** | **625** | **27.9%** |

**결론: 기준 수준 비교는 전체의 28%, 사실상 EU·중국·영국 건에서만 가능하다.**
나머지 72%는 사유만 적혀 있어 비교할 근거가 없다. 이걸 알고 시작하는 것과
모르고 시작하는 것은 다르다.

한 가지 더 확인했다. EU 공고의 "EN 60598-2-12"와 우리 "KC 60598-2-12"는
같은 국제표준(IEC)에서 온 같은 문서라 **번호로 바로 대조된다.** 반면 완구
표준(EN 71)이나 중국 가전 표준(GB 4706)은 우리 어린이제품 기준과 번호
체계가 아예 달라 번호로는 안 이어진다 — 그건 사람이 판단할 몫으로 남겼다.

**⑤ 심각한 누락 하나를 발견해서 고쳤다**

해외 리콜 분석을 돌려 보다가 결과가 이상하게 얄팍한 것을 발견했다.
조항 본문이 대부분 **"제1부의 이 항목을 적용한다"** 한 줄이었다.

이유를 찾아보니 이랬다. 전기용품 국제표준은 **"제1부(공통) + 제2-x부(품목별)"**
두 권으로 되어 있고, **제2-x부는 제1부를 고치는 개정문**이다. 실제 요구사항의
대부분은 제1부에 있다.

```
KC 60335-2-98 (가습기)   요구사항  54개  ← 우리가 보고 있던 것
KC 60335-1    (공통)     요구사항 395개  ← 통째로 빠져 있던 것
```

**가습기 사고를 분석하면서 요구사항의 88%를 못 보고 있었다.** 품목을 찾을 때
제1부를 자동으로 함께 넣도록 고쳤다. 어린이제품에서 부속서에 공통안전기준을
같이 묶는 것과 같은 구조인데, 전기용품은 그 묶음이 없어서 만들어 준 것이다.

**⑥ 정확도 측정표를 만들었다**

설계문서 §5.8이 요구한 비교표(코드만 / 코드+어휘 / 코드+어휘+의미 / +리랭킹을
하나씩 켜면서 재현율·오탐률을 재는 표)를 만들었다.

정답지를 어디서 가져오느냐가 갈리는 지점인데, **운영 기록을 정답지로 쓰지
않기로** 했다. 시스템이 보여 준 후보 중에서 담당자가 고른 기록은, 시스템이
애초에 안 보여 준 조항을 정답에 넣을 수 없다. 그러면 점수가 늘 부풀려진다.
전문가가 **시스템 결과를 보기 전에** 작성한 정답지를 기본으로 삼는다.

> 지금은 정답지가 없어서 실제 수치는 아직 못 낸다. 표를 찍는 도구까지만
> 준비된 상태다.

**왜 이 라운드가 중요한가**

- 이제 사고보고서 한 건을 넣으면 **품목 확정 → 코드화 → 조항 검색 → 시험방법**
  까지 끊기지 않고 이어진다. 그전까지는 조각들만 있었다.
- 해외 리콜도 같은 엔진을 타되, **국내 유통 확인·기준 수준 비교·안전조치
  검토는 별도로** 다룬다. 리콜을 사고와 똑같이 취급하면 트랙 B의 고유한
  가치(제품안전기본법 13조 3항 사업자 보고의무 판단 등)가 사라진다.
- **시스템이 판단하지 않는 선을 그었다.** 국내에 같은 제품이 유통됐는지는
  통관·유통 자료로 확인할 일이지 이 시스템이 추측할 일이 아니다. 담당자가
  확인한 결과를 받아 적기만 한다.

## 지금 시점에서 되어 있는 것 / 안 되어 있는 것

*(라운드 5 종료 시점 기준)*

**되어 있는 것**
- 위해요인 코드북, 안전기준 76개 문서(조항 13,501개), 사고조사보고서 5건이
  모두 데이터베이스에 들어가 있다. 보고서 PDF 원본도 보관함(Storage)에 있다.
- 사고보고서 한 건을 넣으면 **품목 확정 → 원인·결과 코드화 → 관련 조항 검색
  → 시험방법 연결**까지 끊기지 않고 이어진다. 가습기 화재 사건으로 끝까지
  돌려서 확인했다.
- AI 코드화가 실제로 돌아간다. 싼 모델 3회 → 답이 갈리면 비싼 모델로 승격하는
  2단 방식이고, 흔들린 건을 검수 목록으로 따로 뽑아 준다.
- 해외 리콜(2,239건)에 실제로 연결된다. 검색해서 가져오고, 코드를 붙이고,
  국내 기준 조항과 대조하고, 상대국이 지목한 표준과 우리 기준을 견줄 수 있다.
- 화면에서 현황을 볼 수 있고, 사고보고서를 올릴 수 있다.

**아직 안 되어 있는 것 (다음에 할 일)**
- **전체 조항 태깅**: 요구사항 조항 7,766개 중 지금까지 코드를 붙인 것은
  가습기 관련 기준뿐이다. 나머지는 아직이다. 한 번에 다 돌리기 전에
  담당자가 지금까지 붙은 코드를 검수해 보는 게 순서다.
- **정확도 수치**: 재는 도구(§5.8 비교표)는 만들었지만, **전문가가 만든
  정답지가 없어서 실제 숫자는 아직 못 낸다.** "이 사고면 어느 조항의 시험을
  의뢰하겠는가"를 담당자가 시스템 결과를 보기 전에 적어 주면 바로 잴 수 있다.
- **국내 리콜 연동**: 해외 리콜은 연결했지만 국내 리콜(주소는 받아 둠)은
  아직이다. 국내 리콜은 코드가 안 붙어 있어 우리가 붙여야 한다.
- **전기용품 품목 등록**: LED등기구, 스팀다리미 등 일부 품목은 적용범위
  원문 검색으로도 안 잡힌다. 담당자가 확인해서 등록해 줘야 한다.
- **화면 반영**: 이번 라운드에 새로 생긴 것들(조항 역할 구분, 품목 확정
  근거, 원인 미확정 안내, 해외 리콜 분석)이 아직 화면에는 안 붙었다.
  명령줄에서만 돌아간다.
