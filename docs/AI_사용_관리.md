# AI 사용 관리

이 시스템에서 AI는 **정해진 자리에서만** 돈다. 「어느 조항이 걸리는가」는 SQL이 계산하고, AI는 뜻을 옮기거나(품목·코드) 후보를 걸러내는 일만 맡는다. 이 경계가 흐려지면 재현할 수 없는 결과가 담당자에게 근거로 제시된다.

전체 흐름에서 AI가 어디에 끼는지는 **[전체 프로세스와 용어](전체_프로세스와_용어.md)**에 있다. 이 문서는 그 자리들을 하나씩 놓고 **무엇을 묻고, 어떻게 받고, 근거를 어디에 남기는지**를 적는다.

## 1. 부르는 자리 열한 곳

**이 표는 화면에서 본다 — [🤖 AI 사용과 비용](/llm)** 의 「AI를 부르는 자리」 절이 자리마다 무엇을 묻는지, 어떤 모델을 쓰는지, 답을 무엇으로 못박았는지, 근거가 DB 어디에 남는지를 한 표로 보여 준다.

**목록의 원본은 코드다**(`src/lib/llm/catalog.ts`). 문서에 손으로 적어 두면 코드가 바뀔 때 조용히 틀리기 때문이다. 실제로 그런 일이 있었다 — 사진 분석이 코드 부여와 같은 이름(`purpose='tagging'`)으로 기록되고 있었는데 이 문서에는 별개의 자리로 적혀 있었다(2026-09-08에 `vision`으로 분리).

| # | 무엇을 묻나 | 모델 설정 | 언제 도나 |
| --- | --- | --- | --- |
| 1 | 위해요인 코드 부여 (HF·DT) | `OPENAI_BULK_MODEL` · 애매하면 `OPENAI_ESCALATE_MODEL` | 사고보고서·리콜을 사건으로 만들 때 |
| 2 | 사고 사진 분석 | `OPENAI_VISION_MODEL` | 사진이 붙은 사고보고서 |
| 3 | 조항 재채점 | `OPENAI_RERANK_MODEL` | 분석 실행 — 후보 조항 순위를 다시 매길 때 |
| 4 | 가상 조항 생성 (HyDE) | `OPENAI_RERANK_MODEL` | 분석 실행 — 의미 검색 질의를 다듬을 때 |
| 5 | 적용범위 의미검색 | `OPENAI_RERANK_MODEL` | 품목 확정 — 사전에 없는 품목 |
| 6 | 적용범위 후보 거르기 | `OPENAI_RERANK_MODEL` | 품목 확정 — 원문검색이 둘 이상 물어 왔을 때 |
| 7 | 품목 기준 제안 | `OPENAI_RERANK_MODEL` | 용어 사전 채우기 |
| 8 | GPC 계위 검증 | `OPENAI_RERANK_MODEL` | 품목분류를 붙일 때 |
| 9 | 검색어(별칭) 생성 | `OPENAI_RERANK_MODEL` | 검색어 사전 — 「AI로 검색어 더 만들기」 |
| 10 | 법정 품목 → 기준 잇기 | `OPENAI_RERANK_MODEL` | 대응표를 만들 때 |
| 11 | 임베딩 | `OPENAI_EMBEDDING_MODEL` | 조항·사건·적용범위를 뜻으로 견주려고 |

모델명을 코드에 박지 않고 환경변수로 두는 이유는, 모델이 바뀌면 결과도 바뀌기 때문이다. 무엇으로 만든 결과인지 나중에 알 수 있도록 **모델명을 결과와 함께 저장한다**(`clause_tag.tagging_model`, `clause.embedding_model`, `match_run.rerank_model`).

## 2. 답을 정해진 모양으로 받는다 (Structured Outputs)

열 곳 모두 자유 서술로 받지 않는다. 스키마를 주고 `strict: true`로 강제한다(`src/lib/llm/client.ts`).

이것이 막아 주는 것이 셋이다.

| 무엇을 막나 | 어떻게 |
| --- | --- |
| 형식 오류 | 스키마가 강제되므로 파싱이 깨지지 않는다 |
| **없는 값 창작** | 고를 대상을 `enum`으로 못박는다 — 존재하지 않는 기준 id나 코드북에 없는 코드를 만들어 낼 수 없다 |
| 근거 누락 | 근거 필드를 `required`로 둔다 — 답만 쓰고 근거를 빠뜨릴 수 없다 |

가운데가 특히 중요하다. 이 체계에서 가장 나쁜 고장은 **그럴듯한 오답**이다. 담당자가 검수해도 걸러내기 어렵기 때문이다. 그래서 「기준 후보 12종 중 하나를 고르거나 NONE」처럼 **고를 수 있는 것 자체를 좁혀** 놓는다.

### 자리별 감사 (2026-09-08 전수 점검)

| 자리 | 스키마 | 고를 대상을 못박았나 | 근거 필드 |
| --- | --- | --- | --- |
| 코드 부여 | `hazard_tagging` | 코드북의 HF·DT 코드 전체를 enum 으로 | `evidence_span` (원문 인용, 필수) |
| 사진 분석 | `photo_analysis` | 쪽 번호를 실제 첨부 쪽의 enum 으로 **(2026-09-08에 추가)** | `description` · `hazard_note` |
| 조항 재채점 | `rerank_scores` | 후보 조항 id 를 enum 으로 | `reason` |
| 가상 조항 (HyDE) | `hypothetical_clause` | 없음 — 지어내는 것이 목적이라 고정할 대상이 없다 | 지어낸 문단 자체 |
| 적용범위 의미검색 | `scope_verification` | 후보 기준 id + NONE | `reasoning` |
| 적용범위 후보 거르기 | `scope_filter` | 후보 기준 id (빈 배열 허용) | `reasoning` |
| 품목 기준 제안 | `scope_suggestion` | 기준 id 를 enum 으로 **(2026-09-08에 고침)** | `reason` · `confidence` |
| GPC 계위 검증 | `gpc_verification` | Brick·Class·Family·Segment 코드 + NONE | `reasoning` |
| 검색어 생성 | `item_aliases` | 대상 품목명을 enum 으로 **(2026-09-08에 고침)** · 검색어 자체는 고정 불가 | `note` |
| 법정 품목 → 기준 잇기 | `taxonomy_standard_links` | 후보 기준 id + NONE | `reasoning` · `confidence_score` |

**2026-09-08에 고친 것 셋.** 점검해 보니 열 자리 중 셋이 「프롬프트로 부탁하고, 어긋나면 코드에서 버리는」 방식이었다.

- **품목 기준 제안**은 기준 이름을 자유 문자열로 받아, 목록에 없는 이름이면 코드가 조용히 버렸다. 이름을 한 글자만 다르게 적어도 그 제안이 통째로 사라지는데 **버린 건수를 아무도 세지 않았다.** id enum 으로 바꾸고, 그래도 어긋나면 몇 건을 버렸는지 로그로 남긴다.
- **검색어 생성**도 대상 품목명이 자유 문자열이었다. 같은 이유로 enum 으로 고정했다.
- **사진 분석**은 쪽 번호를 정수면 무엇이든 받았다. 모델이 없는 쪽을 적으면 사진 설명이 엉뚱한 쪽에 붙는데, 사람이 사진과 대조하지 않는 한 드러나지 않는다.

「프롬프트로 부탁한다」와 「스키마가 못 하게 만든다」는 다르다. 앞은 대체로 지켜지고, 뒤는 항상 지켜진다. 이 체계는 뒤쪽만 믿는다.

**확신도(confidence)에는 스키마로 범위를 걸 수 없다.** OpenAI 구조화 출력이 `minimum`·`maximum` 을 지원하지 않기 때문이다. 그래서 받는 쪽에서 0~1 로 자른다. 애초에 자기보고 확신도는 실제 정확도와 어긋나는 경향이 있어(v0.7 §5.2.3) 승격 판단에는 쓰지 않고, 반복 호출의 일치도를 쓴다.

## 3. 판단 근거를 반드시 DB에 남긴다

답만 저장하면 검수는 그저 AI를 믿는 일이 된다. 담당자가 확정·반려를 판단하려면 **왜 그렇게 봤는지**가 함께 있어야 한다.

| 무엇을 묻나 | 근거 필드 | 어디에 남나 | 화면에서 보이나 |
| --- | --- | --- | --- |
| 코드 부여 | `evidence_span` (필수) | `case_tag` · `clause_tag` | 보인다 — 원문의 어느 구간인지 |
| 사진 분석 | `description` · `hazard_note` | `source_file.photo_analysis` (JSON) | 보인다 (`/accidents`) |
| 조항 재채점 | `reason` | `match_result.rerank_reason` | 보인다 — 후보마다 한 줄 |
| 적용범위 의미검색 | `reasoning` | `scope_term.evidence` · `case_event.scope_evidence` | 보인다 |
| 적용범위 후보 거르기 | `reasoning` | `case_event.scope_evidence` | 보인다 |
| 품목 기준 제안 | `reason` | `scope_term.evidence` | 보인다 (`/terms`) |
| GPC 계위 검증 | `reasoning` | `standard.gpc_verification` (JSON) | 일부 |
| 법정 품목 → 기준 잇기 | `reasoning` | `taxonomy_standard.evidence` | 보인다 (`/keywords`) |
| 가상 조항 생성 (HyDE) | 지어낸 문단 자체 | `match_run.hyde_text` | **아직 안 보인다** |

`evidence_span`은 **원문에서 그대로 인용한 구간**이어야 한다. 요약을 쓰면 원문에 없는 원인을 지어낼 여지가 생기므로, 스키마에서 필수로 두어 구조로 막는다.

### HyDE는 저장은 하되 보여 줄 때 조심한다

HyDE는 사고 서술로 「답에 해당할 법한 조항」을 지어내 의미 검색의 질의로 쓴다. 즉 **어떤 조항이 후보로 떠오르는지를 바꾼다**(재현율 23.8% → 25.2%). 그래서 되짚을 수 있어야 하고, 2026-09-07부터 `match_run.hyde_text`에 남긴다.

**다만 그 문단은 기준 원문이 아니다.** 화면에 그대로 내보내면 담당자가 실제 조항으로 오해한다. 보여 줄 자리를 만들 때는 「AI가 지어낸 검색용 문장」임을 반드시 밝혀야 한다.

## 4. 비용 보기

전용 화면 **[🤖 AI 사용과 비용](/llm)** 에서 본다 — 부르는 자리 열한 곳의 모델·스키마·근거 저장 위치, 용도별·모델별 비용, 날짜별 추이, 지금 쓰고 있는 단가, 최근 호출 스무 건이 있다. 운영 화면에는 이상 여부만 요약으로 남겼다(2026-09-08).

운영과 떼어 놓은 이유는 성격이 다르기 때문이다. 운영은 「지금 제대로 돌고 있는가」를 보는 자리이고, AI는 「무엇을 물어보고 있고 얼마가 드는가」를 **관리하는** 자리다. 한 절에 눌러 담으면 표 하나로 줄어들어 「어디에 어떤 모델을 쓰나」에 답할 수 없다.

기록은 `llm_call` 표에 쌓인다(052). 호출 한 건마다 용도·모델·토큰·성공 여부를 남기며, **실패한 호출도 남긴다** — 입력 토큰은 이미 나갔으므로 성공만 세면 실제 지출과 어긋난다.

054에서 두 가지를 더 남기기 시작했다. **캐시 적중 토큰**(`cached_tokens`)과 **무엇을 처리하다 부른 것인지**(`case_id`·`standard_id`)다. 뒤엣것은 052가 칸만 만들어 두고 아무도 채우지 않아 계속 비어 있었다 — 「이 사건 한 건 분석에 얼마 들었나」에 답하려고 만든 칸이다.

### 단가는 환경변수로 넣는다

표에는 **토큰만** 저장하고 돈 환산은 화면이 한다. 모델 단가는 바뀌고, 코드에 박아 두면 어느 시점 값인지 알 수 없게 되기 때문이다.

2026-09-08에 `developers.openai.com/api/docs/pricing`에서 확인한 값이다(100만 토큰당 USD).

| 모델 | 입력 | 캐시된 입력 | 출력 | 긴 문맥 입력 | 긴 문맥 캐시 | 긴 문맥 출력 |
| --- | --- | --- | --- | --- | --- | --- |
| `gpt-5.6-sol` | $4.00 | $0.40 | $20.00 | $8.00 | $0.80 | $30.00 |
| `gpt-5.6-terra` | $2.00 | $0.20 | $12.00 | $4.00 | $0.40 | $18.00 |
| `gpt-5.6-luna` | $0.20 | $0.02 | $1.20 | $0.40 | $0.04 | $1.80 |
| `text-embedding-3-large` | $0.13 | — | — | (구간 없음) | — | — |

```bash
# .env.local
LLM_PRICES={"gpt-5.6-terra":{"input":2.00,"cachedInput":0.20,"output":12.00,"inputLong":4.00,"cachedInputLong":0.40,"outputLong":18.00},"gpt-5.6-luna":{"input":0.20,"cachedInput":0.02,"output":1.20,"inputLong":0.40,"cachedInputLong":0.04,"outputLong":1.80},"text-embedding-3-large":{"input":0.13}}
```

**캐시된 입력은 일반 입력의 1/10이다.** 같은 프롬프트 앞부분을 다시 보내면 그만큼 싸게 청구된다. 이 체계는 입력이 출력의 스무 배가 넘으므로, 적중이 걸리면 금액이 크게 달라진다.

**다만 지금은 적중률이 0%다**(2026-09-08 실측, 호출 926건 · 입력 1,825,769토큰). 적중은 프롬프트의 **앞부분이 글자 그대로 같을 때**만 걸리는데, 우리 프롬프트는 품목명·사고 서술처럼 매번 다른 값이 앞쪽에 온다. 그래서 이 숫자는 「캐시가 고장났다」가 아니라 **「아직 캐시가 걸릴 모양으로 짜지 않았다」**는 뜻이다.

줄이려면 프롬프트 순서를 바꿔야 한다 — 코드북 enum 목록이나 후보 기준의 적용범위 원문처럼 호출마다 똑같이 나가는 덩어리를 **앞으로** 보내고, 매번 달라지는 값을 뒤로 미는 것이다. 그 전에 적중 토큰을 기록해 두어야 고친 효과를 숫자로 볼 수 있다. 기록이 먼저인 이유가 그것이다.

`.env.local`에 이 값이 아예 없으면 화면은 모든 금액을 「단가 미등록」으로 표시한다. 실제로 그렇게 되어 있었다(2026-09-08에 채웠다) — 0으로 세지 않는 설계 덕분에 「비용이 0인 것」과 「단가를 모르는 것」이 구별됐다.

**금액이 한 숫자가 아니라 범위로 나오는 이유** — 생성 모델은 문맥 길이에 따라 단가가 갈리는데, **어느 길이부터 「긴 문맥」인지가 단가표에 적혀 있지 않다.** 낮은 쪽만 쓰면 금액이 실제보다 적게 보이고 높은 쪽만 쓰면 부풀려지므로, 둘 다 계산해 `$1.30~$2.47`처럼 범위로 보여 준다. 정확한 한 숫자를 지어내는 것보다 「이 사이」라고 말하는 편이 정직하다. 임베딩은 구간이 없어 한 숫자로 나온다.

**단가가 등록되지 않은 모델은 금액을 계산하지 않고 「단가 미등록」으로 표시한다.** 0으로 세지 않는 이유는, 모르는 것을 0으로 적으면 비용이 실제보다 적어 보이고 담당자가 「얼마 안 드네」라고 잘못 판단하기 때문이다.

단가는 바뀐다. 바뀌면 `.env.local`과 위 표를 함께 고치고 확인한 날짜를 남긴다.

### 기록이 드러낸 것

기록을 붙이자마자 두 가지가 숫자로 보였다.

**임베딩 낭비가 사라진 것이 확인됐다.** 적용범위 의미검색이 저장된 임베딩을 두고도 매번 기준 73종을 다시 임베딩하고 있었는데(라운드 54에서 수정), 고친 뒤 실측하니 호출당 **375토큰**이다. 고치기 전이라면 기준 73종의 적용범위(약 28,000자)를 매번 보냈을 것이므로 1만 토큰이 넘는다.

**어느 단계가 비싼지도 바로 드러났다.** 리콜 재확정을 돌리는 동안 잰 값이다.

```
적용범위 후보 거르기   150회   입력 317,311   출력 14,007   $0.80~$1.52
적용범위 의미검색       58회   입력 199,818   출력  8,072   $0.50~$0.94
임베딩                 58회   입력  21,750   출력      0   $0.01 미만
```

입력 토큰이 출력의 20배가 넘는다. 후보 기준의 적용범위 원문을 프롬프트에 통째로 넣기 때문이다. 값을 줄이고 싶다면 출력이 아니라 **넣는 원문의 길이**를 손봐야 한다는 뜻이다.

## 5. 화면의 🤖 표시와 메뉴 묶음

왼쪽 메뉴의 🤖는 **그 화면에서 AI가 관여한다**는 뜻이다. 장식이 아니라 「결과는 후보이고 확정은 사람이 한다」는 표시다. 뜻을 메뉴 아래에 적어 두고 AI 화면으로 링크한다 — 표시만 있고 뜻이 어디에도 없으면 장식으로 읽힌다.

| 묶음 | 화면 | 🤖 | 무엇에 쓰나 |
| --- | --- | --- | --- |
| 업무 흐름 | 1 안전기준 | 🤖 | 조항 코드 부여 · GPC 검증 |
| 업무 흐름 | 2 사고보고서 | 🤖 | 코드 부여 · 사진 분석 · 품목 확정 · 분석 실행 |
| 업무 흐름 | 3 리콜 | 🤖 | 코드 부여 · 품목 확정 · 분석 실행 |
| 산출물 | KC안전기준 개선 요인 | | 쌓인 것을 세기만 한다 |
| 사전 · 참고 | 품목 검색어 사전 | 🤖 | 검색어 생성 |
| 사전 · 참고 | 품목 용어 사전 | 🤖 | 품목 기준 제안 |
| 사전 · 참고 | 위해요인 코드 | | 참고 문서 |
| 시스템 | AI 사용과 비용 | 🤖 | 이 문서가 설명하는 화면 |
| 시스템 | 운영 | | 상태·알림·접속 관리 |

메뉴를 네 묶음으로 나눈 것은 2026-09-08이다. 그전에는 번호 없는 다섯 개가 한 줄로 이어져 있어, 산출물인 「KC안전기준 개선 요인」과 시스템 화면인 「운영」이 같은 무게로 보였다.

## 6. 모델을 바꿀 때

- **임베딩 모델은 함부로 못 바꾼다.** 차원이 스키마(`vector(1536)`)에 박혀 있고, 바꾸면 기존 임베딩과 견줄 수 없다. DB 컬럼·검색 함수·전량 재생성을 담은 마이그레이션이 함께 필요하다.
- 생성 모델은 환경변수만 바꾸면 되지만, **바꾸기 전후로 채점을 돌려 견준다**(`npm run eval`, `npm run link:eval`). 이 저장소는 "좋아 보인다"가 아니라 숫자로 판정해 왔다.
- 바꾼 뒤 옛 모델로 만든 결과가 DB에 남아 섞인다. 모델명이 함께 저장되므로 어느 판으로 만든 것인지는 되짚을 수 있다.
