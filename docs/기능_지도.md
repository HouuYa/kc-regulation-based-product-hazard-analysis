# 기능 지도

## 이 문서를 언제 읽는가

**새 기능·화면·배치·스크립트를 만들거나 고치기 전에 읽는다.** 이 저장소에는 이미 만들어 둔 공유 로직이 많다. 2026-10-07에 한 세션이 「품목 지정」 기능을 새로 짜다가, 이미 `src/lib/gpc/classify.ts`(품목분류 공유 파이프라인)와 `src/lib/gpc/domestic.ts`의 원칙 「브릭만으로 기준을 고르지 않는다」가 있다는 것을 뒤늦게 알았다. 이 표는 그런 일을 막으려고 둔다. 어느 컴퓨터, 어느 세션에서든 이 파일 하나로 「이 개념은 어디 사는가」를 먼저 찾는다.

**구현이 바뀌면 같은 커밋에서 이 표도 고친다.** 담당 파일이 옮겨졌거나, 새 테이블·스크립트·화면이 생겼거나, 지켜야 할 원칙이 바뀌었으면 해당 줄을 고친다. 「지금 채움 상태」 칸은 실측 날짜를 함께 적는다. 숫자는 검수와 배치가 돌면 달라지므로, 날짜 없는 숫자는 옛 숫자인지 알 수 없다(`docs/wiki/색인.md`의 출처 규칙과 같다).

이 문서는 「어디에 있나」를 다룬다. 「왜 그런 순서로 도나」는 `docs/전체_프로세스와_용어.md`, 표의 칸 뜻은 `docs/스키마.md`, 법령·제도와 업무 원자료는 `docs/wiki/색인.md`를 본다.

## 표 읽는 법

- **담당 코드**: 재사용할 로직은 `src/lib/`에 있고 `scripts/`는 인자 파싱과 출력만 한다(CLAUDE.md §9). 새로 만들기 전에 이 칸의 파일 머리 주석부터 읽는다.
- **화면**: 2026-10-07 화면 재구성 뒤의 주소다. 옛 주소(`/ops`, `/llm`, `/insights`, `/keywords`, `/terms`, `/accidents/status`, `/recalls/status`, `/analysis/[caseId]/insight`)는 새 자리로 넘겨준다.
- **실행 스크립트**: `npm run …` 이름이다. 「cron」은 DB 안 pg_cron이 도는 정기 작업 이름이다.
- **지금 채움 상태**: 특별한 표시가 없으면 2026-10-07에 `npm run db:query -- "select …"`로 잰 값이다.

## 자주 헷갈리는 것

**「품목」이라 부르는 것이 셋이다 — 서로 다르다.**

| | 등록 품목 `product_scope` | 법정 품목 `product_taxonomy` | GPC 브릭 `gpc_brick` |
| --- | --- | --- | --- |
| 무엇 | 어린이제품 부속서에서 뽑아 등록한 품목군 | 협회 「품목별 세분류 매칭 DB」의 법정 품목 계층(대분류 > 품목 > 세부품목) | GS1 국제 품목분류의 가장 작은 단위 |
| 몇 개 | 33종 | 2,148행 · 브릭 764종 | 5,318 |
| 기준과 잇는 다리 | `standard_applicability` 49줄 | `taxonomy_standard` 502건(미검수) | 직접 안 이음 — `product_taxonomy`를 거친다 |
| 고칠 수 있나 | 우리가 관리 | 협회 원본이라 고치지 않음 | GS1 판 그대로(`gpc:load`) |

`case_event.product_scope_id`가 비어 있다고 「품목 미확정」이 아니다. 다른 갈래(용어 사전·적용범위 검색 등)로 기준을 찾으면 `product_scope_id`는 비고 `scope_evidence`만 찬다. 해외 리콜에서 전자는 40건, 후자는 2,081건이다(`docs/전체_프로세스와_용어.md` 7장 「품목이 붙었다를 세는 칸이 둘이다」).

**Recall Hub의 `approved`는 이 체계 담당자의 검토가 아니다.** 해외 리콜 원본 시스템(별도 Supabase 프로젝트)의 관리자가 승인한 것이고, 우리는 그것만 받아 온다(`recall/source.ts`). 그래서 `recall_cache.approval_status`는 2,399건 전부 `approved`지만, 우리 쪽 사람이 한 일(국내 유통 확인·어린이제품 확정·품목 지정·조항 채택)은 거의 0건이다. 리콜 `case_tag`의 `approved` 8,460줄도 원본 관리자 값이다.

**리콜 GPC의 `gpc_source='OECD'`는 담당자 판단이고, 우리 관찰은 달랐다.** 원본의 `classification_method`가 전부 `ai_auto`였고 확신도가 붙어 있었으며 OECD 포털 주소가 0건이었다. 담당자 지시로 OECD 서열에 두되 관찰은 066 주석과 `recall/load.ts`에 남겨 두었다. 이 값을 의심할 일이 생기면 거기서 되짚는다.

**원본 GPC는 그대로 쓰고, 없을 때만 LLM을 부른다.** `classify.ts` 0단계(`from-registered.ts`)가 이 자리다. 원본 코드를 놔두고 제품명 몇 글자로 다시 추정하지 않는다(065에서 겪은 실수). 품목 판정도 같아서, 믿을 만한 출처(`needsReview()`가 거짓)의 브릭이 있으면 `resolveByGpcBrick()`을 먼저 본다.
**「품목이 정해졌다」를 칸 하나로 세지 않는다.** `product_scope_id`(등록 품목 33종)만 보면 해외 리콜 40건이지만, 수집 배치가 자동 판정한 `scope_evidence` 2,081건과 원본 GPC 1,939건이 따로 있다. 화면·홈·정책 현황판은 `src/lib/cases/classified.ts`의 `classifiedSql()` 하나로 센다. 라운드 83에서 등록 품목 칸만 보고 2,359건을 「직접 정하라」로 띄운 일이 있었다(CLAUDE.md §16). 사람은 검토만, LLM·배치가 재료를 최대한 차려 둔다는 원칙에 맞추려면 「이미 차려진 것」부터 세야 한다.

**브릭만으로 기준을 고르지 않는다.** 베개(브릭 10002225) 하나가 성인용이면 생활용품, 만 3세 미만이면 어린이제품 안전확인으로 갈린다. 속성(연령·재질)은 서류에 안 적힌 일이 많아 사람이 정한다(`domestic.ts`). 갈래가 하나일 때만 자동으로 쓰고, 갈리면 `child_product_check`나 품목 지정으로 사람에게 넘긴다.

**불량과 불법은 산출물이 다르다(CLAUDE.md §10).** 불량은 시험을 해야 아는 것이라 시험항목(`TEST_ITEM`)으로, 불법은 법령을 보면 판정되는 것이라 인증·표시 확인항목(`CERT_MARKING_CHECK`)으로 나간다. 표시사항이 KC안전기준 문서 안에 있더라도 그것을 안 지킨 것은 불법이다. 조항 쪽은 `clause_role`의 `REQUIREMENT`/`MARKING`이 이미 가른다. 판정 기준은 `docs/wiki/개념/법령제도/불법과_불량_판정기준.md`.

**병행 점검은 확정 태그와 기본 목록을 덮지 않는다(CLAUDE.md §13).** 추정 코드는 `second_opinion_finding`에만 산다. `case_tag`와 `match_run`/`match_result`에 쓰지 않으며(`second-opinion/run.ts` 머리 주석이 코드 리뷰 체크리스트다), 화면에서도 기본 목록 아래 별도 구역에 둔다.

**「검색」이 두 군데에서 일어난다.** 품목 판정의 적용범위 의미검색(`scope-semantic.ts`)과 조항 검색(`search/match.ts`)은 다른 장치다. 하이브리드·RRF·HyDE·재채점은 품목이 정해진 **뒤** 조항을 찾을 때만 쓴다.

**「사전」이 셋이다.** 용어 사전(`scope_term`, 품목명 → 기준), 검색어 사전(`item_keyword`, 일상어 → 법정 품목), 코드북(위해요인 코드)이다. 「사전 검수」라고 하면 앞의 둘이다.

## 만들기 전 점검 순서

새 기능·화면·배치·스크립트를 만들기 전에 이 순서로 확인한다. 앞 단계에서 이미 있는 것을 찾으면 거기서 멈추고 그것을 쓴다.

1. **`docs/wiki/색인.md`** — 업무 개념과 원자료가 이미 정리돼 있는지 본다. 제도·법령 해석은 추측하지 않는다(CLAUDE.md §10).
2. **이 문서** — 해당 개념의 담당 코드·테이블·원칙을 찾는다.
3. **해당 `src/lib/` 파일의 머리 주석** — 「왜 만들었나」「무엇을 하지 않나」가 적혀 있다. 원칙 대부분이 여기에 있다(예: `gpc/domestic.ts`, `second-opinion/run.ts`, `cases/resolve-scope.ts`의 갈래별 주석).
4. **`package.json`의 `scripts`** — 같은 일을 하는 `npm run …`이 이미 있는지 본다.
5. **테이블 grep** — `supabase/migrations/`와 `codebook/sql/`에서 테이블·칸 이름을 찾고, 그 칸을 쓰는 코드를 `src/`·`scripts/`에서 찾는다. 이미 칸이 있으면 새 칸을 만들지 않는다.
6. **실제 채움 수치 SQL** — `npm run db:query -- "select …"`(`scripts/db-query.ts`, SELECT/WITH만·읽기 전용 트랜잭션)로 지금 그 칸이 얼마나 차 있는지 잰다. 「기능이 있다」와 「데이터가 차 있다」는 다르다 — 예를 들어 `taxonomy_standard`는 502건이 있지만 확정 0건이라 품목 판정에는 아직 쓰이지 않는다.
