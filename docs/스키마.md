# 스키마 구조

DB는 두 스키마로 나뉜다. 행 수는 2026-09-05 실측이다.

```
codebook   위해요인·피해유형 코드의 정의        판(version)으로 관리
public     기준 원문 · 사건 · 태그 · 분석 이력   실제 업무 자료
```

나눈 이유는 **정의가 한 곳에만 있어야 공통 언어가 성립하기 때문**이다. 코드의 뜻이 여러 곳에 흩어지면 같은 코드를 두 사람이 다르게 쓰게 된다. 나중에 코드북을 별도 서비스로 떼어 내도 이용하는 쪽 호출부가 그대로이도록 조회 함수는 `public`에 둔다.

---

## 1. 코드북 — 코드의 정의

### 왜 모든 표의 키에 판번호가 들어가나

판번호 없이 지금 코드 목록만 주면, **과거에 붙인 태그가 어떤 정의로 붙었는지 되짚을 수 없다.** 코드북이 개정되면 뜻이 바뀐 코드가 생기는데, 그 사실을 모르면 옛 판으로 붙인 태그와 새 판으로 붙인 태그가 한 통에 섞인다. 그래서 코드 표의 키는 `(version_id, code)`다.

| 표 | 행 | 담는 것 |
|---|---|---|
| `version` | 1 | 코드북 개정 이력. `active`는 동시에 하나만 존재한다 |
| `hazard_factor` | 64 | **원인(HF)** 코드. M-SHELL 대분류·계위·상위코드·정의 |
| `damage_type` | 16 | **피해유형(DT)** 코드. 심각도 범위, EU Safety Gate 대응 |
| `code_keyword` | 117 | 코드에 딸린 검색 키워드 |
| `code_constraint` | 3 | 단독 사용 금지 규칙. 예를 들어 사용자 오용 코드는 설계·품질 결함 코드와 반드시 함께 쓴다 |

`hazard_factor.depth`가 2~4로 가변인 것은 실물이 그렇기 때문이다 — `HF.UNKNOWN`은 2단, `HF.M.DES`는 3단, `HF.H.ELEC.NPC`는 4단이다.

### 이번에 더하는 두 표

두 코드 축을 **잇는** 표다. 지금은 원인 목록과 피해 목록이 따로 있고 둘을 잇는 줄이 없다. 설계 근거는 [`04-1_결과에서_원인으로_가는_다리.md`](../04-1_결과에서_원인으로_가는_다리.md).

| 표 | 담는 것 |
|---|---|
| `hf_route` | 원인 코드마다 **무엇으로 확인하는가** — `TEST`(시험/불량) · `LEGAL`(법령/불법) · `GAP`(기준공백) · `OTHER` |
| `cause_bridge` | 피해유형 → 원인 후보. 근거 건수·신뢰도·리프트·표본 크기·계산 시각 |

`cause_bridge`를 뷰가 아니라 표로 굳히는 이유는 리콜 자료가 계속 쌓여 같은 질의라도 시점마다 답이 달라지기 때문이다. "그때 왜 이 후보를 냈나"를 되짚으려면 그 시점의 값이 남아 있어야 한다.

## 2. 기준 원문 — 무엇을 시험하는가

| 표 | 행 | 담는 것 |
|---|---|---|
| `standard` | 76 | 안전기준 한 종. **대분류·인증구분**·부속서 번호·적용범위 원문·**적용범위 임베딩**·GPC 대응 |
| `clause` | 13,501 | 조항 하나. 본문·계위 경로·검색용 텍스트·임베딩 |
| `clause_link` | 1,066 | 조항 사이 관계. **성능요건 → 시험방법**이 핵심이다 |
| `test_condition` | 351 | 조항이 정한 허용치. 값과 단위를 쪼개 둔다 |
| `clause_tag` | 15,319 | 조항의 HF·DT 코드와 검수 상태 |

### `standard.item_group` 과 `standard.cert_types` — 축이 둘이다 (058)

담당자 지적으로 2026-09-09에 나눈 칸이다. 그전에는 `cert_scheme` 한 칸에 대분류와 인증구분이 섞여 있었다 — 파일명에서 뽑는 칸이라 「안전확인 부속서 6(완구)」에서는 인증구분이, 「KC 60335-2-15」처럼 번호뿐인 파일에서는 대분류('전기용품')가 들어갔다. 축이 다른 값이 한 칸에 있으니 어느 쪽으로도 정렬하거나 셀 수 없었다.

| 칸 | 값 | 무엇에 붙나 |
|---|---|---|
| `item_group` | 전기용품 · 생활용품 · 어린이제품 · 기타 | 기준 하나에 하나 |
| `cert_types` | 안전인증 · 안전확인 · 공급자적합성확인 · 안전기준준수 · 안전성검사 | **배열** — 인증구분은 품목에 붙으므로 기준 하나가 여럿에 걸린다 |
| `item_group_source` · `cert_type_source` | TAXONOMY · SCHEME · NAME · FILENAME · MANUAL | 그 값을 무엇을 보고 정했는가 |

`cert_scheme` 은 지우지 않았다. 파일명이 무엇이라고 했는지의 기록이고 적재기가 아직 그 칸에 쓴다. 다만 **판단에는 쓰지 않는다.**

실측(2026-09-09) 전기용품 43 · 생활용품 17 · 어린이제품 16. 인증구분은 21종이 미상이고 모두 품목표 대응이 없는 전기용품 계열이다.

### 뷰 셋 — `standard_view` · `case_event_group` (057~059)

| 뷰 | 무엇을 주나 | 왜 뷰인가 |
|---|---|---|
| `standard_view` | 기준 + 대분류 + 인증구분 + **세부품목 목록** | 세부품목(`taxonomy_standard`)은 검수하며 계속 바뀐다. 복사해 두면 어긋난다 |
| `case_event_group` | 사건의 대분류 | 서류의 제품명 → 품목 용어 사전 → 기준의 대분류. 사전이 자라면 저절로 따라간다 |

`standard_view.sub_items` 가 「KC 60335-2-17 → 전기담요 및 매트, 전기침대」 같은 품목명의 출처다. 화면이 번호만 보여 주던 것을 이것으로 고쳤다 — 이름이 없던 게 아니라 화면이 두 칸(`item_name`·`title_ko`)만 읽고 있었다.

### `clause.clause_role` — 조항을 같은 자격으로 다루지 않는다

| 값 | 뜻 | 취급 |
|---|---|---|
| `REQUIREMENT` | 성능요건 | **태깅·검색 대상은 이것뿐이다** |
| `TEST_METHOD` | 시험방법 | 직접 검색하지 않고 `clause_link`로 도달한다 |
| `MARKING` | 표시·주의사항 | 시험이 아니라 **표시 의무**다. 불법 판단 쪽이다 |
| `SCOPE` `DEFINITION` `REFERENCE` `ANNEX` `FRAGMENT` | 적용범위·정의·인용·부록·표 | 요구하는 바가 없어 시험 후보가 될 수 없다 |

이 칸이 없을 때 실제로 오염이 있었다. *"가량이 벨트란 …장치를 말한다"* 는 용어의 정의에 원인·피해 코드가 일치도 1.0으로 붙었다. 정의문은 아무것도 요구하지 않으므로 시험 후보가 될 수 없는데, 코드가 붙으면 진짜 안전요건과 같은 자격으로 검색에 걸린다.

시험방법을 직접 검색하지 않는 이유는 문체가 다르기 때문이다. 사고 서술("불이 났다")과 시험방법 서술("시료를 30분간 유지한 뒤 측정한다")은 어휘가 겹치지 않는다. 성능요건이 걸리면 그 조항이 지목하는 시험방법을 따라가는 편이 훨씬 잘 맞는다.

## 3. 사건 — 무슨 일이 있었는가

사고보고서와 해외 리콜을 **한 표에 담는다.** 들어오는 경로는 다르지만 "제품 때문에 사람이 다쳤다"는 점에서 같은 것이고, 같은 표에 있어야 함께 셀 수 있다.

| 표 | 행 | 담는 것 |
|---|---|---|
| `source_file` | 72 | 올린 PDF 원본. 추출 텍스트·상태·막힌 사유 |
| `source_file_image` | 113 | PDF에서 뽑은 사진과 비전 분석 결과 |
| `case_event` | 2,370 | 사건 하나. `source_type`이 `ACCIDENT`/`RECALL_OVERSEAS` |
| `case_tag` | 8,251 | 사건의 HF·DT 코드, 근거 구간, 모델·판번호 |
| `recall_cache` | 2,299 | 외부 리콜 원자료와 국내 유통 확인 상태 |

`case_event.is_confirmed`가 따로 있는 이유는, **담당자가 원문을 눈으로 보기 전에는 분석 대상이 아니기 때문이다.** L0 추출이 표를 뭉갰는지는 사람이 봐야 안다.

`source_file.status`가 `error`인 건은 사건이 만들어지지 않는다. 개인정보가 발견되거나 스캔본이면 여기서 멈춘다 — 사건이 되면 코드화 단계에서 외부 LLM으로 나가기 때문이다.

## 4. 품목 — 어느 기준을 적용하는가

전 기준을 뒤지면 다른 제품의 시험이 섞인다. 그래서 **범위를 먼저 확정한 뒤** 검색한다.

| 표 | 행 | 담는 것 |
|---|---|---|
| `product_scope` | 33 | 품목군과 별칭 |
| `standard_applicability` | 65 | 품목군 → 적용 기준 |
| `scope_term` | 169 | 일상 용어 → 기준. "머리인두"처럼 담당자가 쓰는 말 |
| `scope_term_gpc` | 37 | 일상 용어 → GPC 브릭 |
| `gpc_brick` | 5,318 | GS1 국제 품목 분류와 임베딩 |
| `product_taxonomy` | 2,148 | **법정 품목 계층 ↔ GPC.** 협회 「품목별 세분류 매칭 DB」 원본 |
| `item_keyword` | 5,982 | **일상어 → 법정 품목.** 담당자 1,039 + AI 4,943 |
| `item_keyword_stopword` | 124 | 품목 매칭에서 뺄 말. 협회 「검색 제외어」 |
| `taxonomy_standard` | 187 | **법정 품목 → KC기준.** 적용범위를 뜻으로 견주어 이은 것 |

### 같은 물건을 다섯 군데서 다르게 부른다

이 표들이 왜 넷이나 되는지가 여기 있다.

```
사고보고서   "LED등기구"                         법정어 84%
법정 고시    "조명기기 > 일반조명기구 > LED등기구"    product_taxonomy
KC안전기준   "KC 60598-2-1"                     taxonomy_standard 가 잇는다
GPC 국제분류 "전구/튜브/발광 다이오드"              product_taxonomy 가 잇는다
해외 리콜    "체인 조명" · "토끼 나무 기차"          법정어와 6%만 일치 → item_keyword
```

품목 확정은 다섯 경로를 차례로 본다. 앞에서 찾으면 뒤는 보지 않는다.

```
① 용어 사전(scope_term)        품목명 → 기준. 담당자 확정분이 먼저다
② 검색어 사전(item_keyword)     일상어 → 법정 품목 → 기준
③ 품목명·별칭 일치
④ 적용범위 원문 검색
⑤ 적용범위 의미 검색
```

②가 쓰는 안전 조건이 셋이다 — **정확 일치만 · 충돌하는 말 제외 · 확정된 것만.** 부분 일치를 허용하면 "세척기"가 식기세척기까지 끌어오고, 실제로 검색어 5,982개 중 600개가 두 품목 이상에 걸쳐 있다.

### `taxonomy_standard.standard_id` 가 비어 있을 수 있다

"이을 기준을 못 찾았다"는 것도 담기 때문이다. 조항 쪽에서 "0건도 산출물"이라고 정한 것과 같은 규칙이다. 사유는 `evidence` 에 있고, 화면에서 담당자가 바로잡거나 **「적재해야 할 기준」 목록**으로 쓴다.

## 5. 분석 이력 — 무엇을 왜 제시했는가

| 표 | 행 | 담는 것 |
|---|---|---|
| `match_run` | 12 | 검색 실행 1회. **켠 갈래·가중치·질의한 코드·모델**을 모두 남긴다 |
| `match_result` | 220 | 후보 조항과 갈래별 등수, 재채점 점수와 사유 |
| `review_log` | 0 | 담당자의 채택·반려 이력 |
| `tagging_run` | 33 | 태깅 실행 이력. 프롬프트 해시까지 남긴다 |
| `clause_tag_review` | 0 | 조항 태그 검수 이력 |

`match_run`이 설정을 통째로 남기는 이유는 **재현 때문이다.** 같은 사건이라도 가중치가 다르면 결과가 달라진다. 무엇을 켜고 돌린 결과인지 남지 않으면 나중에 그 목록을 설명할 수 없다.

`match_run.rerank_status`가 따로 있는 것도 같은 이유다. 재채점 점수가 비어 있을 때 "리랭커가 죽었다"와 "리랭커가 후보를 다 낮게 봤다"는 전혀 다른 뜻인데, 화면에서 구별되지 않으면 담당자가 후자로 오해한다.

## 8. 마이그레이션 규칙

```
supabase/migrations/   본 체계  (001 ~ 044)
codebook/sql/          코드북    (001 ~ 002)
```

**이미 적용된 파일은 고치지 않는다.** 새 번호 파일을 더한다. `npm run db:push`로 적용하고, 적용 이력은 `schema_migration`에 해시와 함께 남는다.

새 함수를 만들면 `anon`·`authenticated` 실행 권한이 자동으로 열리므로(Supabase 기본 동작), 의도한 것이 아니면 반드시 `revoke`한다. 실제로 이 실수가 있었고 어드바이저로 발견했다.
