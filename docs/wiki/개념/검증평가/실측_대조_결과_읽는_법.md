# 실측 대조 결과 읽는 법

## 0. 이 문서의 출처

`docs/raw/분석/2026-09-05_시험항목_비교/` 안 세 파일(`건별_대조.csv`,
`건별_대조.txt`, `절_분포_대조.txt`)을 직접 열어 읽고,
`scripts/compare-testitems.ts`(이 폴더의 `건별_대조.*` 두 파일을 만드는
스크립트)와 대조해 정리했다. `절_분포_대조.txt`는 저장소 안 어떤 스크립트도
만들지 않는다 — 아래 §3에 그 사실과 뜻을 남긴다.

## 1. 무엇을 재는가 — 사람이 지목한 절 vs 시스템이 제시한 조항

`건별_대조.txt`는 사건마다 두 목록을 나란히 보여 준다.

- **[사람이 지목한 것]** — 정답지(`docs/raw/eval/answer-key.json`)에
  담당자가 적은 (기준, 조번호)를 실제 DB의 하위 조항까지 펼쳐서, 시스템이
  낸 후보 순위 안에 있으면 "찾음(몇 위)", 없으면 "못찾음"으로 표시한다.
- **[시스템이 제시한 상위 10]** — 같은 사건에 대해 검색 파이프라인
  (`searchCandidates()`, 리랭킹은 끈 상태 `useRerank: false`)이 실제로
  낸 순위 1~10위를 조항 본문 일부와 함께 보여 준다.

`건별_대조.csv`는 같은 데이터를 사건·접수번호·품목·사람이지목한기준·
사람이지목한절·시스템순위·시스템조항·판정 8개 열의 표로 옮긴 것이다 —
스프레드시트로 정렬·필터링할 때 쓴다.

## 2. 2026-09-05 실측 수치 — 스냅샷이다, 현재값이 아니다

`절_분포_대조.txt`가 요약한 그 시점의 숫자다.

```
대조 사건 47건
판정: {'못찾음': 99, '찾음': 38}
```

즉 정답으로 지목된 조항 137개(99+38) 중 38개(약 28%)만 시스템 상위
순위 안에서 찾아졌다. 사람이 가장 많이 지목한 절은 절 7(24회)·절
11(18회)·절 19(18회) 순이고, 시스템이 가장 많이 낸 절은 절 11(87회)·절
19(76회)·절 5(68회) 순이다 — 두 분포가 겹치는 절(11, 19)도 있지만 겹치지
않는 절(사람의 절 7 vs 시스템의 절 5·3)도 있다는 것을 이 대조가 보여준다.

**이 수치를 지금 이 체계의 정확도로 인용하면 안 된다.** 검색 로직·
품목 확정·기준 적재 범위가 이후 라운드에서 계속 바뀌었다(예: 라운드 10~12의
GPC 검증 단계 추가, 원인 다리 §8 등). 현재 정확도가 필요하면
`npm run eval`을 다시 돌리거나 `구현이력.md`의 최신 라운드에서 더 최근
실측을 찾아야 한다 — 이 스냅샷은 "그 시점에 무엇이 막혀 있었는지"를
되짚는 기록으로만 쓴다.

## 3. 폴더명은 자동 날짜 갱신이 아니라 하드코딩이다

`compare-testitems.ts`의 출력 경로는 상수로 고정돼 있다.

```ts
const OUT = join(import.meta.dirname, '..', 'docs', 'raw', '분석', '2026-09-05_시험항목_비교');
```

즉 **`npm run eval:compare`를 오늘 다시 돌려도 새 날짜 폴더가 자동으로
생기지 않는다** — `2026-09-05_시험항목_비교` 폴더를 그대로 다시 쓰고
덮어쓴다. 새 스냅샷을 날짜별로 남기고 싶으면 이 상수를 실행 전에 직접
오늘 날짜로 바꿔야 한다. 이 문서를 쓰며 실제 코드를 열어 보고서야 확인한
사실이라, 다음에 이 스크립트를 돌리는 사람이 같은 오해(자동으로 새
폴더가 생길 것이라는 짐작)를 하지 않도록 남긴다.

`절_분포_대조.txt`는 이 스크립트가 만드는 파일이 아니다 — 저장소 안
어떤 스크립트에도 그 파일명이 나오지 않는다. `건별_대조.csv`를 놓고 절
번호별로 집계한 **1회성 수작업(또는 그 자리에서 실행한 임시 분석)**의
결과로 보인다. 같은 분석을 다시 돌리는 방법이 스크립트로 남아 있지 않으므로,
재현하려면 `건별_대조.csv`를 절 번호 기준으로 다시 집계해야 한다.
