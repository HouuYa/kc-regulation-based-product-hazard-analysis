# 정답지 기반 정확도 평가

## 0. 이 문서의 출처

`scripts/eval.ts`·`scripts/build-answer-key.ts` 머리 주석과
`docs/raw/eval/answer-key.example.json`을 직접 읽고 정리했다. 두 스크립트의
주석이 이미 "v0.6 §5.8"·"v0.7 §0.2"를 인용하고 있어, 이 문서는 그 인용이
가리키는 설계 결정을 코드 옆에서 확인할 수 있게 모은 것이다. v0.7이라는
이름의 별도 파일은 없다 — `02_1차 보완 및 구현 설계서.md`가 v0.6
(`01_사전분석_...v0.6.md`)을 보완한 문서이고, 코드 주석은 그 보완 내용을
관례적으로 "v0.7"이라 부른다.

## 1. 정답지를 어디서 가져오는가 — v0.6과 v0.7이 갈리는 지점

**v0.6 §5.8**은 "정답지는 별도로 만들지 않는다. 담당자가 실제로 채택·반려한
기록(`review_log`)이 그대로 정답지가 된다"고 했다.

**v0.7 §0.2**는 이것을 **평가 설계 오류**로 지목했다. 시스템이 제시한
후보를 보고 담당자가 고른 기록은, 시스템이 애초에 제시하지 않은 조항을
정답에 포함할 수 없다. 재현율의 분모가 시스템 출력 자체에 의존하게 되므로
**재현율이 구조적으로 늘 부풀려진다.**

그래서 이 저장소는 두 경로를 모두 지원하되 기본은 v0.7을 따른다.

```
npm run eval -- --source expert   docs/raw/eval/answer-key.json (기본값)
npm run eval -- --source review   review_log (운영 로그. 사후 개선용, 정확도 근거로 쓰지 않음)
```

`review`로 낸 수치에는 경고가 함께 출력된다 — 위 부풀림 문제 때문에 두
경로의 수치를 나란히 놓고 "review가 더 낫다"고 읽으면 안 된다.

## 2. 정답지가 clause id가 아니라 (기준, 조번호, 부위)로 사건을 지목하는 이유

`answer-key.example.json`의 형식이다.

```json
{
  "cases": [
    {
      "caseId": 4,
      "note": "예시 — 유아용 의자가 옆으로 넘어져 유아가 떨어진 사고",
      "expected": [
        { "standard": "부속서 8(유아용 의자)", "marker": "4.3.3", "part": "제1부" }
      ]
    }
  ]
}
```

`clause.id`(데이터베이스 기본키)를 쓰지 않는다. **id는 기준을 재적재하면
바뀌지만, 조항번호(`marker`)는 기준이 개정되기 전까지 그대로**이기 때문이다.
정답지에 id를 넣으면 다음 재적재 때 정답지 전체가 무효가 된다. `standard`는
부분 일치로 찾으므로 "부속서 8"처럼 짧게 써도 된다.

이 지목 방식은 `build-answer-key.ts`가 만드는 정답지와도 같다 — 담당자
작성분(수기)과 엑셀 자동 추출분(아래 §3)이 같은 스키마를 쓴다.

## 3. 전문가 정답지의 두 원천 — 수기 작성과 엑셀 추출

**수기 작성**: 담당자가 시스템 결과를 보기 전에 `answer-key.example.json`을
복사해 "이 사고면 어느 조항의 시험을 의뢰하겠는가"를 직접 채운다.
`answer-key.json`은 실제 사건 정보를 담을 수 있어 커밋 대상이 아니다
(`.gitignore`).

**엑셀 자동 추출** (`scripts/build-answer-key.ts`, `npm run eval:build-key`):
`사고조사보고서/__사고조사 건별 결함조사 항목 목록화_전달용.xlsx`에서
정답지를 뽑는다. 이 엑셀이 정답지로 쓰일 수 있는 이유는 v0.7 §0.2의
지적을 피해 가기 때문이다 — 담당자가 사고조사 과정에서 "어느 조항의
시험을 의뢰하겠는가"를 이 저장소의 시스템과 **무관하게** 미리 적어 둔
것이라, review_log와 달리 시스템 출력에 의존하지 않는다. xlsx는
`build-answer-key.ts`가 zip+XML을 직접 파싱해 읽는다 — 이 파일 하나를
읽자고 xlsx 라이브러리를 들이지 않는다는 이 저장소의 일관된 선택이다.

## 4. 세 스크립트의 역할

| 스크립트 | npm 명령 | 하는 일 |
| --- | --- | --- |
| `scripts/eval.ts` | `npm run eval` | §5.8 정확도 비교표를 만든다 — ①코드만 → ①+②코드+키워드 → ①+②+③하이브리드 → +맥락결합 → +리랭킹 순으로 한 갈래씩 켜며 재현율·오탐률·상위k 정답포함률을 측정한다. `--source`로 정답지 원천을, `--case`로 한 사건만, `--k`로 상위 k건 기준을, `--no-llm`으로 리랭킹 행(비용이 드는 행)을 뺄 수 있다 |
| `scripts/build-answer-key.ts` | `npm run eval:build-key` | 위 엑셀에서 `docs/raw/eval/answer-key.json`을 만든다 |
| `scripts/compare-testitems.ts` | `npm run eval:compare` | 정답지의 시험항목과 시스템이 실제로 제시한 시험항목을 건별로 대조한다 |

## 5. 측정 방법론 자체의 유의점

`SECTION_POOL = 200`(절로 묶기 전에 훑는 후보 수)은 진단에서 "정답의
49%가 상위 20위 밖 200위 안에 있었다"는 실측을 근거로 정해졌다 — 후보
풀을 너무 좁히면 애초에 정답이 그 풀에 들어오지 못해, 뒤 단계(하이브리드·
리랭킹)를 아무리 잘 만들어도 재현율이 오르지 않는다.

"+ 원인 다리" 행은 다른 행처럼 갈래를 하나 더 켜는 것이 아니라 **입력
자체를 바꾼다**(`04-1_결과에서_원인으로_가는_다리.md` §8) — 원인이
미상인 사건에 추정 원인을 얹어 같은 하이브리드 구성으로 다시 돌린다.
다리를 켠 행과 끈 행이 나란히 찍혀야 그 효과를 그 자리에서 판정할 수
있다.
