# 해외 리콜 원본표와 수집 경로

## 0. 이 문서의 출처

`docs/raw/해외리콜수집/recalls table schema.txt`(Recall Hub 원본 표 DDL)와
`src/lib/recall/source.ts`·`load.ts` 머리 주석을 직접 대조해 정리했다.
두 코드 파일의 주석이 이미 실측 근거(건수·날짜)를 남기고 있어, 이 문서는
그것을 한곳에 모으고 원본 표 구조와 나란히 보여 주는 역할이다.

## 1. 경로가 한 번 바뀌었다 — REST API에서 원본 표 직접 조회로

**2026-09-02 이전**: Recall Hub가 제공하는 얇은 REST API를 불렀다(16개
필드만 내려주는 요약본, 코드에서는 `hub.ts`였다).

**2026-09-02부터**: 원본 표(`recalls`)를 담당자 Supabase 프로젝트에 직접
조회한다(`src/lib/recall/source.ts`). `hub.ts`는 폐기됐다 — 이 저장소에
더 이상 존재하지 않는다.

바꾼 이유는 `source.ts` 머리 주석에 있다. 실물 확인(2026-09-02, project
`xicivtmjfkpuehgsieex`, 표 `recalls`) 결과 approved 2,252건은
`hazard_factor_code`·`damage_type_primary`·`iso5665_severity`가 **결측
없이** 채워져 있었다 — 담당자가 검토·분류까지 마친 값이다. 16개 필드짜리
요약 API로는 이 값을 받을 수 없었으므로, 원본 표를 직접 봐야 우리가 다시
AI로 태깅하지 않아도 된다.

## 2. 원본 표는 90여 칼럼, 우리는 25개만 타입으로 승격한다

원본 표(`recalls table schema.txt`)의 실제 칼럼 수는 90개에 가깝다 —
원문/번역 쌍(`product_name`/`product_name_original` 식으로 12개 필드가
번역 전후 두 벌씩), 이미지 5장·PDF 3장, `raw_data jsonb`, 업데이트 이력
(`update_history jsonb`), 그리고 검색용 `search_vector`(생성 컬럼)까지
포함한다.

`source.ts`의 `SourceRecall` 인터페이스는 이 중 **약 25개만 명시적 타입**으로
승격한다(id·source·guid·제품명·위해 서술·HF-DT 코드·승인 상태·품목분류
코드 등, 실제 이 저장소가 쓰는 값 위주). 나머지는 `[key: string]: unknown`
한 줄로 통째로 통과시킨다 — 90여 칼럼을 전부 타입으로 옮겨 적는 대신,
`load.ts`가 원본을 통째로 `recall_cache`에 보관해 두고(§7.1 원본층)
필요해지면 그때 타입을 늘리는 쪽을 택했다.

## 3. 승인과 관리대상은 서로 다른 칸이다 — 실측으로 확인된 함정

Recall Hub 관리자 화면에는 「승인」과 「관리 대상」이 **서로 다른 칸**으로
있다. 코드에서는 각각 `approval_status`(승인/반려 배지)와
`korea_relevance`(켜고 끄는 토글)다. 이름만 봐서는 관리 대상 여부를 알 수
없어 혼동이 반복됐고, 2026-09-07에 실물로 세어 근거를 남겼다.

| 승인 상태 | 관리대상 | 건수 |
| --- | --- | --- |
| 승인 | O | 2,336건 ← 우리가 받아 오는 것 |
| 승인 | X | 0건 |
| 반려 | O | 4건 ← 두 칸이 따로 움직인다는 증거 |
| 반려 | X | 2,634건 |
| 대기 | X | 5건 |

「승인이면서 관리대상 아님」은 0건이라 두 조건이 겹쳐 보이지만, **반려인데
관리대상이 켜진 4건**이 있다. 관리대상만으로 거르면 이 4건이 섞여
들어오므로 `fetchApprovedRecalls()`는 `approval_status='approved'`와
`korea_relevance=true`를 **AND로 함께** 건다.

## 4. 원본이 이미 GPC 코드를 갖고 있다 — 읽지 않고 있었다

원본 표의 `classification_code`·`classification_method`·
`classification_confidence`는 원본 시스템이 이미 붙인 품목분류 코드다.
실측(2026-09-09, 승인·관리대상 2,356건) 중 1,904건(81%)에 코드가 있고,
348종 중 341종은 브릭이며 나머지는 클래스·패밀리였다 — OECD 등록 규약대로
좁힌 계위까지만 채운 값이다. 이 저장소는 라운드 65에서야 이 값을 읽도록
고쳤다(그전까지는 이 칸을 무시하고 AI로 다시 붙이고 있었다). 자세한 내용은
[OECD_GPC_부여_워크플로.md](OECD_GPC_부여_워크플로.md)와
[표준제품분류체계_K-GPC.md](../GPC/표준제품분류체계_K-GPC.md) §5 참고.

지금 `classification_method`는 전부 `'ai_auto'`다 — 등록국이 OECD 포털에
신고한 값이 아니라 원본 시스템이 자동으로 붙인 값이라는 뜻이다. 등록국
신고 코드가 별도로 오면 그때 `method`로 갈릴 수 있게 `provenance.ts`가
이미 그 구분을 갖고 있다.

## 5. 이미 발견된 함정 — 비밀값 스캐너가 오탐한 사례

`RECALL_SOURCE_SUPABASE_URL`(원본 프로젝트 주소)이 비밀값 스캐너에
80곳 넘게 걸린 적이 있다. 실제로 열어 보니 전부
`.../storage/v1/object/public/recall-images/...` 형태의 **공개(public)
이미지 스토리지 주소**였다 — 리콜 사진 URL이 우연히 이 프로젝트 호스트명을
포함하고 있을 뿐, 접근 권한이 있는 키(`RECALL_SOURCE_SUPABASE_SECRET_KEY`)와는
무관했다. 이 저장소의 개인정보·비밀값 탐지 원칙(CLAUDE.md §7 — 오탐이
생기면 정규식을 헐겁게 풀지 않고 더 정밀한 조건을 추가한다)과 같은
결의 사례다.

| 명령줄 진입점 (인자 해석·출력만) | `scripts/load-recalls.ts` |
