# 리콜 이미지 분석 워크플로

## 0. 이 문서의 출처

협회 n8n 워크플로 원본(`이미지 처리 연습.json`)을 직접 읽고 정리했다. 이
저장소의 이식본은 `src/lib/gpc/describe-image.ts`이고, 그 파일 머리
주석이 이미 "협회 n8n 워크플로 「이미지 처리 연습」의 이식본"이라고 밝히고
있다.

## 1. 원본 워크플로가 하는 일

1. **사진 목록 조회** — 리콜 UID(`recallUid`)를 받아 Supabase Storage의
   `product-images` 버킷에서 그 UID로 시작하는 파일 목록을 가져온다
   (`Image List - Supabase`).
2. **다운로드** — 각 파일마다 서명 URL을 발급받아(`expiresIn: 3600`) 실제
   이미지를 내려받는다.
3. **비전 분석** — LangChain 에이전트가 이미지를 받아 영어로 된 긴 프롬프트로
   분석을 지시한다. 모델은 OpenAI(`gpt-5.1`)이고, Google Gemini
   (`gemini-2.0-flash`) 노드도 있지만 연결 그래프상 실제로는 쓰이지 않는다
   (`ai_languageModel` 연결이 빈 배열).
4. **결과 집계** — 여러 장을 분석한 결과를 `Aggregate` 노드로 모은다.

## 2. 원본 프롬프트가 요구하는 것

프롬프트(영어, 출력은 한국어로 강제)는 사진 한 장에서 4개 항목을 순서대로
뽑으라고 지시한다.

1. **제품 식별** — 제품명, 브랜드/제조사, 모델번호/제품코드
2. **제품 특성** — 주 용도, 대상 사용자(성인/어린이/전연령), 작동 방식(전기·
   전지·수동)
3. **법적 분류 정보** — 제품 카테고리, 세부 품목분류, 안전 관련 특징(전기
   사용·화학물질·삼킬 수 있는 작은 부품 등)
4. **물리적 특성** — 크기, 재질, 색상/디자인

출력은 `【PRODUCT IDENTIFICATION】` 같은 대괄호 머리글이 붙은 **자유 서술
텍스트**로 받고, 사진이 흐리거나 식별이 안 되면 "Image is unclear"·"Cannot
confirm" 같은 정해진 문구를 본문에 섞어 적으라고 지시한다. 목적은 명확히
적혀 있다 — "전기용품 및 생활용품 안전관리법이냐 어린이제품안전특별법이냐를
가리는 데 필요한 정보를 다음 단계에 제공하는 것."

## 3. 이식본이 바꾼 것 — 자유 서술을 구조화 출력으로

`describe-image.ts` 머리 주석이 직접 밝히는 두 가지 변경이다.

1. **머리글 파싱 대신 JSON 스키마.** 원본은 `【PRODUCT IDENTIFICATION】…`
   같은 머리글이 붙은 글을 받아 다음 노드에서 다시 파싱해야 한다 — 모델이
   머리글 하나를 빠뜨리면 그 뒤 파싱이 조용히 어긋난다. 이식본은
   `structuredVisionCall()`로 스키마(`product_name`·`brand`·`model_name`·
   `description`·`guessed_group`·`safety_note`·`unreadable_reason` 7개 필드)를
   강제한다.
2. **"모르면 모른다"를 별도 칸으로.** 원본도 "Cannot confirm"·"Image is
   unclear" 지침이 있지만 자유 서술 안에 섞여 들어가 다음 단계가 그 말을
   제품 설명으로 잘못 읽을 수 있다. 이식본은 `unreadable_reason`을 별도
   필드로 분리해 섞이지 않게 했다.

그 외에 원본의 4개 분석 항목(제품 식별·특성·법적 분류·물리적 특성)을 이식본
스키마의 7개 필드로 재구성했다 — `guessed_group`(전기용품/생활용품/
어린이제품/알 수 없음 enum)이 원본의 "법적 분류 정보" 항목을, `safety_note`가
"안전 관련 특징"을 그대로 잇는다. 원본이 영어 프롬프트에 "Respond in Korean
despite the English prompt"라고 적어 둔 것처럼, 이식본도 프롬프트와 출력
모두 한국어다.

## 4. 사진 수집 경로는 원본과 다르다 — 그리고 아직 안 이어져 있다

원본은 Supabase Storage에서 리콜 UID로 사진을 직접 찾는다(협회의 저장
경로가 이미 정해져 있다는 뜻). 이식본은 사진 수집 경로를 정하지 않았다 —
`describeProductImages()`는 `ProductImage[]`(base64 `dataUrl` 배열)를
그대로 받을 뿐, 어디서 그 배열을 만드는지는 호출부의 몫이다.

`describe-image.ts` 머리 주석이 밝히듯 **지금은 이 함수를 부르는 곳이
없다**(2026-09-09 기준). 담당자 요청이 "사진을 읽어 들이는 로직은 추후
사용 가능하므로 구현만"이었기 때문이다. 리콜 사진은 협회 저장소에 있고
이 저장소 쪽 수집 경로가 아직 정해지지 않았다 — 경로가 정해지면
`describeProductImages()`를 부르고 `assignGpcFromImages()`처럼 이어 붙이면
된다(이미 그 형태로 구현되어 있다).

## 5. 사고보고서 사진 분석과는 다른 모듈이다

이 저장소에는 사고보고서 첨부사진을 읽는 `src/lib/llm/vision.ts`도 있다.
목적이 다르다 — 그쪽은 여러 장이 섞인 보고서에서 "이건 증거 사진인가
기관 로고인가"부터 가리고 손상·탄 흔적 같은 위해 단서를 뽑는다. 여기
(`describe-image.ts`)는 사진이 제품 사진임이 이미 분명한 상태에서 "이
제품이 무엇인가"만 본다. 목적이 달라 프롬프트도 스키마도 다르므로
합치지 않았다.

## 6. 결과가 흘러가는 곳

`describeProductImages()`의 결과(`ProductImageDescription`)는
`src/lib/gpc/classify.ts`의 1단계 입력으로 들어간다 — 사진 판독 서술이
품목분류 질의문에 보태져 "의자"·"나선형 장난감" 같은 짧은 공고 제품명만으로
벡터 색인이 엉뚱한 브릭을 무는 것을 막는다.

| 하는 일 | 파일 |
| --- | --- |
| 사진 여러 장을 읽어 하나의 서술로 | `describeProductImages()` (`src/lib/gpc/describe-image.ts`) |
| 서술을 품목분류까지 이어 붙이는 헬퍼 | `assignGpcFromImages()` (같은 파일, 아직 부르는 곳 없음) |
| 사진 판독을 포함한 공통 진입점 | `src/lib/gpc/classify.ts` (`images` 입력) |
| 사고보고서 사진 분석(별도 목적) | `src/lib/llm/vision.ts` |
