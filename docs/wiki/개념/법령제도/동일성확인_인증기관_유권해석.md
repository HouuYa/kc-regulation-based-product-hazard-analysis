# 동일성확인 — 인증기관 유권해석

## 0. 이 문서의 출처

담당자가 2026-09-12 대화에서 직접 정정해 준 내용이다. 원자료 문서(`docs/raw/`)는
아직 없다 — 사고보고서를 다루는 병행 점검 계층(라운드 70, `CLAUDE.md` §13)을
만드는 중에, "동일성확인 결과"를 시스템이 어떤 무게로 다뤄야 하는지를 담당자가
바로잡아 준 것이 이 문서의 계기다. 관련 raw 문서가 들어오면 이 문서에 합친다.

## 1. 「동일성확인」이 무엇인가

사고조사보고서에 반복해서 나오는 「동일성확인 결과」는 **조사관의 관찰이나
의견이 아니다.** 사고 제품이 KC 인증 당시의 모델과 같은지 다른지를
**인증기관에 질의해 받는 유권해석**이다.

```
사고조사 담당자 → (질의) → 인증기관 → (유권해석: 동일함 / 상이함) → 보고서에 기재
```

그래서 보고서 원문의 "인증당시와 비교하여 전지 정격이 불일치함", "인증 당시와
주요 부품 상이 (PCB)" 같은 문장은 **이미 인증기관이 공식적으로 판정을 마친
결과**다. 조사관이 육안으로 다르다고 느낀 소감이 아니라, 인증 절차를 관장하는
기관이 "그 부품 변경은 인증받은 모델과 다르다"고 확정한 것이다.

## 2. 이것이 왜 중요한가 — 우리 체계의 신뢰도 등급에 영향을 준다

`불법과_불량_판정기준.md` §1의 구분을 다시 쓰면 이렇다.

| | 불량 | 불법 |
|---|---|---|
| 확인 | 시험을 해야 안다 | 법령을 보면 판정된다 |

「동일성확인 = 상이함」은 이 표의 오른쪽 칸에 속하는 판정이면서, **이미
확인이 끝난 판정**이다. 우리 시스템이 "부품이 다른 것 같다"고 추정한 것이
아니라, 인증기관이 이미 그렇게 결론 낸 것을 보고서에서 그대로 옮겨 오는
것뿐이다.

이 구분이 실무에 영향을 준다 — 병행 점검 계층(`src/lib/second-opinion/`)이
동일성 「상이함」을 근거로 `LEGAL_SIGNAL` 소견을 낼 때, 그 소견의 신뢰 등급은
"AI가 원문을 읽고 추정함"이 아니라 **"인증기관이 이미 유권해석한 사실을
그대로 인용함"**이다. 화면과 소견 문구에 이 차이를 분명히 적는다 — 담당자가
그 소견을 볼 때 "이건 이미 공식적으로 확정된 사실이구나"와 "이건 시스템이
지어낸 추정이구나"를 구분할 수 있어야 한다.

다만 **어떤 법령 위반으로 분류할지**(예: `HF.M.REG.ILLEGAL` 고의 위반인지
`HF.S.QC` 품질검수 미비인지)는 별개의 판단이라 여전히 담당자 확인이
필요하다 — 유권해석이 확정하는 것은 "부품이 다른가"이지 "그것이 고의적
불법인가"가 아니다. `second_opinion_finding.needs_expert_confirm`이 계속
`true`인 이유가 이것이다.

## 3. safetykorea 포털 조회 — 지금도 담당자가 직접 할 수 있다

사고조사 담당자는 `safetykorea.go.kr`(국가기술표준원 제품안전정보센터)
포털에서 인증번호로 인증 정보를 직접 조회할 수 있다. 인증 당시 등록된
모델명·주요 부품 목록 등을 여기서 확인한다. 지금은 이 조회가 사람이 포털에
직접 접속해서 하는 수작업이고, 이 저장소의 어떤 코드도 아직 이 포털을
연동하지 않는다.

## 4. 향후 계획 — SafetyKorea Open API 연동 (아직 미구현)

담당자가 밝힌 계획: safetykorea 포털의 인증정보 조회 기능이 **Open API로
제공될 예정**이고, 그것이 열리면 API 키를 `.env.local`에 등록해 인증번호
조회 기능을 이 저장소에 추가할 것이다.

**아직 하지 않은 것 — 착수 시점에 참고**
- API 키 발급·등록. `.env.example`에 템플릿 항목을 아직 추가하지 않았다
  (§7 원칙대로 실제 키는 `.env.local`에만, 값 없는 템플릿만 `.env.example`에).
- API 스펙(엔드포인트, 응답 필드) 확인. Open API가 실제로 열리면 이 문서에
  이어서 정리한다.
- 이 연동이 가능해지면 `case_investigation_item`의 `IDENTITY_CHECK` 항목을
  **보고서 원문에서 추출하는 것에 더해, 인증번호로 직접 조회해 대조하는
  두 번째 경로**를 만들 수 있다 — 보고서가 동일성확인 결과를 안 적어
  놓았거나(원인미상 케이스), 조사가 진행 중이라 아직 유권해석을 못 받은
  단계에서도 우리 쪽에서 먼저 인증 당시 부품 구성을 확인해 볼 수 있게
  된다는 뜻이다. 다만 이것은 Open API가 실제로 제공된 뒤에 설계한다 —
  지금 API 스펙을 모르는 채로 인터페이스를 앞서 만들지 않는다(CLAUDE.md
  §2 단순성 원칙).

## 5. 우리 체계·코드와의 연결

- `src/lib/second-opinion/extract.ts`의 `identity_check` 필드가 보고서
  원문에서 이 유권해석 결과(`동일함`/`상이함`/`확인불가`/`해당없음`)를
  뽑아 `case_investigation_item`(`item_type='IDENTITY_CHECK'`)에 저장한다.
  이 저장소 71건 전량 실측 기준 「상이함」 24건, 「동일함」 24건,
  「확인불가」 7건이다(`구현이력.md` 라운드 70).
- 2단계(`legal.ts`, 착수 예정)가 이 값을 `HF.S.QC`/`HF.M.REG.ILLEGAL`
  코드로 잇는다 — 코드 정의는 `codebook/제품_위해요인_분류체계_정립_PDR_v0_9_7.md`
  §5.2·§5.3.
- SafetyKorea Open API 연동은 착수되면 `src/lib/` 아래 새 모듈로 만들고
  (§9 원칙대로 스크립트는 얇게, 로직은 `src/lib/`에), 이 문서와
  `.env.example`을 함께 갱신한다.
