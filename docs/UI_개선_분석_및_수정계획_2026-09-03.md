# UI 개선 분석 및 수정 계획서

작성일: 2026-09-03  
범위: 공통 좌측 메뉴, 상세 화면의 우측 목차, `/ops` 운영 화면  
이번 단계: 현황 분석과 수정 계획만 확정하며, 화면 동작 코드는 아직 바꾸지 않음

## 1. 결론 요약

현재 UI는 각 화면의 본문은 읽을 수 있지만, 긴 화면을 다룰 때 현재 위치와 다른 화면으로 이동할 방법이 부족하다. 특히 운영 화면은 상태 확인, 즉시 실행, 이력, 설정이 한 줄로 길게 이어져 "지금 무엇을 먼저 해야 하는지"가 늦게 드러난다.

수정의 중심은 다음 세 가지다.

1. 데스크톱 좌측 메뉴를 페이지 본문과 분리해 항상 화면에 남긴다
2. 긴 상세 화면에 현재 읽는 제목을 표시하는 우측 고정 목차를 넣는다
3. 운영 화면을 "요약 → 확인 필요 → 실행 → 상세/설정" 순으로 다시 구성한다

## 2. 현황 및 원인

| 항목 | 현 상태 | 문제 원인 | 영향 |
| --- | --- | --- | --- |
| 좌측 메뉴 | `src/app/layout.tsx`에 `lg:sticky lg:top-0` 적용 | 고정이 `lg`(1024px 이상)에서만 활성화된다. 앱 창 폭이나 브라우저 확대 비율에 따라 일반 스크롤 메뉴가 된다. 또한 콘텐츠와 같은 flex 흐름 안의 sticky에 기대고 있어 레이아웃 변화에 취약하다 | 긴 목록에서 다른 메뉴로 가려면 맨 위로 이동해야 함 |
| 상세 페이지 탐색 | `/standards`, `/accidents`, `/recalls`, `/codebook`, `/ops`, 분석 상세에 제목은 있으나 앵커와 탐색 UI가 없음 | 공통 상세 레이아웃과 목차 컴포넌트가 없음 | 아래 내용을 읽은 뒤 위쪽의 상태·작업 영역으로 돌아가기 어려움 |
| 운영 화면 | 7개 섹션을 세로로 같은 무게로 나열 | 정상 상태, 예외, 비용이 드는 작업, 설정/이력이 한 흐름에 섞여 있음. "확인이 필요한 것"도 문제가 있을 때만 나타나므로 위치가 일정하지 않음 | 평상시 점검과 장애 대응의 우선순위가 즉시 보이지 않음 |
| 반응형 표 | 운영·목록 화면에 가로 열이 많은 grid 사용 | 좁은 화면에서 열의 최소 폭과 읽기 우선순위가 별도로 설계되지 않음 | 모바일/좁은 창에서 정보가 압축되거나 가로 읽기가 어려울 수 있음 |

### 확인한 코드 위치

- 공통 메뉴: `src/app/layout.tsx`
- 공통 화면 제목: `src/components/Panel.tsx`의 `PageHead`
- 운영 화면: `src/app/ops/page.tsx`
- 긴 목록 화면: `src/app/standards/page.tsx`, `src/app/accidents/page.tsx`, `src/app/recalls/page.tsx`, `src/app/codebook/page.tsx`
- 분석 상세: `src/app/analysis/[caseId]/page.tsx`

로컬 브라우저 자동화 연결은 이 작업 환경에서 사용할 수 없어 실제 스크롤 재현은 하지 못했다. 다만 위 원인은 소스에서 확인했으며, 구현 단계에서 데스크톱/태블릿/모바일 폭별로 다시 검증한다.

## 3. 수정 설계

### A. 좌측 메뉴: 독립된 데스크톱 레일

- `lg`에서만 고정하던 조건을 검토해, 실제 업무용 최소 폭에서 안정적으로 동작하는 데스크톱 기준으로 조정
- 데스크톱에서는 좌측 레일이 본문 흐름과 독립적으로 화면 높이를 차지하도록 변경. 메뉴 내부만 필요할 때 스크롤
- 본문에는 레일 폭을 명시적으로 확보해 메뉴와 겹치지 않도록 구성
- 작은 화면에서는 현재의 가로 메뉴 방식을 유지하되, 메뉴가 본문을 과도하게 차지하지 않게 유지
- 현재 경로를 시각적으로 표시해 사용자가 어느 화면에 있는지 알 수 있게 개선

권장 구현: 상위 컨테이너를 데스크톱 grid로 바꾸고, 레일은 화면 좌측에 고정하거나 grid 내부 sticky를 사용한다. 구현 전 두 방식 중 실제 브라우저에서 겹침·스크롤을 확인하고 더 단순한 방식을 택한다.

### B. 우측 목차: 제목, 현재 위치, 위로 이동

- 새 공통 컴포넌트(예: `PageToc`)를 만들고, 페이지가 제공한 제목 목록으로 우측 목차를 그림
- 각 주요 섹션 제목에 안정적인 `id`와 `scroll-margin-top`을 부여
- 데스크톱에서는 우측에 sticky 목차를 표시하고, 스크롤 위치에 맞는 현재 제목을 강조
- 목차 항목을 누르면 해당 섹션으로 이동하고 URL hash도 갱신
- 모바일/좁은 창에서는 우측 칼럼을 없애고, 제목 아래 접을 수 있는 `현재 페이지 목차`로 제공
- 목차 하단에 `맨 위로`를 둬 긴 페이지에서 시작 영역으로 즉시 돌아가게 함

현재 위치 강조에는 작은 클라이언트 컴포넌트와 `IntersectionObserver`만 사용한다. 데이터 조회와 기존 서버 페이지는 서버 컴포넌트로 유지한다.

적용 순서:

1. 운영 화면과 분석 상세처럼 섹션이 명확한 화면에 우선 적용
2. 안전기준·사고보고서·리콜·코드북에 적용
3. 제목이 실질적으로 하나뿐인 화면은 목차를 만들지 않음

### C. 운영 화면: "관리 대시보드"로 재구성

운영 화면은 단순히 카드 수를 늘리는 방향이 아니라, 담당자가 들어온 순간 판단해야 할 순서로 바꾼다.

| 영역 | 새 배치 | 목적 |
| --- | --- | --- |
| 상단 요약 | 정상/주의/문제 수와 마지막 갱신 시각 | 화면을 열자마자 오늘 조치가 필요한지 판단 |
| 우선 확인 | 보류 항목·자동 작업 실패를 항상 같은 위치에 표시. 없으면 `현재 확인할 문제 없음` | 예외가 있어도 위치가 흔들리지 않음 |
| 즉시 실행 | 일반 작업과 비용 발생 작업을 분리. 비용 작업에는 남은 건수·예상 비용·정지 방법을 한 묶음으로 표시 | 실수로 비용 작업을 시작할 위험 감소 |
| 운영 상세 | 자동 작업 목록, 최근 실행, 의미 검색 준비 현황 | 평시에는 접거나 아래에서 확인 |
| 알림 및 접속 | 알림 이력/시험 발송과 접속 설정을 `설정 및 연결` 그룹으로 분리 | 매일 보지 않는 설정이 핵심 상태를 밀어내지 않음 |

세부 원칙:

- 색만으로 상태를 구분하지 않고 상태 문구와 건수를 함께 표시
- 실패 내용은 기본적으로 한 줄 요약, 원문 오류는 필요할 때만 펼쳐서 표시
- 위험/비용 작업은 기본 행동 버튼과 시각적으로 분리
- 운영 화면 목차는 위 다섯 영역을 바로 이동할 수 있게 제공

## 4. 구현 작업 순서와 검증

1. 공통 페이지 골격 및 좌측 레일 변경
   - 대상: `src/app/layout.tsx`, `src/app/globals.css`
   - 검증: 1280px, 1024px, 768px, 375px 폭에서 본문을 끝까지 스크롤해 메뉴 위치·겹침·내부 스크롤 확인

2. 공통 우측 목차 컴포넌트 추가
   - 대상: 새 `src/components/PageToc.tsx`, 필요 시 공통 레이아웃 컴포넌트
   - 검증: 목차 이동, hash 주소, 현재 섹션 강조, `맨 위로`, 키보드 포커스, 모바일 접기 동작 확인

3. 페이지별 제목 앵커와 2단 레이아웃 적용
   - 대상: standards, accidents, recalls, codebook, ops, analysis 상세
   - 검증: 각 페이지의 모든 목차 항목이 실제 제목으로 이동하고, 데이터가 비어 있거나 연결 오류일 때 레이아웃이 깨지지 않는지 확인

4. 운영 화면 정보 구조와 표현 재편
   - 대상: `src/app/ops/page.tsx` 및 필요한 작은 표시 컴포넌트
   - 검증: 정상/주의/실패 데이터 조합에서 우선 확인 영역, 비용 작업 구분, 긴 오류 메시지의 가독성 확인

5. 회귀 점검
   - `npm run typecheck`
   - `npm run build`
   - 실제 브라우저에서 데스크톱·태블릿·모바일 스크롤 및 링크 확인

## 5. 완료 기준

- 데스크톱에서 본문 최하단까지 내려도 좌측 메뉴가 화면에 남아 있음
- 긴 대상 페이지에서 우측 목차가 보이고, 현재 읽는 제목이 표시됨
- 목차와 `맨 위로`로 페이지 상단/각 구역으로 한 번에 이동 가능
- 모바일에서는 목차와 메뉴가 본문을 가리지 않으며 가로 스크롤을 강요하지 않음
- 운영 화면에서 `확인 필요 여부`, `지금 할 수 있는 안전한 작업`, `비용 작업`, `상세 이력/설정`이 명확히 분리됨
- 타입 검사와 프로덕션 빌드 통과

## 6. 구현 전 결정이 필요한 범위

`운영` 화면의 데이터와 기능은 유지한다. 이번 계획의 기본안은 정보 구조와 표현만 재설계하는 것이다. 운영 화면에서 제거하거나 새로 추가할 업무 기능이 있다면 구현 착수 전에 별도 범위를 정한다.

## 7. 함께 고칠 UI 품질 항목

### A. 속도와 반응성

현재 목록은 이미 서버에서 페이지 단위로 가져오므로, 수천 건을 한 번에 그리는 문제는 피하고 있다. 다만 화면마다 여러 개의 독립 집계 쿼리와 목록 쿼리를 실행하며, 자동 새로고침도 사고·리콜 화면에서 20초마다 전체 페이지를 다시 연다. 다음을 개선한다.

| 개선 항목 | 방향 | 기대 효과 |
| --- | --- | --- |
| 초기 표시 | 제목·업무 흐름·기본 골격을 먼저 보여 주고, 집계/목록은 `Suspense` 경계로 늦게 채움 | DB 응답이 늦어도 빈 화면처럼 보이지 않음 |
| 자동 갱신 | 전체 페이지 갱신 대신 상태 숫자만 갱신하는 작은 경로를 검토 | 작성 중인 검색 조건과 펼친 원문이 불필요하게 초기화되지 않음 |
| 목록 정보 | 첫 화면에서는 핵심 열만, 부가 정보는 펼치기 또는 상세 화면으로 이동 | 렌더링·읽기 부담 감소 |
| 집계 쿼리 | 개요·안전기준·운영의 반복 집계를 뷰/RPC 또는 한 번의 집계 쿼리로 정리할지 측정 후 결정 | DB 왕복과 첫 화면 대기시간 감소 |
| 글꼴 | 외부 글꼴 실패 시에도 줄바꿈 폭이 크게 흔들리지 않도록 fallback과 `font-display` 점검 | 느린 네트워크에서 레이아웃 흔들림 감소 |

성능 최적화는 추측으로 하지 않는다. 구현 전후에 각 페이지의 서버 응답 시간, SQL 실행 계획, 초기 렌더 시점을 측정해 가장 느린 지점만 고친다.

### B. 말투와 문장 길이

현재 문구는 정책상 단정하지 않으려는 점이 좋지만, 설명이 길고 같은 배경 설명이 상태 카드·본문·도움말에 반복되는 곳이 있다. 화면에는 판단과 행동만 남기고, 이유와 예외는 `자세히`에 넣는다.

| 현재 경향 | 개선 원칙 | 예시 |
| --- | --- | --- |
| 한 문장에 원인·제약·정책을 모두 설명 | 첫 문장은 결과, 둘째 문장은 필요한 행동 | `품목 미확정 — 분석을 실행할 수 없습니다` → `품목을 정한 뒤 다시 실행하세요` |
| 시스템 용어를 쉬운 말로 풀되 반복 | 화면의 표준 용어를 정하고 처음 한 번만 보조 설명 | `의미 검색 준비`를 유지하고, 상세 설명에서만 “단어가 달라도…” 제공 |
| 경고 문단이 길게 이어짐 | 상태 + 영향 + 다음 행동의 3줄 형식 | `확인 필요 / 분석 결과가 완전하지 않을 수 있음 / 운영에서 준비 상태 확인` |
| 버튼 문구가 문장형 | 동사 중심의 짧은 명령형 | `원문을 확인했습니다 — 분석 대상으로` → `원문 확인 완료` |

금지 원칙은 유지한다. 후보를 법적 판단처럼 보이게 하는 표현, AI가 확정했다는 표현, 불필요하게 불안감을 주는 적색 경고는 쓰지 않는다.

### C. 정보 밀도와 접근성

- 상태 카드에는 `숫자 + 상태 + 다음 행동`만 표시하고 긴 설명은 도움말/상세로 이동
- 표의 숫자 열에는 제목·정렬 상태·단위를 항상 함께 표시하고, 작은 화면에서는 중요 열만 남김
- 링크·버튼·접기 요소의 포커스 표시와 클릭 영역을 키워 키보드·터치 조작을 보장
- 색상만으로 정상/주의/실패를 구분하지 않고 텍스트와 아이콘/상태명을 병기
- 페이지 갱신·분석 실행 중에는 진행 상태를 화면에 유지하고, 완료 후 바뀐 지점으로 초점을 이동
- `용어 풀이`는 모든 화면 마지막에 반복하기보다, 어려운 용어 옆의 짧은 도움말과 한 곳의 전체 용어집으로 정리 검토

## 8. 페이지별 업무 흐름 표기

각 페이지 제목 아래에 1줄짜리 `업무 흐름`을 공통 컴포넌트로 표시한다. 문단이 아니라 짧은 단계와 화살표를 쓰며, 현재 화면의 핵심 단계만 진하게 표시한다. 단계는 링크가 가능한 경우 해당 화면/구역으로 연결한다.

| 페이지 | 표시할 흐름 |
| --- | --- |
| 개요 | `준비 상태 확인 → 사고·리콜 확인 → 분석 결과 검토 → 담당자 판단 기록` |
| 안전기준 | `기준 적재 → 조항·시험 연결 확인 → 위해요인 코드 준비 → 분석에 사용` |
| 사고보고서 | `PDF 올리기 → 추출 원문 확인 → 분석 실행 → 후보 조항 검토·기록` |
| 리콜 | `리콜 수집 → 국내 유통 확인 → 분석 실행 → 후보 조항 검토·기록` |
| 분석 상세 | `사건 내용·품목 확인 → 관련 조항 후보 확인 → 근거·시험방법 검토 → 채택/반려 기록` |
| 위해요인 코드북 | `현재 판 확인 → 코드 뜻 조회 → 개정 영향 확인 → 필요한 범위만 재부여` |
| 운영 | `오늘 상태 확인 → 문제 확인 → 필요한 작업 실행 → 이력·알림 확인` |

표현 예시는 아래와 같다.

`PDF 올리기  →  원문 확인  →  분석 실행  →  후보 조항 검토  →  판단 기록`

구현 규칙:

- 4~5단계를 넘기지 않음
- 설명 문장이 아니라 명사/동사구로만 표기
- 현재 단계는 색·굵기·`현재` 보조 텍스트로 구분
- 완료 여부를 시스템이 확정할 수 없는 단계는 완료 표시를 하지 않음
- 화면에서 실제로 수행할 수 없는 단계는 링크처럼 보이게 만들지 않음

## 9. 페이지별 추가 개선안

| 페이지 | 문제/기회 | 개선안 |
| --- | --- | --- |
| 개요 | 준비 상태 수치가 많고, 초기 사용자가 어디서 시작할지 바로 알기 어려움 | 상단에 `지금 막힌 단계` 1개와 다음 행동 링크를 표시. 모든 수치는 `기준 데이터`와 `사건 처리` 두 묶음으로 접기 |
| 안전기준 | 6개 숫자 열이 좁은 화면에서 과밀 | 데스크톱 표 유지, 모바일은 기준명·준비 상태·조항 수만 보이고 세부 수치는 펼치기 |
| 사고보고서 | 업로드, 원문 확인, 분석 행동이 한 목록 행 안에 분산 | 진행 상태를 `추출 오류 / 원문 확인 필요 / 분석 가능 / 분석 완료` 칩으로 통일하고, 행마다 다음 행동 버튼 하나를 우선 표시 |
| 리콜 | 목록에서 국내 유통 확인과 분석의 우선순위가 섞임 | `국내 유통 확인 필요` 필터를 기본 빠른 필터로 제공하고, 분석 행동은 상세/행 확장으로 분리 |
| 분석 상세 | GPC, 품목, 해외 리콜 근거, 후보 조항이 길게 이어짐 | 우측 목차 외에 상단 `검토 요약`을 두고, 후보 조항을 최우선 영역으로 배치. 보조 근거는 접기 제공 |
| 위해요인 코드북 | 참고 화면인데 개정 절차 설명이 길게 노출 | 기본은 현재 판·검색·코드 목록, 개정 영향과 관리자 절차는 접은 `개정 관리`로 이동 |
| 운영 | 우선순위가 세로 나열에 묻힘 | 제3절의 대시보드 구조 적용, 평시에는 요약과 최근 변화만 우선 노출 |

## 10. 추가 완료 기준

- 모든 주요 페이지 제목 아래에 1줄 업무 흐름이 있고, 작은 화면에서도 두 줄 이내로 읽힘
- 반복되는 설명 문구를 줄이고, 각 상태는 `무슨 상태인지 / 왜 중요한지 / 다음에 무엇을 할지`를 빠르게 알 수 있음
- 자동 갱신 중에도 검색 조건·목록 위치·열어 둔 상세 정보가 예상치 않게 초기화되지 않음
- 성능 개선 전후의 측정값을 남기고, 가장 느린 화면의 초기 표시 시간이 개선됨
- 키보드만으로 메뉴, 목차, 검색, 목록 액션, 맨 위로 이동을 모두 수행할 수 있음
