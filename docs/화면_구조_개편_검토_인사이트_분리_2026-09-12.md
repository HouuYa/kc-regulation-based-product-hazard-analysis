# 사건 분석 화면 — 검토용 / 인사이트용 탭 분리 설계

작성일: 2026-09-12
범위: `/analysis/[caseId]` 한 페이지(근거는 §2 참고)
이번 단계: 설계만 확정. 화면 동작 코드는 아직 바꾸지 않음

## 1. 결론 요약

담당자가 사건 분석 화면을 "검토와 인사이트가 한 화면에 섞여 복잡하다"고 지적했다. 원인은 한 페이지 안에 성격이 다른 두 가지 일 — ① 조항 후보를 채택·반려하는 **결정 작업**과 ② 그 결정을 도울 통계·사례·후보 같은 **참고 자료 읽기** — 가 스크롤 하나로 이어져 있다는 것이다. 앱 전체를 감사(audit)해 보니 이 문제는 이 페이지 하나에만 있고, 다른 목록·검토 화면은 이미 깔끔하게 한쪽으로 정리돼 있다(§2). 해결책은 같은 URL 안에서 "검토" 탭과 "인사이트" 탭으로 나누는 것이다(§3). 병행 점검 판정(채택·보류·해당없음)처럼 두 성격을 동시에 갖는 항목은 양쪽에 다른 형태로 걸친다 — 인사이트 탭엔 전체 설명과 함께, 검토 탭엔 미판정 항목만 간단히.

## 2. 범위 — 왜 이 페이지 하나뿐인가

`src/app/` 아래 모든 페이지를 감사한 결과다.

| 페이지 | 결정 버튼 | 별개 인사이트 자료와 섞여 있는가 |
| --- | --- | --- |
| `/analysis/[caseId]` | 채택/반려, 병행 점검 판정, 어린이제품 확정 | **그렇다** — 이번 개편 대상 |
| `/accidents`, `/recalls` | 원문 확인, 분석 실행 | 아니다 — 상태 요약은 진행률이지 별개 참고자료가 아니다 |
| `/standards/review`, `/keywords`, `/terms` | 확정/반려 | 아니다 — 행마다 붙은 정보는 그 행 자신의 판정 근거일 뿐, 별개 인사이트 구역이 없다 |
| `/insights`, `/codebook`, `/llm`, `/standards` | 없음 | 이미 순수 읽기 전용 |
| `/ops` | 운영 트리거(재시도·토글 등) | 섞여 있으나 축이 다르다 — "운영 컨트롤 vs 운영 대시보드"이지 "사건 검토 vs 사건 인사이트"가 아니다. 이번 개편 대상에서 제외 |

**결론**: "전부 적용"이 가리킬 다른 대상이 현재 코드베이스엔 없다. `/ops`를 포함할지는 별도 판단이 필요하며, 이번 스펙에는 넣지 않는다(§6 남겨 둔 것 참고).

## 3. 설계 — 탭 배치

### 3.1 탭 밖 (항상 보임, 공통 헤더)

검토든 인사이트든 먼저 알아야 하는 전제 정보라 탭으로 가리지 않는다.

- 사건 요약: 제목·원문(`<details>`)·붙은 코드·FlowChart·첨부 사진
- 품목·적용기준: 스코프 확정 상태, 적용 기준 목록, 어린이제품 여부 **확정 버튼은 예외적으로 여기 남긴다** — 이 결정은 적용 기준 자체를 바꾸는 전제 조건이라, 검토 탭 안으로 옮기면 "품목·적용기준"과 "그걸 바꾸는 버튼"이 떨어져 오히려 헷갈린다.

### 3.2 검토 탭

담당자가 조항별로 채택·반려를 "남기러" 오는 화면. 버튼이 중심이고, 설명은 판정에 필요한 최소한만 남긴다.

- 관련될 수 있는 조항 목록(`SectionBlock`, 채택/반려 `recordReview`) — 상위 5건 + "더 보기". 이 목록에 딸린 경고 배너(재채점 실패, 원인 미확정 `hfUnresolved`, AI 가상 조항 `hyde_text` 보기)도 같은 묶음으로 이동한다 — 전부 이 목록 자체에 대한 설명이라 목록과 떨어지면 안 된다
- 원인 후보 고르기(`CausePicker`, `CauseResult`) — 원인 미확정 사건에서만 뜨는 보조 검색, 이것도 "무엇을 채택할지 고르는" 작업이라 검토 탭
- CSV 내려받기 — 검토 결과물이므로 검토 탭
- **병행 점검 미판정 큐** — `SecondOpinionFindings`의 findings 중 `decision == null`인 것만, 절 번호/사건명 + 판정 버튼 3개만(긴 rationale 없이). 길게 읽지 않고 빠르게 훑어 판정하는 용도

### 3.3 인사이트 탭

담당자가 "이 사건에 대해 더 알아보려고" 오는 화면. 전부 읽기 자료이고, 병행 점검 판정 버튼만 예외적으로 그 자리에 같이 둔다(맥락을 읽으면서 바로 판정해도 되도록).

- 보고서가 한 일(`InvestigationSummary`) — 병행 점검 실행/다시 점검 버튼 포함. 이 버튼은 "결정"이 아니라 "인사이트 재생성"이라 여기 둔다
- GPC 품목분류 후보
- 해외 리콜 근거
- 병행 점검 소견 전체(`SecondOpinionFindings`) — 시험 범위 공백·인증표시 확인항목·기준 사각지대·리콜 교차 근거, 전부 통계·사례·rationale과 함께. 판정 버튼도 같이 뜬다(이미 판정한 것은 "판정함" 표시로, §3.2와 데이터 소스는 같다)

### 3.4 겹치는 지점 — 병행 점검 판정

같은 `second_opinion_finding` 데이터를 두 군데서 다르게 그린다. 새 상태를 만들지 않는다 — 화면만 두 가지다.

- 인사이트 탭: 지금의 `FindingList`(절 번호·rationale·근거 인용·판정 버튼 전부)
- 검토 탭: 같은 findings를 `decision == null`로만 거른 **경량 버전**(제목/코드 한 줄 + 버튼) — 새 컴포넌트 하나(`FindingQueue` 가칭)가 필요하다. `recordFindingReview` 액션은 그대로 재사용(이미 `caseId`·`findingId`·`decision`만 받는다)

### 3.5 탭 전환 방식

같은 URL(`/analysis/[caseId]`), 클라이언트 컴포넌트 하나가 탭 상태를 들고 있는다. `?tab=review|insight` 같은 쿼리 파라미터로 상태를 주소에 실어 둔다 — 링크 공유·새로고침 시 탭이 유지되고, 기존에 페이지 안 앵커(`#analysis-results` 등)를 가리키던 외부 링크(`/accidents`·`/recalls`의 "분석 보기" 링크, `PageToc`)가 있으면 올바른 탭이 열리게 할 수 있다. 서버 컴포넌트 구조(`page.tsx`가 데이터를 불러오는 방식)는 그대로 두고, 탭 전환만 클라이언트에서 처리한다 — 두 탭 다 이미 서버에서 렌더된 내용을 감추고 보이고만 하면 되므로, 데이터를 다시 불러올 필요가 없다.

## 4. 건드릴 파일

- `src/app/analysis/[caseId]/page.tsx` — 섹션을 공통/검토/인사이트 세 묶음으로 재배치하고, 탭 컨테이너로 감싼다
- `src/app/analysis/[caseId]/SecondOpinion.tsx` — `SecondOpinionFindings`(인사이트용, 그대로) 옆에 `FindingQueue`(검토용, 신규)를 추가
- `src/components/` — 탭 UI 자체를 담을 작은 클라이언트 컴포넌트 하나 신규(예: `Tabs.tsx`) — 이미 `PageToc.tsx`가 `IntersectionObserver` 기반 클라이언트 컴포넌트 패턴을 갖고 있어 그 스타일(디자인 토큰, `'use client'` 구조)을 따른다
- `src/app/analysis/[caseId]/actions.ts` — 변경 없음(기존 `recordReview`·`recordFindingReview`·`setChildProductCheck`·`runAnalysisAction`·`runSecondOpinionAction` 재사용)

계산 로직(`src/lib/search/*`, `src/lib/second-opinion/*`)은 건드리지 않는다 — 이번 개편은 배치·탐색이지 판정 로직이 아니다.

## 5. 검증 계획

- `npm run typecheck`·`npm run lint`·`npm run build`
- 사건 7325(라운드 73에서 이미 상태를 확정해 둔 사건 — 시험 범위 공백 2건, 리콜 교차 근거 16건, 미판정 병행 점검 소견 다수)로 실제 서버 렌더 확인:
  - 검토 탭에 병행 점검 미판정 항목이 실제로 뜨고, 판정 버튼을 누르면 `decision`이 저장되어 인사이트 탭에도 "판정함"으로 반영되는지
  - `?tab=` 쿼리로 새로고침해도 탭이 유지되는지
- 결과가 아무것도 없는 사건(품목 미확정, `!run` 상태 등) 하나 더 확인 — 탭 분리 후에도 기존 빈 상태 문구들이 정상 위치(어느 탭)에서 뜨는지 회귀 확인

## 6. 남겨 둔 것

- `/ops`(운영 컨트롤 vs 대시보드)는 이번 스펙에 안 넣었다 — 축이 다르다고 판단했고, 필요하면 별도로 스펙을 낸다.
- 탭 URL 파라미터 이름(`tab=review|insight`)은 가안이다 — 구현 단계에서 기존 라우팅 규칙과 충돌이 없는지 한 번 더 본다.

## 7. 추가 — 목록 페이지(/accidents, /recalls)로 확장 (2026-09-12 추가 합의)

담당자가 사건 분석 화면 외에 "사고, 리콜, KC안전기준 등등 모든 페이지"에도 적용해 달라고 요청했다. `/standards`·`/standards/review`는 §2 감사에서 이미 한쪽으로 깔끔했으므로(각각 순수 읽기 전용·순수 검토 전용) 그대로 둔다. `/accidents`·`/recalls`는 "결정 버튼 + 무관한 인사이트"가 섞인 게 아니라 업로드폼·현황요약·설명문·행별 목록이 한 화면에 쌓여 복잡해 보이는 경우였다 — 같은 "버튼(할 일) vs 읽기 전용(현황)" 축을 이름만 바꿔 재적용한다.

### 7.1 공통 (탭 밖)

`PageHead`(제목·설명·워크플로 다이어그램), `DoneBanner`, `ConnectionError` — 페이지 전체의 방향을 잡는 정보라 탭으로 안 가린다.

### 7.2 "현황" 탭 — 읽기 전용

- `StatusBar`(집계 숫자)
- (사고보고서만) "올린 뒤 무슨 일이 일어나는지" 여섯 걸음 설명 `<details>`
- `AutoRefresh` 안내 문구

### 7.3 "처리할 것" 탭 — 행별 작업

- (사고보고서만) "사고보고서 올리기" 업로드 폼 — 새 행을 만드는 능동적 작업이라 여기
- `BoardToolbar`(찾기·필터), `BoardTabs`(대분류/원본 구분)
- 행 목록 전체(`EmptyState` 또는 각 `article`) — **행을 필터링하지 않는다.** "액션 필요한 행만" 거르면 검색·전체 열람이 깨진다. 탭이 가르는 것은 "이 화면에서 지금 무엇을 하러 왔는가"이지 행의 부분집합이 아니다
- `BoardPager`

### 7.4 건드릴 파일 (추가)

- `src/app/accidents/page.tsx`, `src/app/recalls/page.tsx` — §7.1~7.3 구조로 재배치
- `src/components/Tabs.tsx`(§4에서 신규 예정) — `analysis/[caseId]`와 그대로 공유. 탭 라벨만 다르게 받는다(`검토/인사이트` vs `현황/처리할 것`)
